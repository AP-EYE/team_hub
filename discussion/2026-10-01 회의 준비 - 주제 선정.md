## 후보별 4줄 (노션 원문 요약)

### 재훈: BOLA 확정·보류
- 가설: 테스트 객체 몇 개만 지정해 권한표 없이 BOLA를 확정하고 근거 없는 객체는 보류한다. 접근 성공 여부만 쓰는 판정보다 공개·공유 조회 오탐률이 낮다.
- 필요: 단순 "타인 접근 = 위반"은 공개·공유 조회를 오탐한다. 권한표 전체는 비용이 크다.
- 선행: Sahin et al. 2604.00702, Atlidakis ICST 2020 (vault 노트에는 BACScan CCS 2025 추가)
- 차이: 테스트 객체 단위 확정, 보류 분리, 확정 범위·오탐률·보류율 측정.
- 예비 실험: Gitea 28.0.0에서 단순 규칙 오탐 8/18 확인.

### 성빈: 예측 점수 vs 실측 점수
- 가설: 타인 데이터를 조회하지 않고 산정한 예측 노출 점수가 재전송으로 확인한 실측 점수의 우선순위를 재현한다.
- 필요: 운영 환경에서 타인 토큰 재전송은 법적·윤리적 부담이 크다.
- 선행: EDEFuzz ICSE 2024, SMS URL 2601.09232
- 차이: 재전송 없이 예측한 노출 규모·내용을 격리 환경 실측과 대조해 정확도를 검증한 사례가 없다.
- 이번 수정: 점수 공식 출처(L-Severity, M-Score, BRM, Vavilis 2015) 표 추가.

### 민경: 로그 최소 저장 (수정본)
- 가설: 게이트웨이 로그에 원문 대신 메타데이터만 저장해도 유출 범위 산정은 유지하면서 저장소 개인정보는 크게 줄인다.
- 필요: 원문 로그는 사고 후 유출 범위 확인 때문에 필요하지만 그 자체가 약점(CWE-532)이다. 너무 줄이면 조사가 안 된다(Azahari 2024).
- 선행: Proteus PoPETs 2026 (2603.06540), Vazão JISA 2023
- 차이: 기존 연구는 가명처리해도 조사가 된다고 주장하거나 시연만 했다. 저장 수준별로 원문 대비 산정 정확도와 잔여 개인정보를 함께 잰다.
- 이번 수정: 다운스트림 작업을 "BOLA 판정"에서 "사후 유출 범위 산정(포렌식)"으로 바꿈. 목표치 정확도 95% 이상, 잔여 필드 80% 이상 감소(팀 설정값).

### 유상: 권한 회수 후 잔존 권한
- 가설: 권한 회수 전 세션으로 보호 API를 다시 호출하고 권한 변경 근거·반영 기한·실제 반환 데이터를 함께 확인해 잔존 권한을 판정한다. 근거 없으면 보류. 기한과 응답 코드만 쓰는 방식보다 오탐이 낮다.
- 필요: 권한을 없애도 기존 세션에 권한이 남을 수 있다(pyLoad GHSA-66hx-chf7-3332). 반대로 정상 반영 지연도 있다.
- 선행: MST-wi TSE 2023, ACtests 2505.12770, Santos-Grueiro 2609.02866
- 차이: 시간, 응답 내용, 변경 확인, 대조 요청 근거를 하나씩 추가하며 오탐·미검출 변화를 같은 요청 기록으로 비교한다.

## 후보별 회의 질문

- 재훈 BOLA
  1. 재현율을 재려면 BOLA를 주입한 Gitea 취약 버전이 필요하다. 누가, 언제까지 만들 수 있나?
  2. 엔드포인트당 테스트 객체 3개로 충분한지 어떻게 보일 것인가?
  - 답변 준비 (2026-10-01 논문 검색)
    - Q1 재현율: 취약 버전을 직접 만들 필요가 꼭 있지는 않다. 선행연구 관행은 두 가지다.
      - 알려진 취약 버전 사용: BACScan(CCS 2025)은 알려진 BAC 취약점 44개(MBAC 24, RBAC 20)가 있는 앱 6개의 구버전을 정답 세트로 쓰고 재현율을 냈다(RBAC 재현율 75.00%, 표 2). 정답 세트에 Memos-0.9.0(알려진 취약점 MBAC 4 + RBAC 5)이 있다. 로컬 PDF `3_연구/papers/BACScan_CCS25.pdf`.
      - 결함 주입: EvoMaster 보안 확장(Sahin et al., 2604.00702)은 실험 대상에 인공 예제 9개와 vulnerable-by-design REST API 8개를 포함한다(초록). 접근 제어 변이 분석은 Elrakaiby, Mouelhi, Le Traon, "Testing Obligation Policy Enforcement using Mutation Analysis"(ICST 2012 무렵)가 있으나, 대상이 의무(obligation) 정책이고 목적이 테스트 묶음 품질 평가라 탐지기 재현율 근거로는 약하다(보류).

    - 1차 읽기 결과 (paper-reading 스킬, 2026-10-01)

      | 논문 | 읽기 수준 | 한 것 | 안 한 것 | 판정 |
      |---|---|---|---|---|
      | BACScan, CCS 2025 | 1차 + 2차(§5.1 표 1·2) | 페이지 간 데이터 의존으로 읽기·수정 BAC를 블랙박스 탐지. 앱 20개에서 89개 발견, 신규 CVE 35개 | 크롤러가 못 간 페이지는 미탐(§6), GET 요청 토큰 삽입 제외(§6). 서론에서 "응답 비교 오라클의 가정은 읽기(RBAC)에서는 성립한다"고 봄 | 살림. 직접 비교군, 정답 세트(Memos-0.9.0) 재사용 |
      | EvoMaster 보안 확장, arXiv 2604.00702 | 1차 | REST 퍼저에 인가 위반 오라클 7개(결론은 인젝션 포함 9개) 추가. API 52개(인공 9, 취약 설계 8, WFD 36) | 일반화 한계, 산업 API 미평가(§6). 1차 범위에는 정밀도·재현율 수치가 없음 | 살림. 2차에서 3.3절 오탐 논의와 표 1의 취약 설계 API 8개 확인 필요 |
      | Elrakaiby·Mouelhi·Le Traon, ICST 2012 무렵 | 1차 | 의무 정책 관리에 최소 오류를 넣는 변이 연산자 정의, 자바 프로그램 실험 | 웹·API 아님, 명세 밖 부분 테스트는 비용 문제로 미해결(§VI), 정책 관리자 분리 테스트는 향후 과제 | 보류. "변이체를 실제 결함 대용으로 쓴다"는 방법 근거로만 |

      - 주의 1: BACScan 서론은 읽기 위반에는 응답 비교가 대체로 통한다고 본다. 우리는 "공개 객체 때문에 읽기에서도 오탐이 난다"를 주장하므로, BACScan 3.3절의 공개 페이지 필터를 근거로 차이를 설명해야 한다.
      - 주의 2: RBAC 5개의 정확한 엔드포인트는 미확인.

    - EvoMaster 2차 (3.3절, 5.1절, 표 1·3)
      - 3.3절 인가 누락 오라클은 같은 자원에 PUT·PATCH·DELETE 중 둘이 403이고 하나만 2xx이면 위반으로 본다. 대상이 **수정 동사**다. 읽기(GET) BOLA를 판정하는 오라클이 아니다. 저자도 이 규칙의 오탐 가능성을 인정한다("we cannot exclude the presence of some false-positives").
      - RQ2는 취약 설계 API 8개(capital, crAPI, damn-vulnerable-rest, DVAPI, dvws-node, VAmPI, vulnerable-rest-api, WebGoat)에서 발견 결함 수만 센다(표 3). 알려진 취약점 대비 재현율은 내지 않는다.
      - RQ1은 인공 API 9개에 결함을 주입해 "모두 탐지"를 보였다. 주입은 실현 가능성 확인용이다.
      - 우리와의 관계: EvoMaster는 공개·공유 같은 예외 때문에 단순 규칙이 오탐한다고 지적만 하고(3.3절), 그 대안도 수정 동사 일관성이다. 읽기에서 공개 객체를 구분하는 문제는 여기서 남는다.

    - Memos 0.9.0 확인 (로컬 docker `neosmemo/memos:0.9.0`, 2026-10-01)
      - 스크립트·결과: `3_연구/data/memos090_visibility_probe.py`, `memos090_visibility_probe_result.txt`
      - 같은 엔드포인트 `POST /api/memo`로 PUBLIC, PROTECTED, PRIVATE 메모를 각각 만들 수 있다. 응답에 `visibility` 필드가 있다.
      - `GET /api/memo/{id}` 결과: PUBLIC은 다른 사용자·비로그인 모두 200, PROTECTED는 로그인 사용자 200·비로그인 403, PRIVATE는 둘 다 403.
      - 단순 규칙("타인이 200이면 위반")은 이 6건 중 3건(PUBLIC 2, PROTECTED 1)을 오탐한다. 공개 범주가 3개라 테스트 객체도 3개 필요하다(Gitea는 공개·비공개·공유).
      - 알려진 읽기 취약점 예: CVE-2022-4811 "0.9.0 이하에서 편집 화면 URL 조작으로 비공개 메모 접근", 0.9.1에서 수정(https://vulert.com/vuln-db/CVE-2022-4810 검색 결과 기준). 위 `GET /api/memo/{id}`는 403이므로 취약 경로는 다른 엔드포인트다. 원 보고서(huntr) 2차 확인 필요.
      - 제안: Memos는 메모마다 PUBLIC/PROTECTED/PRIVATE 공개 범위를 지정한다(https://usememos.com/docs/usage/sharing). 객체별 공개 상태와 알려진 취약점 정답이 한 앱에 같이 있고, BACScan과 같은 대상이라 직접 비교도 된다. Gitea는 오탐률용, Memos-0.9.0은 재현율용으로 쓴다. 미확인: 0.9.0에 공개 범위 기능이 이미 있었는지, RBAC 5개가 어떤 엔드포인트인지.
      - 참고: Gitea 최근 IDOR CVE-2026-58438은 이슈 의존성 삭제(쓰기) 문제라 읽기 BOLA 정답으로는 맞지 않는다(https://advisories.gitlab.com/golang/gitea.dev/CVE-2026-58438/).
    - Q2 테스트 객체 3개 근거: 범주 분할 기법(Ostrand, Balcer, "The category-partition method for specifying and generating functional tests", CACM 31(6), 1988, pp. 676-686). 입력 영역을 동치 범주로 나누고 범주마다 대표값을 고른다. 공개·비공개·공유가 범주이고 각 1개가 대표 객체다. 한계: 관리자·조직 권한, PROTECTED(로그인 사용자) 같은 범주가 있으면 범주 수가 늘어난다. 3개는 고정값이 아니라 "앱의 공개 범주 수"로 표현하는 편이 정확하다.
- 성빈 예측·실측

2. 탈락 기준 먼저 적용: 실험 대상이 없거나 한 단계로 좁혀지지 않는 후보 제외 (10분)
3. 남은 후보 중 해결 가능성으로 1개 선정 (10분)
4. 선정 주제에 교수님 절차 적용: 직접 다룬 논문 검색 → 있으면 AI로 부족한 점 → 해결 방법 → "기존 연구는 여기까지, 우리는 이 차별성" (20분)
5. 역할 분담 (5분)

## 메모

- 이 비교의 "리스크"와 "질문"은 노트 작성자(재훈 측) 관점이다. 회의에서 각 담당자 답변으로 갱신한다.
- 재훈 후보가 예비 실험을 한 유일한 후보라 비교가 재훈 쪽에 유리하게 보일 수 있다. 회의에서는 "지금 준비도"가 아니라 "해결 가능한가"로 판단한다.
