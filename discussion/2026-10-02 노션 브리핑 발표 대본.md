## 그대로 말할 대본

### 1. 주제와 필요성

화면: 맨 위 2단의 연구 주제와 필요성 콜아웃을 함께 보여줍니다.

> 교수님께서 질문 주신 공개 조회 API와 BOLA의 구분 문제를 바탕으로 주제를 구체화했습니다.
>
> 연구 질문은 다른 계정이 객체를 읽었을 때, 정상적인 공개·공유 조회인지 실제 접근 위반인지 어떻게 구분할 것인가입니다.
>
> 예를 들어 A의 비공개 저장소를 B에게 공유했다면 B의 조회는 정상입니다. 반대로 B에게 읽기 권한이 없는데 데이터가 반환됐다면 위반입니다.
>
> 응답이 성공했다는 사실만으로는 두 경우를 구분할 수 없습니다. 그래서 응답과 별도의 권한 근거를 함께 보는 방법을 검토하고 있습니다.

### 2. BACScan

화면: BACScan의 첫 요약과 바로 아래 공개 필터 원문 이미지입니다.

> 먼저 기존 연구가 이 문제를 어떻게 처리하는지 직접 비교했습니다.
>
> BACScan은 두 계정으로 각각 탐색하고, URL과 내용이 같은 페이지를 공개 자원으로 제외합니다. 공유받은 페이지도 두 계정에서 관찰됐다면 제외될 수 있습니다.
>
> 따라서 공유 객체를 처리하지 못한다고 주장하는 것은 아닙니다. 저희가 검증할 조건은 읽기가 허용됐지만 한쪽 탐색에서 빠지는 경우입니다.

### 3. AuthScope

화면: AuthScope의 첫 요약만 봅니다.

> AuthScope는 로그인 없이 앱을 다시 탐색해 공개 자원을 제외합니다.
>
> 다만 로그인 사용자에게만 공개되거나 특정 계정에 공유된 객체의 허용 여부는 비로그인 조회만으로 확인하기 어렵습니다. 이 차이를 비교 조건으로 보겠습니다.

### 4. AuthProbe

화면: AuthProbe 첫 요약을 보여준 뒤, 두 번째 원문 이미지인 한계 문단으로 이동합니다.

> AuthProbe는 계정별 목록에 나타난 객체로 읽기 자격을 추정합니다. 여기서 목록은 목록 조회 API가 반환한 객체들입니다. 다른 계정의 목록에만 있는 객체를 교차 조회해 실제 객체가 반환되면 BOLA로 보고합니다.
>
> 따라서 다중 계정 검사와 반환 객체 확인 자체는 차별성이 아닙니다.
>
> 원문에서도 목록이 소유 관계를 정확히 반영하지 않으면 판단이 왜곡될 수 있다고 인정합니다. 저희는 이 전제를 공개·공유 객체의 목록 누락 조건으로 구체화해 검증하려 합니다.

### 5. EvoMaster와 추가 조사

화면: EvoMaster 요약을 짧게 짚은 뒤 ‘추가 조사’ 표의 오른쪽 열을 봅니다.

> EvoMaster는 수정 동사 간 불일치 검사이므로 GET 비교와 구분합니다.
>
> 추가 조사에서는 Rennhard 논문이 탐색 누락 오탐과 테스트 데이터 보완을 이미 다뤘다는 점을 확인했습니다.
>
> FlowWatcher는 별도의 정책으로 권한 상태를 관리하고, 공개 도구인 AuthzTrace는 객체 표식과 작은 권한 규칙으로 응답을 검사합니다.
>
> 따라서 별도 권한 근거를 사용하는 것 자체를 차별성으로 주장하지 않겠습니다.

### 6. 같은 사례로 직접 비교

화면: 비교표의 두 번째 행을 가리킵니다. 질문이 있을 때만 네 번째 행도 설명합니다.

> 비교에서 가장 중요한 사례는 이 두 번째 행입니다.
>
> B에게 공유한 객체가 B의 탐색이나 목록에는 없지만, 직접 조회하면 반환되는 경우입니다.
>
> 표의 관찰 기반 두 방법은 조건에 따라 이 접근을 위반 후보로 판단할 수 있습니다. 설정 근거를 사용한다면 공유 관계에 따라 정상 접근으로 구분합니다.
>
> 다만 AuthzTrace에도 B의 읽기를 허용하는 규칙을 넣으면 정상으로 구분할 수 있습니다. 우리만 처리하는 사례는 아닙니다.
>
> 이 표는 아직 도구를 실행한 결과가 아닙니다. 논문 절차를 같은 조건에 대입한 분석이며, 실제 결과는 실험으로 확인하겠습니다.

### 7. 우리 방법과 기여의 조건

화면: 개선하려는 점의 첫 콜아웃과 판정 절차 오른쪽 표입니다.

> 저희 방법은 테스트 객체의 공개 범위와 공유 관계를 기록하고, 진단 직전에 상태를 재확인해 조회 결과와 대조합니다.
>
> 허용된 계정에 객체가 반환되면 정상 접근입니다. 금지된 계정에 비공개 본문 같은 보호 내용이 반환되면 위반입니다. 설정이나 보호 내용의 반환을 확인할 수 없으면 보류합니다.
>
> 여기서 권한표 없이라는 말은 전체 운영 객체의 권한표를 작성하지 않는다는 뜻입니다. 테스트 객체의 권한 정보는 필요합니다.
>
> 설정값을 수동 권한 규칙으로 옮기는 것과 같다면 기여가 부족합니다. 검증할 후보는 설정 근거의 확보·재확인 절차가 제공하는 판정 개선과 준비 비용입니다.

### 8. 현재 확인한 결과

화면: 현재 결과의 첫 콜아웃과 8/18·3/6 부분입니다. 서비스 소개 전체는 읽지 않습니다.

> 예비 실험에는 코드 협업 서비스인 Gitea와 메모 앱인 Memos를 사용했습니다.
>
> 타인 계정의 조회 성공을 위반으로 보는 단순 규칙은 Gitea의 정상 요청 18건 중 8건, Memos의 6건 중 3건을 오탐했습니다.
>
> 단순 규칙의 문제를 보여주는 결과이며, 저희 판정기의 개선 결과는 아닙니다. 실제 읽기 위반은 아직 확인하지 않아 재현율도 계산할 수 없습니다.

### 9. 실험과 평가

화면: 비교 방법의 수동 부분 정책 행, 정답 검증 목록, 평가 지표 순으로 이동합니다.

> 다음에는 Gitea에서 정상 공개·공유 접근을 평가하고, Memos에서 실제 읽기 위반과 접근 거부 대조군을 확보하겠습니다.
>
> 같은 계정과 객체, 요청으로 관찰 기반 판정과 저희 방법을 비교하겠습니다. 탐색 보완과 AuthzTrace식 수동 부분 정책도 비교군에 넣겠습니다.
>
> 평가 정답은 앱 정책과 설정 상태를 별도로 검토해 정하겠습니다. 판정기 입력을 그대로 정답으로 삼지 않겠습니다.
>
> 공유 객체의 목록 포함·누락과 실제 금지 내용의 누출을 비교합니다. 자연스러운 누락과 인위적인 제거도 구분하겠습니다.
>
> 재현율, 오탐률, 보류율과 준비·검토 비용을 측정합니다. 보류·미검사 위반도 미탐으로 셉니다. 수동 부분 정책 입력과 비교해 같은 사례의 비용과 같은 시간 안에서 다룰 수 있는 사례 수를 확인하겠습니다.

### 10. 범위와 마무리

화면: 연구 범위의 첫 콜아웃입니다. 마지막 질문은 화면에서 눈을 떼고 말합니다.

> 이번 연구는 읽기 BOLA의 확정·보류 판정에 집중하겠습니다. 게이트웨이는 요청 실행과 근거 기록에 사용합니다.
>
> 이 비교 조건과 입력 비용까지 포함해 검증하는 방향이 연구 질문으로 적절한지 의견을 부탁드립니다.

## 어디를 보면서 말할지

- 화면을 계속 읽기보다 각 목차의 첫 콜아웃에서 말할 내용을 확인합니다. 설명을 마친 뒤 다음 목차로 이동합니다.
- 논문 부분은 요약을 보고 방법을 설명한 뒤 원문 이미지를 잠깐 가리킵니다. 영어 문단 전체를 낭독할 필요는 없습니다.
- AuthProbe는 알고리즘 이미지보다 한계 문단 이미지에 시간을 씁니다. 목록 기반 판단의 전제와 우리 실험 질문이 연결되는 근거입니다.
- 추가 조사 표에서는 ‘이미 다룬 문제’와 ‘차별성이 아닌 부분’을 짚습니다. 세 자료의 세부 기능을 모두 읽지 않습니다.
- 비교표는 두 번째 행을 왼쪽 사례부터 오른쪽 판정안까지 따라가며 설명합니다. 네 행 전체를 읽지 않습니다.
- 판정 절차는 왼쪽 세 단계의 제목을 확인한 뒤 오른쪽 정상·위반·보류 표를 가리킵니다.
- 예비 결과는 숫자를 읽은 직후 “우리 판정기의 개선 결과는 아닙니다”를 붙입니다.
- 평가 부분은 재현율·오탐률·보류율을 가리킨 뒤 준비·검토 비용으로 시선을 옮깁니다.
- 마지막 질문은 교수님을 보며 말합니다.

## 발표 직전과 진행 중의 팁

- 발표 전에 이 대본을 한 번 소리 내어 읽고 시간을 확인합니다. 5분 배분은 목표이므로 말하는 속도에 맞춰 조정합니다.
- 화면 공유 중에는 노션 브리핑을, 발표자 쪽에는 이 대본을 띄웁니다. 발표 화면에서 대본을 찾느라 계속 이동하지 않도록 합니다.
- 스크롤을 멈춘 뒤 해당 부분을 설명합니다. 화면 이동과 긴 설명을 동시에 하지 않습니다.
- “목록에 없다는 사실이 접근 금지를 뜻하는가”와 “응답과 별도의 권한 근거” 두 문장은 천천히 말합니다.
- 시간에 쫓기면 AuthScope·EvoMaster 설명을 줄입니다. AuthProbe, AuthzTrace와 겹치는 점, 비교표 두 번째 행, 입력 비용의 한계는 남깁니다.
- 질문을 받으면 먼저 한 문장으로 답하고, 해당 표나 원문 이미지를 찾아 근거를 보여줍니다.
- 기존 연구의 실패를 실증한 것처럼 말하지 않습니다. “이 조건을 비교하겠습니다”, “아직 실험으로 확인하지 않았습니다”를 사용합니다.
- 준비한 화면을 매번 처음부터 훑지 않습니다. 현재 목차의 콜아웃과 표의 핵심 행을 길잡이로 사용합니다.

## 예상 질문과 답변

**권한표 없이 한다면서 결국 사람이 권한을 넣는 것 아닌가요?**

> 맞습니다. 테스트 객체의 권한 정보는 필요합니다. 전체 권한표 입력뿐 아니라 AuthzTrace식 수동 부분 정책 입력과도 준비 비용을 비교하겠습니다. 동일한 판정과 비용이라면 기여가 부족하다고 판단하겠습니다.

**AuthzTrace와 무엇이 다른가요?**

> 현재 기능 조합만으로는 충분한 차별성을 확보했다고 말하기 어렵습니다. 설정 근거를 확보하고 재확인하는 절차가 수동 계약 입력보다 어떤 비용과 판정 효과를 제공하는지 검증하려 합니다. 이점이 없다면 가설을 조정하겠습니다.

**목록에 없는 공유 객체가 실제로 존재하나요?**

> 현재는 논문 절차에서 도출한 비교 조건입니다. 대상 앱에서 이 조건을 실제로 만들 수 있는지 확인하고, 가능하다면 같은 객체로 목록 포함·누락 조건을 비교하겠습니다. 재현할 수 없다면 실험 조건과 주장을 조정하겠습니다.

**BACScan이나 AuthProbe보다 성능이 좋아졌다는 결과인가요?**

> 아닙니다. 현재 숫자는 단순 성공 규칙의 오탐 결과입니다. 논문별 직접 비교와 저희 판정기의 성능 측정은 앞으로 수행할 계획입니다.

**테스트 객체 하나의 결과를 모든 객체에 적용하나요?**

> 아닙니다. 현재 범위에서는 설정 근거를 확보한 테스트 객체를 판정합니다. 다른 객체나 엔드포인트로 자동 일반화하지 않습니다.

**현재 실제 취약점은 재현했나요?**

> 아직 실제 읽기 위반은 확인하지 못했습니다. Memos에서 위반 경로와 접근 거부 대조군을 확보하는 것이 다음 검증 단계입니다.
