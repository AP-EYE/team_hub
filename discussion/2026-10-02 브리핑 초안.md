# CCIT-2 브리핑: 테스트 객체 기반 BOLA 확정·보류 판정

## 1. 한 줄 요약

남의 객체를 조회해서 성공하면 위반으로 보는 단순 규칙은 공개 조회와 공유 조회를 위반으로 잘못 잡는다.
객체를 만들 때 공개 상태를 지정한 테스트 객체로 판정하고, 근거가 없는 객체는 보류로 분리하는 방법을 만들어 오탐률·재현율·보류율을 잰다.

## 2. 문제: 접근 성공만으로는 위반인지 알 수 없다

이번 예비 실험의 기준선은 "다른 계정으로 요청했는데 HTTP 200이면 위반"이라는 단순 규칙이다. 블랙박스 도구 전체의 판정을 대표하는 것은 아니다.
이 규칙이 오탐을 만든다는 것은 최신 연구도 지적한다.

> "Simply stating that a user should not access or manipulate resources of other users would just result in many false-positive faults."
> 다른 사용자의 자원에 접근하면 안 된다고 단순하게 규정하면 오탐이 많이 생길 뿐이다.
> (Sahin, Zhang, Arcuri, arXiv 2604.00702, 2026, §3.3, PDF 7쪽)

우리가 직접 확인한 결과다.
인가가 정상 구현된 Gitea에서 공개 저장소를 열거나, 공유받은 사람이 공유 저장소를 열어도 단순 규칙은 위반으로 판정했다.

## 3. 선행연구와 우리가 다른 점 (교수님 주제 선정 절차 적용)

### 3-1. 이 가설을 직접 다룬 논문이 있나

있다.
공개 자원 때문에 생기는 오탐을 알고, 거르는 방법까지 낸 논문이 두 편이다.

| 논문 | 공개 자원 처리 방식 | 읽기 수준 |
|---|---|---|
| AuthScope (Zuo, Zhao, Lin, CCS 2017) | 로그인 없이 한 번 더 실행해서, 비로그인으로도 응답이 오는 인터페이스를 공개로 보고 제외 (§4.3, PDF 9쪽) | 1차 + 2차 |
| BACScan (Liu et al., CCS 2025) | 공격자·피해자 세션으로 각각 크롤링해서 URL과 내용이 같은 페이지를 공개로 보고 제외 (§4, PDF 8쪽) | 1차 + 2차 |
| EvoMaster 확장 (Sahin et al., arXiv 2604.00702) | 오탐 문제를 지적만 함. 인가 누락 판정은 수정 동사(PUT·PATCH·DELETE) 일관성 규칙 (§3.3) | 1차 + 2차 |

09_bacscan_public_filter.png

### 3-2. 가장 직접적인 논문(BACScan)이 부족한 점

1. 공개 여부를 관찰로 추정한다. 공격자가 탐색 중에 그 페이지에 도달했는지로 공개를 정한다.
2. 원문 공개 필터는 URL·내용의 공통 관찰을 쓴다. 특정 사용자 공유나 로그인 공개도 두 계정 모두 탐색하면 필터에 포함될 수 있다. 이 조건을 처리하지 못한다고 단정하지 않는다.
3. 읽기 위반 절차에는 독립적인 정책 근거의 부족을 보류로 보고하는 별도 단계가 명시되지 않는다. 보류 기능의 가치도 성능과 검토 비용으로 확인해야 한다.
4. 크롤러에 의존한다. 저자 스스로 크롤러가 못 간 페이지는 미탐이 된다고 밝힌다(§6, PDF 13쪽).

1번은 원문 절차에서 나온 우리 추론이며 BACScan이 측정한 오류는 아니다.

### 3-3. 우리는 어떻게 해결하나

| BACScan의 부족한 점 | 우리 방법 |
|---|---|
| 공개 여부를 탐색 도달로 추정 | 테스트 객체를 만들 때 공개 상태를 지정해 독립적인 정답으로 쓴다 |
| 공개·공유 처리의 탐색 의존성 | 공개·로그인 공개·특정 공유 조건과 계정별 탐색 도달 여부를 교차 평가 |
| 위반·정상 두 판정 | 근거 없는 객체는 보류로 분리하고 보류율을 보고 |
| 크롤러 의존 | 화면 탐색 없이 API 응답과 테스트 객체 ID로 판정 |

### 3-4. 최종 문장

기존 연구는 공개 자원 때문에 생기는 오탐을 알고 있고, 비로그인 실행(AuthScope)이나 두 세션의 탐색 결과 비교(BACScan)로 공개 페이지를 걸러냈다.
우리는 정상 공개·공유 객체가 한쪽 계정의 탐색에서 빠지는 조건에서 관찰 기반 권한 추정과 사전 설정 근거의 차이가 생기는지 검증한다.
객체 생성·공유 설정을 기록한 판정과 단순 규칙·객체 일치 기준선·BACScan식 공개 필터의 오탐률·재현율·보류율·입력 비용을 비교한다.
AuthProbe도 다중 계정과 반환 객체 일치 검사를 사용하므로 그 자체는 차별성이 아니다([원문 §III·§V](https://arxiv.org/html/2607.20574)).

## 4. 가설

공개·비공개·공유 상태의 설정 근거를 쓰면 관찰 기반 판정보다 공개·공유 오탐을 줄이면서 실제 읽기 위반 탐지를 유지하고, 전체 객체 권한표 입력보다 준비 비용을 줄일 수 있다는 가설이다.
테스트 객체의 소유자·공개 범위·공유 대상·계정 역할 입력은 필요하다. 범주별 1개는 초기 점검안이며 충분성은 검증하지 않았다.
한 테스트 객체의 결과를 다른 객체나 엔드포인트의 판정으로 자동 확대하지 않는다.

주의: 테스트 객체는 정답을 우리가 지정하므로 그 위에서 오탐이 0인 것은 당연하다.
따라서 가설은 공개·공유 오탐, 실제 위반 재현율, 설정 입력 비용의 세 조건을 함께 검증한다. 테스트 객체 위의 오탐 감소만으로 기여를 주장하지 않는다.

## 5. 실험 설계

### 5-1. 실험 대상

| 대상 | 쓰는 이유 | 용도 |
|---|---|---|
| Gitea 28.0.0 | 같은 엔드포인트에서 공개, 비공개, 협업자 공유 저장소를 만들 수 있다 | 오탐률 |
| Memos 0.9.0 | 메모마다 PUBLIC·PROTECTED·PRIVATE 지정. BACScan 정답 세트에 포함된 버전 | 오탐률, 재현율 |
| Memos 수정 대조 버전(선정 필요) | 같은 취약 요청이 차단되는 버전 확보 | 재현율 비교(수정 전후). 0.9.1은 경로별 확인 필요 |

이번 공개·공유 상태 실험은 Gitea·Memos를 우선 사용한다.
crAPI의 기존 검색에서 공개 설정 필드 후보가 0건이었다. 이 검색 결과만으로 객체별 상태 실험이 절대 불가능하다고 증명한 것은 아니다.

### 5-2. 정답

- 정답: 객체 생성·공유 설정과 앱 정책 의미로 계정별 허용·금지를 정하고, 실제 응답에 대상 객체가 반환됐는지 확인한다.
- 재현율: Memos의 실제 재현한 읽기 위반을 사용한다. BACScan 표 1의 Memos 알려진 위반 4+5건을 우리 평가 정답으로 자동 옮기지 않는다. 막히면 통제된 취약 변형을 보조 평가에 쓰고 자연 취약점 평가와 구분한다.

### 5-3. 비교군

1. 단순 규칙: 다른 계정으로 HTTP 200이면 위반. 추가로 대상 객체 일치까지 확인하는 기준선을 두어 응답 검사 효과를 분리한다.
2. BACScan식 공개 필터: 두 세션에서 URL과 내용이 같으면 공개로 빼고 나머지를 판정 (원도구를 못 돌리면 논문 절차대로 재구현하고 "재구현"으로 표시)
3. 우리 방법: 테스트 객체 기반 확정·보류 판정

### 5-4. 지표

| 지표 | 뜻 |
|---|---|
| 오탐률 | 정상 접근(공개 조회, 공유받은 조회)을 위반으로 잘못 판정한 비율 |
| 재현율 | 실제 위반 중 위반으로 확정한 비율. 보류한 실제 위반은 놓친 것으로 센다 |
| 보류율 | 전체 중 근거 부족으로 결론을 내리지 않은 비율 |
| 입력 비용 | 테스트 객체 수, 계정 수, 수동 설정 항목 수, 준비 시간, 추가 요청 수 |

Gitea 8/18·Memos 3/6의 분모는 접근 거부를 포함한 전체 정상 요청이다.
정상 공개·공유 반환만 분모로 쓰면 각각 8/8·3/3이다. 두 분모를 섞어 비교하지 않는다.
실제 위반 0건인 예비 실험의 재현율은 계산할 수 없다.

### 5-5. 보류는 어떻게 처리하나

1. 근거 보강: 생성·공유 설정 기록과 정책 의미를 확인한다. 주인 계정의 `private` 필드만으로 특정 사용자의 접근 금지를 확정하지 않는다.
2. 사람 확인: 그래도 근거가 없으면 "확인 필요"로 남기고, 무엇이 없어서 보류했는지 사유를 적는다.
3. 숫자로 공개: 보류는 위반으로도 정상으로도 세지 않고 보류율로 따로 보고한다.

보류한 실제 위반은 재현율에서 미탐으로 센다. 근거 일부를 가린 평가 집합을 따로 만들고 사람 확인 시간을 잰다.
판정률을 조절할 수 있는 방법끼리는 같은 판정률로 비교하고, 고정된 기준선은 원래 판정률과 성능을 함께 보고한다.

## 8. 한계와 아직 확인하지 못한 것

1. 우리 판정기는 아직 없다. 예비 실험은 "단순 규칙이 오탐한다"는 문제 확인까지다.
2. 재현율은 미측정이다. 저장된 `GET /api/memo/{id}` 결과는 비공개에 403이다. 10/2 소스 검토에서 목록 조회의 `visibility` 질의 인자 처리에 읽기 취약 후보를 찾았지만 실행하지 않았다. 0.9.1에도 같은 코드가 있어 수정 버전으로 확정하지 않는다. 상세는 [BOLA 판정 연구 구체화](../docs/research/BOLA%20%ED%8C%90%EC%A0%95%20%EC%97%B0%EA%B5%AC%20%EA%B5%AC%EC%B2%B4%ED%99%94.md)를 따른다.
3. 보류율은 미측정이다. 예비 스크립트에는 제안 판정기가 없으므로 0%라는 성능 결과를 내지 않는다.
4. BACScan식 필터가 Gitea·Memos에서 실제로 무엇을 놓치는지는 아직 측정하지 않았다. 3-2의 1번은 추론이다.
5. [BACScan 원도구 공개 저장소](https://github.com/LFYSec/BACScan)는 10/2 확인했다. 원도구 실행은 미완료이며 공개 크롤러는 README상 간소화된 버전이다.

## 9. 예상 질문과 답

- Q. 권한표 없이 판정한다는 게 무슨 뜻인가?
  - A. 전체 운영 객체 권한표 대신 직접 만든 테스트 객체의 설정을 입력한다. 작은 권한 입력은 여전히 필요하며 준비 비용과 판정 범위를 비교한다.
- Q. 테스트 객체는 몇 개 필요한가?
  - A. Gitea·Memos 각각 세 상태로 초기 점검을 했다. 객체 종류·계정 관계·경로별 정책에 따라 추가 객체가 필요하고, 범주별 하나로 충분하다는 보장은 없다.
- Q. 보류된 것은 누가 판단하나?
  - A. 먼저 생성·공유 설정과 정책 근거를 보강하고, 그래도 없으면 사람이 확인한다. 보류 건수와 사람 확인 시간을 함께 보고한다.
- Q. BACScan도 공개 페이지를 거르는데 뭐가 다른가?
  - A. BACScan도 두 계정이 공통으로 탐색한 공유 페이지를 거를 수 있다. 우리는 탐색에 나타나지 않은 허용 객체에서 설정 근거가 도움이 되는지, 추가 비용은 얼마인지 비교한다.
- Q. 테스트 객체 위에서 오탐 0은 당연하지 않나?
  - A. 맞다. 그래서 공개·공유 오탐, 실제 위반 재현율, 설정 입력 비용의 세 조건을 함께 검증한다.
