# 9/23 계획 발표 피드백 대응 현황 (9/28 기준)

## 1. 받은 피드백

1. 공개 조회 API와 인가 실패를 구분하는 기준
2. 운영 관찰(인벤토리)과 승인된 테스트 환경의 진단을 어떻게 나눌지
3. 결제 등 상태 변경 요청과 민감정보의 처리 범위
4. 게이트웨이 자체 보안 요구사항과 시험 방법
5. 위 항목과 탐지·스코어링 효과를 확인할 정량 목표와 측정 방법

조재현 교수 질문 원문 요지:

- SNS처럼 타인 데이터를 정상적으로 보여주는 API와 BOLA를 어떻게 구분하는가.
- 운영 API에 진단 요청을 재전송하면 결제 같은 부작용이 생길 수 있다. 어떻게 막는가.
- 결제·카드 정보가 섞일 수 있으므로 외부 LLM API 사용은 부적절할 수 있다. 테스트 데이터와 진단 범위를 정하고 그 안에서만 실행하라.
- 게이트웨이는 요청·응답·토큰을 전부 본다. 게이트웨이 자체가 취약점이 되면 안 된다.
- 스코어링으로 어떤 효과를 몇 퍼센트 이상 낼지 정하라. 중간·최종 발표에서 제3자가 도달 여부를 확인할 수 있어야 한다.

## 3. 항목별 대응 상태

### 항목 1. 공개 조회 API와 BOLA 구분 - 부분 대응

- **있는 것**: 발표 전(9/22)에 판정 기준을 신원 비교에서 응답 필드 델타 비교로 바꿨다([ARCHITECTURE](../arch/2026-09-29%20%EA%B2%8C%EC%9D%B4%ED%8A%B8%EC%9B%A8%EC%9D%B4%20%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98.md) 6장). 호출자에 따라 응답 필드가 줄어들면 서버가 인가를 판단하고 있다고 본다.
- **발표 후 확인한 것**: 가장 가까운 선행연구 AuthProbe는 신원 일치로 판정한다. 공개 API 구분 규칙이 없다. 이 지점이 우리 차별점이다.
- **발견한 약점**: 판정표의 `F_other == F_owner → 위반` 규칙은 누구에게나 같은 뷰를 주는 공개 API(공개 게시글, 공개 프로필)를 오탐한다. 교수가 짚은 SNS 사례가 정확히 여기에 걸린다.
- **남은 일**:
  - 동일 뷰 행을 개인정보 교집합으로 나눈다. `F_other == F_owner ∧ F_other ∩ S = ∅`이면 공개 설계 후보, `∩ S ≠ ∅`이면 위반으로 바꾼다.
  - 공개 조회 엔드포인트를 일부러 넣은 테스트셋을 만들어 오탐을 잰다.

### 항목 2. 운영 관찰과 테스트 진단의 분리 - 부분 대응

- **있는 것**: 관찰 모드(통과시키며 로깅)와 진단 모드(다른 세션으로 재생)를 나눴다. 진단 모드는 서면 동의 환경과 자체 벤치에서만 켠다고 적었다([ARCHITECTURE](../arch/2026-09-29%20%EA%B2%8C%EC%9D%B4%ED%8A%B8%EC%9B%A8%EC%9D%B4%20%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98.md) 2장).
- **없는 것**: 그 원칙을 강제하는 장치가 없다. 문장으로만 있다.
- **남은 일**:
  - 운영 환경에서는 인벤토리 수집만 한다. 재전송 기능 자체를 빌드에서 뺄지, 설정으로 막을지 정한다.
  - 진단 모드는 대상 호스트 allowlist와 테스트 계정 목록이 설정돼 있을 때만 기동한다.

### 항목 3. 상태 변경 요청과 민감정보 범위 - 재생 규칙 반영 (09-28), LLM·테스트 데이터 남음

- **09-28 반영**: [ARCHITECTURE](../arch/2026-09-29%20%EA%B2%8C%EC%9D%B4%ED%8A%B8%EC%9B%A8%EC%9D%B4%20%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98.md) 6.4를 고쳤다. 쓰기 메서드는 기본 차단한다. 테스트 계정 소유, 결제 계열 denylist 제외, 명시 허용의 세 조건을 모두 만족할 때만 재생한다. 차단 건은 판정 보류로 표기한다. 아래 남은 일 중 첫 두 개가 이걸로 해결됐다.
- **원래 충돌**: [ARCHITECTURE](../arch/2026-09-29%20%EA%B2%8C%EC%9D%B4%ED%8A%B8%EC%9B%A8%EC%9D%B4%20%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98.md) 6.4는 PUT, PATCH, DELETE를 재생한 뒤 재조회해서 BFLA를 판정한다. 이것은 실제로 상태를 바꾸는 요청이다. 결제 엔드포인트에 적용하면 교수가 지적한 부작용이 그대로 발생한다.
- **있는 것**: 응답 값은 진단 환경 밖으로 내보내지 않고, 외부 모델에는 필드 이름만 보낸다는 원칙이 있다(6.6).
- **남은 일**:
  - 비멱등 메서드(POST, PUT, PATCH, DELETE)는 기본 차단한다. 테스트 계정이 소유한 리소스에 한해서만 명시적으로 허용한다.
  - 결제·주문 계열 엔드포인트는 경로 기반 denylist로 재생 대상에서 뺀다.
  - 외부 LLM을 완전히 빼고 로컬 모델만 쓸지 결정한다. 교수 지적을 따르면 로컬 전용이 기본값이다.
  - 테스트 데이터 정의서를 쓴다. 합성 카드번호 등 실제 값이 없는 데이터만 쓴다고 명시한다.

### 항목 4. 게이트웨이 자체 보안 - 미착수

- 현재 문서 어디에도 없다.
- **남은 일 (요구사항)**:
  - 로그 적재 전에 Authorization 헤더, 쿠키, 토큰을 마스킹한다.
  - 로그 저장소를 암호화하고 접근을 통제한다. 보관 기간을 정한다([ARCHITECTURE](../arch/2026-09-29%20%EA%B2%8C%EC%9D%B4%ED%8A%B8%EC%9B%A8%EC%9D%B4%20%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98.md) 10장의 "응답 본문 보관 여부" 미결과 같이 결정한다).
  - 관리 인터페이스에 인증을 건다. mitmproxy 웹 UI를 외부에 노출하지 않는다.
  - 진단 모드에서 쓰는 테스트 계정 토큰은 메모리에만 두고 디스크에 남기지 않는다.
- **남은 일 (시험 방법)**:
  - 적재된 로그에서 토큰 평문 검색 결과가 0건인지 확인한다.
  - 인증 없이 관리 인터페이스에 접근하면 거부되는지 확인한다.
  - 게이트웨이를 거친 요청의 원본 토큰이 로그에서 복원되지 않는지 확인한다.

### 항목 5. 정량 목표와 측정 방법 - 부분 대응

- **있는 것**: [평가 설계](../arch/%ED%8F%89%EA%B0%80%20%EC%84%A4%EA%B3%84.md)에 지표(조건 비교, 오탐 별도 측정, 필드 분류 정확도)가 있다. [연구 갭 분석](../docs/research/%EC%97%B0%EA%B5%AC%20%EA%B0%AD%20%EB%B6%84%EC%84%9D.md) 5.2에 검증 가설 4개가 있다.
- **없는 것**: 목표 수치가 하나도 없다. [ARCHITECTURE](../arch/2026-09-29%20%EA%B2%8C%EC%9D%B4%ED%8A%B8%EC%9B%A8%EC%9D%B4%20%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98.md) 10장도 "검토 필요 등급 목표 비율 TBD"로 남아 있다. 교수 요구는 "몇 퍼센트 이상"이다.
- **남은 일**: 아래 초안을 팀이 확정한다. 수치는 아직 근거가 없는 제안값이다.

| 대상 | 지표 | 목표 초안 | 측정 방법 |
|---|---|---|---|
| 인가 탐지 | crAPI·VAmPI 인가 취약점 5건 탐지 수 | 5건 중 5건 | 벤치 공개 정답 대조 |
| 오탐 | VAmPI `vulnerable=0` 모드 위반 판정 수 | 0건 | 안전 버전 실행 결과 |
| 공개 API 구분 | 공개 조회 엔드포인트 오탐률 | 신원 비교 방식 대비 절반 이하 | 같은 테스트셋에 두 판정 방식 적용 |
| 사람 입력량 | 판정에 필요한 수동 입력 항목 수 | ZAP Access Rules 완비 조건 대비 90% 감소 | 입력 항목 수와 작성 시간 계측 |
| 필드 분류 | 법적 3등급 분류 정확도 | 85% 이상 | 조문 기반 정답 라벨([법적 근거](../docs/plan/%EB%B2%95%EC%A0%81%20%EA%B7%BC%EA%B1%B0.md)) |
| 필드 분류 | Presidio가 놓친 비정형 민감 필드 탐지율 | 70% 이상 | 강남언니 구조 모사 자체 API |
| 스코어링 | 영향도 순위와 과징금 처분 순위 상관 | 스피어만 0.5 이상 | 개인정보위 공표 처분 사례 |

제3자 확인 조건: 벤치 구동 스크립트, 정답 라벨, 채점 스크립트를 저장소에 공개해 누구나 같은 숫자를 재현할 수 있게 한다.

## 4. 우선순위

1. **항목 3 충돌 해소.** 설계가 교수 지적과 정면으로 부딪히므로 가장 먼저 고친다. 6.4의 쓰기 재생 규칙을 바꾼다.
2. **항목 5 목표 수치 확정.** 중간 발표 채점 기준이 된다. 팀 회의 안건으로 올린다.
3. **항목 1 판정표 수정.** 한 행만 고치면 된다.
4. **항목 4 요구사항 추가.** [ARCHITECTURE](../arch/2026-09-29%20%EA%B2%8C%EC%9D%B4%ED%8A%B8%EC%9B%A8%EC%9D%B4%20%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98.md)에 새 장으로 넣는다.
5. **항목 2 강제 장치.** 항목 3과 같이 설정 설계로 묶는다.
