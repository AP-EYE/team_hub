API 앞에 한 대 세워두면
발견과 진단과 집계가 한자리에서 끝납니다.

내부망 API 보안 게이트웨이, LLM 판정과 개인정보보호법 기준 집계

사내 API 앞단에 인라인으로 세우는 게이트웨이입니다. 지나가는 트래픽으로 API 목록을 만들고, 인가 취약점을 진단하고, 응답으로 나가는 개인정보를 법 기준으로 집계해 대시보드에 올립니다.

왜 게이트웨이인가

API 보안에서 어려운 일 세 가지가 전부 같은 것을 필요로 합니다.

API 발견어떤 엔드포인트가 살아 있는지 알려면 트래픽을 봐야 합니다
인가 진단실제 요청을 다른 토큰으로 재전송해야 판정이 됩니다
유출 집계응답에 무엇이 실려 나가는지 봐야 셀 수 있습니다

셋 다 트래픽이 지나는 길목이 필요합니다. 게이트웨이가 바로 그 자리입니다.

구조

게이트웨이 안에서 도는 것

1 인벤토리경로 변수를 일반화해 엔드포인트 템플릿을 만듭니다. 문서에 없던 API도 트래픽에 잡히면 목록에 올라옵니다
2 인가 진단수집한 요청을 다른 계정 토큰으로 재전송합니다. 소유자 응답과 타인 응답의 필드 구성을 비교해, 같으면 위반, 민감 필드가 빠진 축소 응답이면 공개 설계로 봅니다. 애매한 건은 검토 필요로 따로 뺍니다
3 개인정보 집계응답 필드를 민감정보, 고유식별정보, 일반 개인정보로 나눕니다. 형태가 있는 값은 정규식으로, 상담 동기처럼 형태가 없는 값은 LLM이 필드명과 맥락으로 판정합니다
4 대시보드엔드포인트별 위험 순위를 보여줍니다. 사고가 나면 같은 데이터로 유출 범위 산정서를 냅니다

LLM이 붙는 자리

전부에 붙이지 않습니다. 기존 방식으로 안 되는 두 곳에만 씁니다.

인가 판정ZAP은 사용자별로 페이지마다 Allowed와 Denied를 사람이 적어야 동작합니다. 그 정답표를 응답 필드 구성의 차이로 대신 만듭니다. 규칙으로 결론이 나는 건은 LLM을 부르지 않고, 검토 필요 등급에만 붙입니다
비정형 필드주민번호나 전화번호는 형태가 있어 정규식으로 잡힙니다. 강남언니에서 나간 상담 동기와 상담 등록 사진은 형태가 없습니다

비용 때문에 LLM은 판정에만 씁니다. 후보를 먼저 정적 규칙으로 거르고 남은 것만 넘깁니다.

법이 요구하는 것

가중치를 저희가 임의로 정하지 않습니다. 신고 의무가 발생하는 요건을 그대로 씁니다.

민감정보나 고유식별정보가 유출되면 건수와 관계없이 72시간 안에 신고해야 합니다.

개인정보 보호법 시행령 제40조제1항제2호. 1천명 이상이라는 건수 요건은 제1호이고, 제2호에는 건수 요건이 없습니다. 제3호는 외부로부터의 불법적인 접근에 의한 유출인데, BOLA 공격이 여기에 해당합니다. 강남언니 사고는 세 호를 모두 충족합니다.

신고서에 가장 먼저 적는 항목이 유출등이 된 개인정보의 항목입니다. 법 제34조제1항제1호입니다. 어떤 필드가 나갔는지를 72시간 안에 특정해야 합니다.

2026년 9월 11일부터 하나가 더 늘었습니다

실제로 샜는지 확인되지 않아도, 불법 접근 정황이 있고 대상을 특정하기 어려우면 유출 가능성을 통지해야 합니다. 법 제34조제2항이 2026년 3월 10일 신설돼 9월 11일 시행됐습니다.

그때 적어야 하는 첫 항목이 유출등의 가능성이 있는 개인정보의 항목입니다. 시행령 제39조의2제2항제1호입니다.

사고가 터진 뒤에는 알아낼 수 없습니다. 그 엔드포인트가 평소에 무엇을 반환하는지를 미리 알고 있어야 쓸 수 있는 내용입니다.

평시에 엔드포인트별 응답 필드 지도를 만들어 두어야 하는 법적 이유가 여기 있습니다. 통지와 신고 기한은 모두 72시간이며 근거는 시행령 제39조, 제39조의3, 제40조입니다. 법률 본문은 지체 없이라고만 정하고 구체적 기한은 시행령에 있습니다.

만드는 것과 만들지 않는 것

게이트웨이라는 말의 범위를 먼저 못 박았습니다. 상용 게이트웨이를 다시 만들면 보안 기여가 남지 않습니다.

만듭니다

  • 인라인 검사 로직. 프록시 엔진은 mitmproxy 리버스 모드를 씁니다
  • 엔드포인트 인벤토리 자동 구성
  • BOLA와 BFLA 진단 엔진
  • 개인정보보호법 기준 분류 사전
  • 위험 순위 대시보드와 신고서 초안

만들지 않습니다

  • HTTP 프록시 엔진. TLS 종단과 스트리밍은 mitmproxy가 처리합니다
  • 라우팅 규칙 엔진. 설정 파일로 대신합니다
  • 로드밸런싱과 고가용성
  • 인증과 토큰 발급. 기존 것을 통과시킵니다
  • 레이트 리밋과 인증서 관리
  • 플러그인 생태계

단계

1단계mitmproxy 리버스 모드 위에 애드온을 올려 엔드포인트 목록이 쌓이는 것까지
2단계인가 진단. crAPI 벤치마크에서 탐지율을 측정합니다
3단계개인정보 집계와 대시보드. 강남언니 유출 항목이 최고 등급으로 분류되는지가 검증 기준입니다

프록시 엔진을 직접 만들지 않기로 하면서 1단계 위험이 크게 줄었습니다. 그래도 막히는 경우를 대비해 2단계와 3단계는 오프라인 트래픽 파일로도 돌아가게 만듭니다.
