# 연구 갭 분석 - 선행연구 대비 신규성 (2026-09-23 기준)

## 0. 우리 설계 한 줄 요약 (대조 기준)

- **입력**: 프록시로 수집한 실제 요청·응답 트래픽. OpenAPI 스펙은 있으면 보조 입력, 없어도 동작이 기본 전제. 테스트 계정 2개.
- **판정**: 소유자 세션 응답 필드 집합 `F_owner`와 타 세션 응답 필드 집합 `F_other`를 정규화된 이름으로 비교. 규칙으로 결론, 애매한 구간만 모델 보조. (`[ARCHITECTURE](../../arch/2026-09-29%20%EA%B2%8C%EC%9D%B4%ED%8A%B8%EC%9B%A8%EC%9D%B4%20%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98.md)` 6장)
- **출력**: 평시 수정 우선순위 리포트 + 사고시 유출 범위 산정서. 엔드포인트별 (인가 취약 x 개인정보 영향도 x 열거 가능성) 랭킹.
- **평가**: crAPI(튜닝) / VAmPI + 자체 API(채점) 분리. 조건 비교(사람 입력량), 오탐 별도 측정, 필드 분류는 Presidio 베이스라인. (`[평가 설계](../../arch/%ED%8F%89%EA%B0%80%20%EC%84%A4%EA%B3%84.md)`)
- **한계**: mitmproxy 기반이라 운영 성능·고가용성 대상 아님. 상태 의존 요청 순서는 반자동. 진단 대상은 동의받은 환경과 공개 취약 앱으로 한정.

세 축으로 나눠 대조한다.
- 축 A: 트래픽만으로 API 엔드포인트와 리소스 관계 복원
- 축 B: 권한표·명세 없이 다중 계정으로 BOLA/BFLA 판정
- 축 C: 노출된 개인정보를 법적 분류로 평가하고 수정 우선순위 산정

## 1. 축 A - 트래픽 기반 엔드포인트/명세 복원

이 축은 우리 1단계(Collector)와 2단계(Normalizer)에 해당한다. 결론부터: 이 축 자체는 선행연구가 성숙해 있고 우리의 신규성이 아니다. 우리는 기성 기법을 쓰고 기여를 축 B, C에 둔다.

### 1.1 선행연구 계보 (선행 → 최신)

| 연구 | 시점 | 입력 | 방식 | 출력 | 평가·지표 | 한계 |
|---|---|---|---|---|---|---|
| APICarv (arXiv 2305.14692, ICSE'23) | 2023 | UI 테스트 실행 | UI 내비게이션 + directed API probing으로 경로변수 추론 | API 테스트 스위트 + OpenAPI | 7개 오픈소스 앱, 엔드포인트 추론 정밀도 98% 재현율 56% | 재현율 낮음. UI 구동이 전제 |
| OOPS (arXiv 2601.12735, 2026-01) | 2026 | 서버 소스코드 | LLM 기반 정적분석 에이전트 워크플로 | OpenAPI | 메서드 F1 98%, 파라미터/응답 97%, 제약 92% | 소스코드 필요. 트래픽만으로는 불가 |
| MRG (arXiv 2604.19471, 2026-04) | 2026 | API 트래픽 | 트리 분해 + 그래프 모델링, `{id}`/`{param}` placeholder 일반화, 비지도 | OpenAPI + 이상탐지 | ATRDF/ATRDF2 정밀도 1.0 높은 재현율, FT-ANN 대비 20배 빠름 | 비정형 환경 재현율 하락. payload 검사 약함 |

관련 도구로 har-to-openapi(트래픽/HAR에서 스펙 생성), Redocly/Levo 상용 파이프라인이 있다. 트래픽에서 스펙을 뽑는 것은 이미 제품화된 영역이다.

### 1.2 우리 설계와의 관계

- 우리의 경로변수 일반화(`/orders/1234` → `/orders/{id}`)와 CIM 필드 정규화는 MRG, OOPS가 이미 하는 것과 같은 종류다. **여기서 새 주장을 하지 않는다.**
- **경계선 하나**: OOPS는 소스코드, APICarv는 UI 구동이 필요하다. MRG는 트래픽 기반이지만 이상탐지가 목적이지 인가 오라클을 세우지 않는다. 우리는 트래픽 기반 복원을 **인가 판정의 전처리**로 쓴다는 점만 다르고, 복원 기법 자체는 기성이다.
- **함의**: 제안서에서 1·2단계를 기여로 내세우면 안 된다. "복원은 기존 기법, 기여는 복원된 인벤토리 위에서의 판정과 영향도"로 명확히 선을 그어야 심사에서 방어된다.

## 2. 축 B - 다중 계정 BOLA/BFLA 판정 (핵심 경쟁 영역)

우리 3단계(Authz Detector)에 해당한다. 우리의 1차 기여(오라클 자동 생성)가 여기서 검증된다.

### 2.1 선행연구 계보 (선행 → 최신)

| 연구 | 시점 | 필요 입력 | 판정 방식(오라클) | 출력 | 평가·지표 | 한계 |
|---|---|---|---|---|---|---|
| AuthScope (CCS'17) | 2017 | 모바일 앱 자동 구동, 2계정 | differential traffic analysis. 프로토콜 필드 치환 후 서버 응답 관찰 | 취약 인가 목록 | Google Play 앱 4,838개, 0-day 597건(306앱) | 응답 신원 비교 수준. 공개설계 구분 없음. 필드 분류 없음 |
| RESTler 보안 검사기 (Atlidakis, Godefroid, Polishchuk, ICST'20, https://patricegodefroid.github.io/public_psfiles/icst2020.pdf) | 2020 | Swagger 스펙 + 인증 토큰 2개. 상태 추적 퍼저 RESTler 확장 | 규칙 4개(use-after-free, resource-leak, resource-hierarchy, user-namespace). user-namespace는 마지막 성공 요청을 다른 토큰으로 재실행해 **성공하면 위반** | 규칙 위반 버그 | 운영 Azure 2개, O365 1개(요청 13~19종), 1시간 퍼징, 버그 수(bug bucket) 보고, 전부 수정됨 | 스펙 필수. 오탐률·정답셋 없음. 운영 서비스에 쓰기·삭제 재전송. 공개 리소스가 없는 클라우드 관리 API 전제 |

참고로 실증 축에 BOLA 실태 분류 연구(arXiv 2605.25865, 2026-05)가 있다. HackerOne IDOR/IAC 태그 200건 중 84건(78.5%)만 실제 in-scope BOLA로 확인. IDOR 태그 자체에 라벨 노이즈가 크다는 발견은 우리가 자체 API/벤치의 정답 라벨을 조문 기반으로 정하는(`[법적 근거](../plan/%EB%B2%95%EC%A0%81%20%EA%B7%BC%EA%B1%B0.md)`) 설계의 정당성을 뒷받침한다.

### 2.2 이 축에서 우리가 새로 검증하는 것

선행연구를 두 그룹으로 가른다.

- **소스/계측 기반** (MACE, BolaRay, BolaZ, BACFuzz): 정확도는 높으나 소스코드나 런타임 계측이 필요하다. 실사고 대상(강남언니·화해)은 소스를 안 준다. 우리는 블랙박스라 같은 조건에서 못 돈다는 제약을 애초에 안 갖는다.
- **블랙박스/트래픽 기반** (AuthScope, BACScan, BacAlarm, AuthProbe): 여기가 우리 경쟁 영역이다.
  - AuthScope: 응답 신원 비교까지. 공개설계 API 오탐 구조. 필드 분류 없음.
  - BACScan: 웹 페이지 기반 IDDG. API 응답 스키마 델타가 아니라 페이지 간 데이터 의존. 우리와 판정 단위가 다르다.
  - BacAlarm: 학습 기반 런타임 탐지. 진단(평시 우선순위)이 아니라 방어. 라벨 트래픽 부재가 근본 한계.
  - **AuthProbe: 가장 가깝다. 4절에서 별도로 판다.**

**우리 축 B의 신규 주장(방어 가능한 것만)**: 스펙 없는 트래픽 조건에서, 응답 필드 델타로 공개설계 API와 BOLA를 구분하는 오라클. 선행 블랙박스 도구 중 이 구분을 판정 규칙에 내장한 것이 없다.

## 3. 축 C - 개인정보 노출 영향도 정량화 (우리의 가장 강한 기여)

우리 4단계(Privacy Scorer)에 해당한다. **이 축에 인가 탐지와 법적 영향도 산정을 결합한 선행연구가 없다.** 여기가 학술 신규성의 핵심이다.

### 3.1 선행연구 계보

| 연구 | 시점 | 입력 | 방식 | 출력 | 한계(우리 관점) |
|---|---|---|---|---|---|
| ReCon (MobiSys'16, arXiv 1507.00255) | 2016 | 모바일 네트워크 트래픽 | ML로 PII 누출 탐지, 크라우드소싱 강화 | PII 누출 플래그 + 차단/치환 | 누출 여부만. 법적 등급·영향도 정량화 없음 |
| ENISA breach severity methodology | 2013(v1.0) | 유출 데이터 유형 | DPC(처리맥락) x EI(식별용이성) + CB(정황). 등급 negligible~maximum | 심각도 점수 | 수작업 평가 프레임. 자동화·API 연계 없음. EU 기준 |

| Detection of Personal Data in Structured Datasets (arXiv 2506.22305, 2025-06) | 2025 | 스프레드시트/DB 컬럼 | GPT-4o에 컬럼명 + 상위 10개 값 + 테이블 제목·형제 컬럼명 제공, 맥락 분류 | personal/non-personal | 정적 데이터셋. 인가/트래픽과 무관. GDPR |

| Akto pii-types (제품) | - | API 트래픽 | 정규식 + 태그(PII/FINANCE/HEALTHCARE) + 3등급 | 민감정보 태그 | 한국 유형 정의 자체 부재(`[선행 솔루션 조사](../plan/%EC%84%A0%ED%96%89%20%EC%86%94%EB%A3%A8%EC%85%98%20%EC%A1%B0%EC%82%AC.md)`). 정규식이라 값 패턴 없는 필드 못 잡음 |

### 3.2 우리 축 C의 신규 주장

- **법적 분류의 한국화**: ENISA·GDPR·Akto 모두 EU/국제 기준이다. 개인정보보호법 제23조 민감정보와 제24조 고유식별정보 구분, 한국 유형(주민등록번호 등)을 판정에 넣은 자동 도구가 없다. (`[법적 근거](../plan/%EB%B2%95%EC%A0%81%20%EA%B7%BC%EA%B1%B0.md)`)
- **맥락 기반 필드 분류를 인가 결과에 결합**: 2506.22305와 2512.04120은 "컬럼명+값+형제 컬럼"으로 맥락 분류를 이미 한다. 이 기법 자체는 새롭지 않다. **새로운 것은 이 분류를 BOLA로 실제 유출되는 응답 필드에 적용해 (취약 x 영향도 x 열거가능성) 우선순위로 산출하는 결합이다.** 강남언니의 "상담 동기"처럼 값 패턴 없는 필드를 맥락으로 최고 등급 분류하는 것이 1차 검증 기준.
- **평시/사고시 이중 출력**: 개인정보보호법 시행령 72시간 신고의 "유출 항목 특정"과 법 제34조제2항(2026-09-11 신설) "유출 가능성 항목"을 자동 산출. 이 법-도구 매핑을 한 선행연구가 없다.

**주의**: 3.1의 두 LLM 컬럼 분류 논문(2025~2026)이 우리 필드 분류기의 직접 베이스라인이다. `[평가 설계](../../arch/%ED%8F%89%EA%B0%80%20%EC%84%A4%EA%B3%84.md)`의 Presidio 베이스라인에 이 둘을 추가해야 한다. "맥락 분류를 우리가 처음 한다"는 주장은 성립하지 않으므로, 기여를 "결합"과 "한국법 가중"으로 좁혀야 방어된다.

### 3.3 국내 선행연구 (2026-09-23 조재현 멘토 DBpia 공유 계기로 조사)

한국 개인정보 노출 위험도 정량화는 국내 학계에 선행연구가 있다. "한국법 가중을 처음 한다"가 아니라 "인가 탐지와 결합해 API 응답 필드에 적용한 것이 처음"으로 주장을 좁혀야 한다.

| 연구 | 시점 | 방식 | 우리 관점 차이 |
|---|---|---|---|
| 개인 정보 노출에 대한 정량적 위험도 분석 방안 (KISTI JAKO201514751644730) | 2015 | 정보노출량을 엔트로피(속성 분포), 자체 식별력, 프라이버시 민감도의 절대적 위험도 + 공격유형별 상대적 위험도로 산출. 페이스북 2만명 공개정보 분석 | 정적 공개정보 대상. 인가·트래픽 무관. **엔트로피 기반 열거·식별 위험도는 우리 "열거 가능성 가중"에 직접 참고 가능** |
| 웹사이트 구조를 고려한 개인정보 노출 위험도 계산 기법 (DBpia NODE06637270, 한국전자거래학회지) | - | 개인정보 민감도 x 웹페이지 예상 방문 확률로 위험도 수치화 | 웹페이지 단위. API 엔드포인트·응답 스키마 아님. 노출 확률 가중 착상은 유사 |
| 빅데이터 개인정보 위험 분석 기술 (KISTI JAKO201321353692848) | 2013 | 빅데이터 상 개인정보 위험도 파악·경고 | 공개정보 수집 관점. 사고 영향도 산정 아님 |
| 다모델·이중 기준 최빈 통합 민감정보 유추 위험 평가 프레임워크 (김효주·박나현·오준형, 정보보호학회논문지 35(6):1505-1519, 2025, DOI 10.13089/JKIISC.2025.35.6.1505) | 2025 | 비식별 속성 조합의 민감정보 유추 위험을 10종 ML 분류기 정확도·F1로 정량화. 행동·수면 10특성 1,023조합, 66.4%가 무작위 초과, 고위험 24.3% | **유추(inference) 위험. 우리는 직접 노출(direct exposure) 위험.** 비식별 조합의 재식별이 초점이라 문제축이 다름. 최신 국내 연구로 related work에 인용 가치 |

공식 기준 문서: **개인정보 위험도 분석 기준 및 해설서** (privacy.go.kr, 개인정보위). ENISA에 대응하는 국내 공식 프레임. 우리 법적 가중치 근거로 `[법적 근거](../plan/%EB%B2%95%EC%A0%81%20%EA%B7%BC%EA%B1%B0.md)`에 이 해설서를 추가 확인해야 한다.

**국내 조사 결론**: 위험도 정량화(엔트로피·식별력·민감도) 자체는 국내에 2013~2015년부터 있다. 최신(2025)은 유추 위험 쪽. 우리 델타는 (a) 유추가 아닌 직접 노출, (b) 정적 데이터가 아닌 BOLA로 실제 유출되는 응답 필드, (c) 개인정보보호법 제23·24조 조문 매핑 + 72시간 신고 항목 자동 산출. 국내 선행연구를 related work로 인용하되 세 델타로 차별화한다.

## 4. AuthProbe 정밀 대조 (가장 가까운 연구, 조건별 차이 검증)

AuthProbe(arXiv 2607.20574, 2026-07-22)는 우리와 문제의식·방식이 가장 겹친다. "다르다"로 넘기지 않고 어떤 조건에서 실제 차이가 나는지 항목별로 본다.

### 4.1 공통점 (진짜 겹치는 부분)

- 블랙박스, 다중 신원(우리 2계정 = AuthProbe alice/bob).
- 소유권을 서버 응답으로 확보해 정답표 없이 판정(우리 1차 기여와 동일한 착상).
- CI 게이트/기계판독 리포트 지향(우리 4단계 JSON 출력과 유사).
- 열거 가능성 탐지(우리 순차 ID 가중 = AuthProbe enumeration walk).

이 겹침은 크다. 제안서에서 AuthProbe를 정면으로 인용하고 차이를 명시해야 한다. 숨기면 심사에서 치명타.

### 4.2 조건별 실제 차이

| 항목 | AuthProbe | 우리 | 차이가 나는 조건 |
|---|---|---|---|
| 필요 입력 | **OpenAPI 스펙 필수**(auto-fetch 또는 파일). 스펙에서 collection/item 경로쌍 탐지 | 트래픽 기본, 스펙은 선택 보조 | 대상이 스펙을 안 주는 실사고 API. crAPI는 스펙 있어 이 조건에서 둘 다 동작 |
| 판정 오라클 | `id(r)=id(o)` 신원 일치. 응답 body의 id 필드가 피해자 것과 같으면 leak | `F_owner`/`F_other` 필드집합 델타 | **공개설계 API(SNS 프로필·공개 게시글). AuthProbe는 타인 객체가 성공 반환되면 leak으로 볼 위험** |
| 공개설계 구분 | 논문에 명시적 구분 규칙 없음. 논문 스스로 "서비스가 [축소된 뷰를] 반환하면 leak을 놓칠 수 있다"고 한계 인정 | `F_other ⊂ F_owner ∧ F_other ∩ S = ∅` → 정상, `∩ S ≠ ∅` → 검토필요 | 서버가 호출자별로 응답 필드를 줄여주는 API. 여기서 판정이 갈린다 |
| 커버 범위 | 읽기 GET 위주. 쓰기(PUT/DELETE)와 BFLA는 future work | GET + 쓰기 재조회 확인 + BFLA 동일 틀 | 쓰기 메서드 취약점, 관리자 엔드포인트 |
| 개인정보 분류 | 없음. 심각도는 취약점 종류 기준(missing auth=critical 등) | 법적 분류 가중으로 영향도 산정 | 유출 필드의 민감도로 우선순위를 매겨야 하는 상황 |
| 평가 | 합성 recruitment API 2종(취약/하드닝), 실데이터 없음, 오탐 0(하드닝) | crAPI/VAmPI/자체 API, 조건 비교 + 오탐 별도 | AuthProbe는 correctness 시연, prevalence는 future work로 명시 |

### 4.3 결론: AuthProbe 대비 우리의 순수 델타

AuthProbe를 뺀 뒤 우리에게 남는 독립 기여는 셋이다.

1. **필드 델타 오라클**: 신원 일치가 아니라 응답 필드 구성으로 판정. 공개설계 API 오탐을 구조적으로 억제. AuthProbe가 인정한 한계("축소 뷰 반환 시 놓침")를 정확히 겨냥한다. **이것이 가장 명확한 학술 델타.**
2. **개인정보 영향도 결합**: AuthProbe에 아예 없는 축. 취약점 유무를 넘어 "무엇이 얼마나 새는가"를 한국법으로 정량화.
3. **스펙 비의존**: AuthProbe는 스펙이 없으면 시작을 못 한다. 우리는 트래픽만으로 동작. 단 crAPI 벤치는 스펙이 있어 이 차이를 실증하려면 "스펙 미사용 조건"을 평가에 명시해야 한다.

BFLA·쓰기 커버는 AuthProbe의 future work와 겹치므로 "먼저 한다"는 약한 주장이다. 신규성 주장은 1·2에 집중한다.

### 4.4 판정 오라클의 계보와 결론 (2026-09-28 ICST'20 추가)

블랙박스 다중 토큰 BOLA 판정은 오라클이 세 단계로 정밀해졌다.

| 단계 | 연구 | 오라클 | 성립 조건 |
|---|---|---|---|
| 1 | RESTler 검사기 (ICST'20) | 다른 토큰으로 요청이 성공하면 위반 | 모든 리소스가 사용자 소유인 도메인. 클라우드 관리 API |
| 2 | AuthProbe (2026-07) | 성공 응답의 id가 피해자 객체 id와 같으면 위반 | 응답에 객체 id가 실리는 API. 공개 설계 리소스는 여전히 오탐 |
| 3 | 우리 | 소유자 응답과 타인 응답의 필드 구성 차이로 판정 | 공개 조회 API가 섞인 소비자 서비스 |

**결론.**
선행 오라클이 단순했던 것은 기법이 부족해서가 아니라 대상 도메인에 공개 리소스가 없었기 때문이다.
ICST'20은 Azure와 Office365를 대상으로 했고, 그 도메인에서는 "다른 사용자가 접근에 성공했다"가 곧 위반이다.
SNS, 쇼핑몰, 의료 상담처럼 타인 데이터를 정상적으로 보여주는 소비자 서비스에서는 이 등식이 깨진다.
우리 필드 델타 오라클은 이 도메인 이동이 요구하는 판정 기준이다.
이 논리가 9/23 조재현 교수 피드백 1번(공개 조회 API와 인가 실패 구분)에 대한 답이다.

**ICST'20에서 가져올 것.**
- resource-hierarchy 규칙: 부모 ID를 바꿔 끼우는 BOLA 변형(`/users/{A}/orders/{B의 주문}`)을 우리 탐지기는 명시적으로 생성하지 않는다. 경로 파라미터가 2개 이상인 엔드포인트의 후보 생성 규칙으로 추가할 수 있다.
- use-after-free 규칙: 삭제 요청이 필요하므로 [ARCHITECTURE](../../arch/2026-09-29%20%EA%B2%8C%EC%9D%B4%ED%8A%B8%EC%9B%A8%EC%9D%B4%20%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98.md) 6.4 쓰기 허용 규칙 안에서만 수행한다.

**ICST'20과 반대로 가는 것.**
- 운영 서비스에 쓰기·삭제를 재전송하지 않는다. ICST'20은 Microsoft가 자사 서비스를 시험해 허가 문제가 없었다. 우리는 쓰기를 기본 차단한다(9/23 피드백 3번).
- 버그 수만 보고하는 평가를 따르지 않는다. 정답셋, 오탐률, 목표 수치를 둔다(9/23 피드백 5번).

**확인 필요.** RESTler(microsoft/restler-fuzzer) 오픈소스에 이 검사기가 포함돼 있고 토큰 2개 설정이 되는지 확인하지 않았다. 되면 crAPI(스펙 있음)에서 1단계 오라클 비교군으로 돌릴 수 있다.

## 5. 종합: 무엇이 없고 무엇을 새로 검증하는가

### 5.1 기존 연구에 없는 것

- 스펙 없는 블랙박스에서 **공개설계 API를 필드 델타로 구분하는 BOLA 오라클** (AuthProbe·AuthScope는 신원 비교, 공개설계 미구분).
- **인가 탐지 + 개인정보 법적 영향도 정량화의 결합** (축 B와 축 C를 한 파이프라인에 붙인 선행연구 부재).
- **한국 개인정보보호법(제23·24조) 기반 가중과 72시간 신고·유출가능성 항목 자동 산출** (ENISA/GDPR/Akto는 국제 기준, 한국 유형·조문 매핑 없음).

### 5.2 우리가 새로 검증할 가설 (채점 가능 형태)

1. 필드 델타 오라클이 신원 일치 오라클(AuthProbe식)보다 공개설계 API에서 오탐이 낮다. → 검증: 공개조회 엔드포인트를 포함한 자체 API에서 두 오라클의 오탐 수 비교. 판정: 필드 델타 오탐 < 신원 일치 오탐.
2. 계정 2개만으로(정답표 0) ZAP Access Rules 완비 조건에 근접한다. → 검증: `[평가 설계](../../arch/%ED%8F%89%EA%B0%80%20%EC%84%A4%EA%B3%84.md)` 조건 A/B/C 비교. 판정: C가 B보다 낫고 A에 근접.
3. 맥락 기반 필드 분류 + 한국법 가중이 Presidio 및 LLM 컬럼분류 베이스라인(2506.22305, 2512.04120)보다 값 패턴 없는 민감필드에서 재현율이 높다. → 검증: 강남언니 구조 모사 필드로 재현율 비교.
4. 영향도 점수 순위가 개인정보보호위 실제 과징금 처분 사례 순위와 상관한다. → 검증: 처분 사례 수집 후 순위 상관 측정.

### 5.3 제안서·논문에 반영할 것

- 1·2단계(복원)는 기여 아님을 명시. 기여는 3(오라클)·4(영향도)단계.
- AuthProbe를 related work에 정면 인용하고 4.2 표로 차이 제시.
- 필드 분류 베이스라인에 2506.22305, 2512.04120 추가 (`[평가 설계](../../arch/%ED%8F%89%EA%B0%80%20%EC%84%A4%EA%B3%84.md)` 수정 필요).
- 신규성 문장은 "결합 + 한국법 가중 + 필드 델타 오라클" 셋으로 좁게. 넓히면 개별 축마다 선행연구에 밀린다.
