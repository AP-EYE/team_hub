# 개인정보 분류 오류의 순위 영향

"오탐률이 높으면 분류 결과가 나빠진다"는 가정을, 분류 오류가 수정 우선순위를 실제로 얼마나 바꾸는지로 검증하는 주제다.

**위치**: [한국어 API 응답 최소 문맥 분류 가설](%ED%95%9C%EA%B5%AD%EC%96%B4%20API%20%EC%9D%91%EB%8B%B5%20%EC%B5%9C%EC%86%8C%20%EB%AC%B8%EB%A7%A5%20%EB%B6%84%EB%A5%98%20%EA%B0%80%EC%84%A4.md)의 **1단계(신뢰성 기준선)** 상세 문서다. 이 블록의 결과물인 수정 우선순위를 "분류기가 틀려도 믿을 수 있나"로 검증하고, 2단계(원인 진단)와 3단계(해결책 선택)가 넘어야 할 목표 숫자를 정한다.

## 주제 한 줄 정의

> **개인정보 분류 라벨에 오탐과 미탐을 비율별로 넣어 엔드포인트 수정 우선순위가 얼마나 바뀌는지 측정하고, 순위가 안정되는 분류 정확도의 기준선을 구한다.**

## 한 사이클 예시

위반이 확인된 엔드포인트 4개. 가중치는 비식별 0, 일반 1, 고유식별 5, 민감 10(가정).

| 엔드포인트 | 노출 필드 (정답 등급) | 점수 |
|---|---|---|
| B 상담 조회 | 상담동기(민감), 이름(일반), 상담일(비식별) | 11 |
| D 프로필 조회 | 주민번호(고유식별), 이름(일반), 가입일(비식별) | 6 |
| A 차량 위치 | 이름, 이메일, 위치 (모두 일반) | 3 |
| C 게시글 조회 | 제목, 본문(비식별), 작성자 이메일(일반) | 1 |

정답 수정 순위는 **B → D → A → C**다.

- **오탐 1개**: C의 "본문"을 민감으로 잘못 분류 → C가 11점 → B와 공동 1위
- **미탐 1개**: B의 "상담동기"를 비식별로 잘못 분류 → B가 1점 → 꼴찌

필드 12개 중 1개만 틀려도 가장 먼저 고칠 대상이 바뀐다.

이 과정을 오류 비율(5%, 10%, 20%)별로 수백 번 반복해 **1순위가 유지되는 비율**을 잰다. "1순위 90% 유지"에 필요한 오탐률이 **기준선**이다. 실제 분류기의 오탐률이 기준선보다 높으면 더 나은 모델이 필요하고, 낮으면 지금 방법으로 충분하다.

## 용어 정리

**개인정보 집계 (Privacy Scorer)**
확인된 위반 응답의 필드를 개인정보 등급으로 분류하고 엔드포인트 점수를 내는 4단계

**필드 등급**
비식별, 일반 개인정보, 고유식별정보, 민감정보 네 단계. 개인정보보호법 분류를 따른다

**가중치**
등급별 점수. 민감정보가 가장 높다. 실제 값은 처분 사례 수집 후 정한다

**엔드포인트 점수**
그 엔드포인트가 노출한 필드들의 가중치 합

**수정 우선순위**
엔드포인트 점수가 높은 순서. "무엇부터 고칠지"다

**오탐**
개인정보가 아닌 필드를 개인정보로 분류한 것

**미탐**
개인정보인 필드를 비식별로 분류한 것

**오류 주입**
정답 라벨을 일부러 틀리게 바꿔 오류가 있는 분류기를 흉내 내는 방법. 실제 분류기 없이 영향을 잴 수 있다

**켄달 타우**
두 순위가 얼마나 같은지 나타내는 값. 1이면 같고 0이면 관계가 없다

**상위 5 유지율**
정답 상위 5개 엔드포인트 중 오류가 섞인 순위에서도 상위 5개에 든 비율

**1순위 유지율**
가장 먼저 고칠 엔드포인트가 그대로인 비율

## 근거 1. 선행연구는 분류 정확도에서 멈춘다

- **Cory·Küpper는 분류 성능 지표만 보고한다**
  > "Unless stated otherwise, we report precision, recall, and F1, computed from true positives (TP), false positives (FP), and false negatives (FN) under the respective matching criterion."
  >
  > → 따로 밝히지 않는 한, 각 일치 기준에서 참양성·거짓양성·거짓음성으로 계산한 **정밀도, 재현율, F1을 보고한다**.
  >
  > (Cory, Küpper, HTTP 메시지 개인정보 탐지, arXiv 2605.06305, 2026, 6.1절)

- **향후 과제에도 다음 단계 영향은 없다**
  > "Future work should therefore validate the approach on real-world traffic captures, including obfuscated or transformed values; extend evaluation beyond request bodies to headers, paths, queries, cookies, and responses; and improve reliability and cost-efficiency through selective or heterogeneous review."
  >
  > → 따라서 향후 연구는 난독화·변형된 값을 포함한 실제 트래픽으로 검증하고, **평가를 요청 본문에서 헤더·경로·쿼리·쿠키·응답으로 넓히며**, 선택적·이질적 검토로 신뢰성과 비용 효율을 높여야 한다.
  >
  > (arXiv 2605.06305, 7절)
  - 향후 과제가 탐지 범위 확장과 검토 효율에 머문다. 분류 결과가 위험 점수나 수정 순위에 미치는 영향은 언급하지 않는다.

- **Telkamp·Hulsebos는 스스로 "탐지 단계"로 범위를 좁혔다**
  > "Protecting sensitive data generally follows a three-step procedure: ① specifying sensitive data, ② detecting sensitive data, ③ remedying data sensitivity. In this work, we focus on the second step, which has received little attention in research."
  >
  > → 민감 데이터 보호는 보통 3단계를 따른다. ① 민감 데이터 정의, ② 민감 데이터 탐지, ③ 민감성 조치. **이 연구는 연구가 적었던 두 번째 단계(탐지)에 집중한다.**
  >
  > (Telkamp, Hulsebos, *Towards Contextual Sensitive Data Detection*, arXiv 2512.04120, 3절)

- **평가 지표도 분류 정확도와 실행 시간이다**
  > "Precision, recall, and F1 are used as evaluation metrics. Besides accuracy metrics, we report the average runtime per column to assess deployment considerations."
  >
  > → 정밀도, 재현율, F1을 평가 지표로 쓴다. **정확도 지표 외에는** 배포를 고려해 열당 평균 실행 시간을 보고한다.
  >
  > (arXiv 2512.04120, 4절)

두 연구 모두 분류 성능을 재는 데서 끝난다. 분류 오류가 다음 단계(조치 우선순위)에 미치는 영향은 평가하지 않았다. 2512.04120은 조치 단계(③)를 명시적으로 범위 밖에 두었다. 우리 질문이 그 ③과 ②의 연결 지점이다.

## 근거 2. 점수 입력이 흔들리면 우선순위가 흔들린다는 문제는 실재한다

- **같은 취약점을 여러 사람이 채점하면 등급이 다르게 나온다**
  > "In a follow-up survey with 59 participants, we found that for the same vulnerabilities from the main study, 68% of these users gave different severity ratings."
  >
  > → 59명 대상 후속 조사에서, 본 연구와 같은 취약점에 대해 **사용자의 68%가 다른 심각도 등급을 매겼다**.
  >
  > (Wunder, Kurtz, Eichenmüller, Gassmann, Benenson, *Shedding Light on CVSS Scoring Inconsistencies*, IEEE S&P 2024, arXiv 2308.15259, 초록)

- **점수만으로 우선순위를 정하면 자원을 잘못 배분할 수 있다**
  > "Using only the Base Score for vulnerability prioritization could lead to misallocated resources to mitigate supposedly high-severity vulnerabilities."
  >
  > → 취약점 우선순위를 기본 점수만으로 정하면, **심각하다고 여겨진 취약점을 막는 데 자원을 잘못 배분할 수 있다**.
  >
  > (arXiv 2308.15259, 6절)
  - 이 연구는 **사람 채점자의 불일치**를 쟀다. 우리 질문은 **자동 분류기의 오류**가 순위를 얼마나 바꾸는지다. 입력 오류가 우선순위로 번진다는 문제의식은 같고, 오류의 원천과 측정 대상이 다르다.

## 근거 3. 방법 시연 (우리 조사, 합성 데이터)

### 왜 했나

오류 주입 방법이 실제로 순위 변화를 잴 수 있는지, 어떤 지표가 차이를 잘 보여주는지 먼저 확인하려고 했다. **실제 API 데이터가 아니므로 결과를 성능 근거로 쓰지 않는다.**

### 무엇을 했나

- 엔드포인트 30개를 만들고, 각각 필드 3~15개를 넣었다.
- 필드 등급은 비식별 50%, 일반 35%, 고유식별 8%, 민감 7% 비율로 무작위 배정했다. 이 비율은 가정이다.
- 가중치는 비식별 0, 일반 1, 고유식별 5, 민감 10으로 가정했다. 실제 가중치는 아직 정하지 않았다([ARCHITECTURE](../../arch/2026-09-29%20%EA%B2%8C%EC%9D%B4%ED%8A%B8%EC%9B%A8%EC%9D%B4%20%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98.md) 10장 미결).
- 엔드포인트 점수는 필드 가중치의 합이고, 점수 순서가 수정 우선순위다.

### 어떻게 셌나

1. 정답 라벨로 우선순위를 만든다.
2. 라벨의 일부를 일부러 틀리게 바꾼다. 비율은 5%, 10%, 20%, 30%. 방식은 세 가지다.
   - 오탐만: 비식별 필드를 개인정보로 바꾼다
   - 미탐만: 개인정보 필드를 비식별로 바꾼다
   - 섞음: 아무 필드나 다른 등급으로 바꾼다
3. 틀린 라벨로 다시 우선순위를 만들고, 정답 순위와 비교한다.
4. 이 과정을 300번 반복해 평균을 낸다. 무작위 추출 순서를 고정(시드 20260929)해서 누가 돌려도 같은 숫자가 나온다.

### 결과 (가정 가중치 기준)

| 오류 | 비율 | 켄달 타우 | 상위 5 유지 | 1순위 유지 |
|---|---|---|---|---|
| 오탐만 | 5% | 0.901 | 84.6% | 76.3% |
| 오탐만 | 10% | 0.825 | 76.3% | 64.3% |
| 오탐만 | 20% | 0.721 | 66.7% | 53.0% |
| 미탐만 | 5% | 0.953 | 91.0% | 83.7% |
| 미탐만 | 10% | 0.904 | 83.3% | 76.3% |
| 미탐만 | 20% | 0.817 | 74.3% | 58.0% |
| 섞음 | 5% | 0.824 | 76.5% | 61.3% |
| 섞음 | 10% | 0.719 | 67.8% | 44.7% |
| 섞음 | 20% | 0.591 | 55.7% | 36.0% |

이 가정에서는 오탐 5%만으로도 가장 먼저 고칠 엔드포인트가 4번 중 1번꼴로 바뀐다. 같은 비율이면 **오탐이 미탐보다 순위를 더 흔든다.** 비식별 필드가 절반이라 오탐이 생길 자리가 많고, 오탐이 민감정보(가중치 10)로 잘못 올라가면 점수가 크게 뛰기 때문으로 보인다.

> [!note]- 코드 (scorer_noise_pilot.py)
> ```python
> def corrupt(endpoints, rate, mode, rng):
>     out = []
>     for fields in endpoints:
>         new = []
>         for c in fields:
>             if rng.random() >= rate:
>                 new.append(c)
>                 continue
>             if mode == "FP":
>                 new.append(rng.choice(CLASSES[1:]) if c == "비식별" else c)
>             elif mode == "FN":
>                 new.append("비식별" if c != "비식별" else c)
>             else:
>                 new.append(rng.choice([x for x in CLASSES if x != c]))
>         out.append(new)
>     return out
> ```

### 이 시연이 말해 주는 것과 말하지 않는 것

- 말해 주는 것: 오류 주입으로 순위 변화를 잴 수 있고, 켄달 타우·상위 5·1순위 세 지표가 서로 다른 모습을 보여 준다. 오탐과 미탐을 따로 재야 한다.
- 말하지 않는 것: 실제 한국어 API에서 몇 % 오류까지 괜찮은지. 결과는 가중치와 등급 비율 가정에 크게 좌우된다. 가중치를 바꾸면 결론이 뒤집힐 수 있다.

## 검증할 질문 (실제 실험)

1. **RQ1**: 실제 분류기(정규식, KLUE-BERT, SemIf 등)가 내는 오류 수준에서 상위 k 수정 대상이 얼마나 바뀌는가?
2. **RQ2**: 순위가 안정되려면(예: 상위 5 유지 90% 이상) 오탐률과 미탐률이 각각 몇 % 이하여야 하는가?
3. **RQ3**: 가중치 설정을 바꿔도 RQ2의 기준선이 유지되는가? (가중치 민감도)
4. **RQ4**: 보류(판정 불충분)를 점수에서 어떻게 다루면 순위가 덜 흔들리는가? 0점 처리, 최고 위험 처리, 점수 구간(하한·상한) 표시를 비교한다.

RQ2의 기준선이 나오면 분류기 선택 기준이 생긴다. 예를 들어 "정규식이 그 기준을 넘으면 비싼 모델은 필요 없다"거나 "넘지 못하면 한국어 모델 미세조정이 필요하다"는 판단을 숫자로 할 수 있다.

## 아직 약한 점

- 가중치가 정해지지 않았다. RQ3로 여러 가중치를 돌려 결론이 유지되는지 봐야 한다.
- 실제 엔드포인트별 필드 구성(몇 개 필드, 등급 비율)을 모른다. crAPI·VAmPI·자체 API에서 먼저 센다.
- 오류가 실제 분류기에서는 무작위가 아니다. 특정 필드(자유서술)에 몰린다. 무작위 주입과 실제 분류기 오류를 둘 다 재서 비교한다.
- 분류 오류가 순위에 미치는 영향을 분석한 연구가 다른 분야(추천, 신용평가 등)에 있을 수 있다. 이번 검색에서는 찾지 못했다.
