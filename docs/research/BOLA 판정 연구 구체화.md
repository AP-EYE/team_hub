# BOLA 판정 연구 구체화

> 2026-10-02 최종 브리핑은 [2026-10-02 목록 조회 판정 브리핑 최종안](2026-10-02%20%EB%AA%A9%EB%A1%9D%20%EC%A1%B0%ED%9A%8C%20%ED%8C%90%EC%A0%95%20%EB%B8%8C%EB%A6%AC%ED%95%91%20%EC%B5%9C%EC%A2%85%EC%95%88.md)과 [2026-10-02 교수 브리핑 10분 대본](../../discussion/2026-10-02%20%EA%B5%90%EC%88%98%20%EB%B8%8C%EB%A6%AC%ED%95%91%2010%EB%B6%84%20%EB%8C%80%EB%B3%B8.md)을 우선합니다. AuthzTrace의 가짜 API 결과는 팀원 제공 보고이며, 실제 Memos 재현과 개선안 성능은 검증 전입니다.

## 출발 가설과 주제 정의

출발 질문은 “타인 객체 조회 성공이 정상 공개·공유인지 BOLA인지 어떻게 구분할 것인가”다.

> 목록 조회의 성공과 객체별 읽기 허용을 구분하면 정상적인 200 응답의 오탐을 줄이면서 실제 비공개 객체 누출을 계속 탐지할 수 있는지 검증한다. 테스트 객체의 권한 근거와 반환된 보호 내용을 대조하며, 근거가 부족하면 보류한다.

“권한표 없이”는 전체 운영 객체의 권한표를 작성하지 않는다는 뜻이다.
객체 생성자, 공개 범위, 공유 대상, 계정 역할이라는 권한 입력은 필요하다.
작은 권한표를 테스트 객체 설정으로 옮긴 것에 그친다면 연구 기여는 약하다.
따라서 입력 비용과 동일한 테스트 범위의 탐지 성능을 함께 비교해야 한다.

**판정 단위**
앱 버전, 요청 메서드·경로, 요청 계정, 대상 객체, 관측 시점의 조합이다.

**독립 근거**
진단 요청의 성공 여부와 별개로 기록한 객체 생성 설정, 공유 설정과 정책 의미다.
취약할 수 있는 API의 목록에 객체가 없다는 사실만으로 접근 금지를 확정하지 않는다.

**보류**
허용 여부나 반환 객체를 확인할 근거가 부족해서 판정하지 못한 상태다.
네트워크 오류·세션 만료·대상 객체 삭제 같은 실행 실패는 별도 기록한다.

## 선행연구 원문에서 확인한 것

확인일은 2026-10-02다.

### 1. BACScan은 이미 공개 페이지를 걸러낸다

> “treating pages with identical URLs and content as public.”
>
> URL과 내용이 같은 페이지를 공개로 취급한다.

출처: Liu et al., BACScan, CCS 2025, §4 RBAC Vulnerability Detection.
[저자 연구실 원문](https://seclab.cse.cuhk.edu.hk/papers/ccs25-BACScan.pdf), 로컬 원문 `papers/BACScan_CCS25.pdf`, 추출 텍스트 `data/bacscan.txt`.

원문 절차는 두 계정의 탐색 결과를 비교하고 남은 페이지의 GET 요청을 다른 세션으로 재실행하는 방식이다.
같은 페이지를 두 계정이 모두 탐색했다면 특정 사용자 공유도 필터에 걸릴 수 있다.
그러므로 “공유 객체를 처리하지 못한다”나 “우리가 최초로 공개를 구분한다”는 주장은 하지 않는다.
대신 허용된 객체가 한쪽 탐색에만 나타나는 조건에서 관찰 기반 필터와 사전 설정 근거의 차이를 측정한다.
이 조건이 실제 오탐을 만드는지는 미측정이며 현재는 우리 추론이다.
원문의 §6은 크롤러의 불완전한 탐색으로 미탐이 생길 수 있다고 명시한다.

[저자 공개 코드](https://github.com/LFYSec/BACScan)는 확인했다.
README는 현재 크롤러가 간소화된 버전이며 누락 요청을 수동 보충할 수 있다고 설명한다.
원도구 실행은 아직 하지 않았다.
원도구 성능과 공개 필터만 재구현한 성능은 별도 표로 보고한다.

### 2. AuthProbe도 다중 계정과 객체 일치를 사용한다

> “We define ownership as the ground truth that the API itself asserts through its collection operation.”
>
> API가 목록 조회 연산을 통해 주장하는 내용을 소유권의 정답으로 정의한다.

출처: AuthProbe, arXiv:2607.20574, §III.
[원문 HTML](https://arxiv.org/html/2607.20574).

원문은 목록 조회로 계정별 객체를 수집하고, 다른 계정 조회 응답이 요청한 객체와 일치하는지 확인한다(§V).
다중 계정 테스트와 객체 일치 확인 자체를 차별성으로 주장하지 않는다.
우리 검증 후보는 공개·로그인 공개·선택 공유가 섞인 조건에서 목록 관찰과 사전 설정 근거가 어떻게 달라지는지다.
이 조건에 대한 우월성은 아직 확인하지 않았다.

### 3. 현재 차별성 후보

> 핵심 후보는 목록 API 호출의 성공과 개별 객체의 읽기 허용을 분리하는 판정이다. 빈 목록·허용 객체·금지 객체 혼합 응답에서 상태 코드 중심 판정과 반환 객체 대조를 같은 권한 근거로 비교한다.

AuthzTrace는 작은 권한 계약과 객체 표식을 사용하는 공개 도구이며 초기 설계와 본체가 겹친다. [공식 저장소](https://github.com/Asttr0/AuthzTrace).
별도 정책 입력, 다중 계정, 표식, 본문 확인 자체를 새로운 방법으로 주장하지 않는다.
사용자가 제공한 팀원 보고에서는 0.6.0이 가짜 API의 수정 모드에서 200+빈 목록 네 건을 BOLA로 오탐했다고 한다. 실제 Memos 재현·원본 로그 대조·개선안 성능 결과는 아니다.
기존 계약·응답 검증 설정으로 해결되는지 먼저 확인하며, 단순한 상태 코드 조건 수정만으로 끝나면 연구 기여가 약할 수 있다.
상세 분모와 근거 수준은 [2026-10-02 목록 조회 판정 브리핑 최종안](2026-10-02%20%EB%AA%A9%EB%A1%9D%20%EC%A1%B0%ED%9A%8C%20%ED%8C%90%EC%A0%95%20%EB%B8%8C%EB%A6%AC%ED%95%91%20%EC%B5%9C%EC%A2%85%EC%95%88.md)을 따른다.

보류 기능을 추가했다는 사실만으로 기여가 되지 않는다.
보류한 실제 위반을 미탐으로 포함하고, 사람이 추가로 확인해야 하는 비용까지 보고한다.
새로운 방법이라는 결론은 비교 실험과 추가 선행연구 검토 후 결정한다.

## 판정 절차

1. 소유자 A, 비공유 계정 B, 공유 계정 C, 비로그인 계정의 역할을 고정한다.
2. 객체를 생성하면서 ID, 공개 상태, 공유 대상, 설정 시각과 설정 성공 근거를 기록한다.
3. 정책 의미와 설정을 바탕으로 각 계정의 읽기 허용·금지·미확인을 정한다.
4. 각 계정으로 대상 API를 조회한다.
5. 응답의 객체 ID와 고유한 합성 표식으로 실제 대상 객체 반환을 확인한다. HTTP 200만으로 반환을 인정하지 않는다.
6. 아래 표로 결과를 출력한다. 판정 근거와 적용한 규칙을 함께 남긴다.

| 독립 근거 | 응답 확인 | 판정 |
|---|---|---|
| 해당 계정의 읽기 금지 | 대상 객체 반환 확인 | 위반 확정 |
| 해당 계정의 읽기 허용 | 대상 객체 반환 확인 | 허용된 접근 |
| 읽기 금지 | 객체 존재·계정 유효성 확인, 명시적 접근 거부 | 이 요청에서 위반 미관측 |
| 읽기 허용 | 명시적 접근 거부 | 허용 접근 실패. BOLA와 별도 기록 |
| 허용 여부 불명 | 반환 여부와 무관 | 정책 근거 부족으로 보류 |
| 허용 여부 확인 | 객체 일치 불명 | 반환 객체 확인 부족으로 보류 |

“위반 미관측”은 앱 전체가 안전하다는 뜻이 아니다.
404는 객체 부재·접근 거부를 구분하기 어려우므로 소유자 조회와 계정 유효성을 함께 확인한다.
하위 객체인 이슈·첨부는 부모 권한을 따른다는 정책 근거가 있을 때만 연결한다.
같은 범주의 테스트 객체 결과를 다른 객체나 엔드포인트의 판정으로 자동 전파하지 않는다.

### 대상과 정답

| 대상 | 확인할 조건 | 정답 확인 방법 | 현재 상태 |
|---|---|---|---|
| Gitea 28.0.0 | 공개·비공개·협업자 공유, 저장소와 이슈 | 설정 이력·정책 의미·계정 관계 | 저장된 예비 조회 18건 검토 |
| Memos 0.9.0 | PUBLIC·PROTECTED·PRIVATE, 개별 조회와 목록 조회 | 설정 이력 + 취약 보고·소스 + 실제 응답 | 개별 조회 6건 검토. 취약 읽기 경로 미재현 |
| Memos 비교 버전 | 같은 취약 요청이 수정 전후 달라지는지 | 동일 요청의 반환 객체와 접근 거부 비교 | 수정 버전 선정 필요 |
| 통제된 취약 변형 | 공개·공유 정상 접근과 비공개 누출을 함께 검사 | 의도적으로 변경한 권한 검사와 별도 정답 | 자연 취약점 확보 실패 시 보조 평가 |

crAPI의 기존 공개 필드 검색 결과는 특정 검색 조건의 결과다.
“공개 필드 0건”만으로 객체별 상태 설정이 절대 불가능하다고 증명할 수는 없다.
이번 본체에서는 공개·공유 상태를 직접 바꿀 수 있는 Gitea·Memos를 우선 사용한다.

### Memos 읽기 취약 후보와 패치 검증

[v0.9.0 server/memo.go](https://github.com/usememos/memos/blob/v0.9.0/server/memo.go)를 직접 읽었다.
`GET /api/memo`와 `GET /api/memo/all`은 계정 상태로 `VisibilityList`를 제한한 뒤 `visibility` 질의 인자가 있으면 그 목록을 다시 지정하는 코드가 있다.
타인 PRIVATE 메모의 합성 표식이 목록 응답에 실제 포함되는지 로컬에서 확인할 후보 경로다.
개별 조회 `GET /api/memo/{id}`는 비공개에 403을 주므로 다른 경로의 음성 대조군으로 쓸 수 있다.

[v0.9.1 소스](https://github.com/usememos/memos/blob/v0.9.1/server/memo.go)에도 해당 질의 인자 처리 코드가 있다.
따라서 0.9.1을 이 후보 경로의 수정 버전으로 확정하지 않는다.
[CVE-2022-4811 관련 수정 커밋](https://github.com/usememos/memos/commit/3556ae4e651d9443dc3bb8a170dd3cc726517a53)에는 여러 API 변경이 있어 후보 경로와 해당 CVE의 일치도 추가 확인이 필요하다.
초기 확인에서 Docker 엔진에 연결되지 않았으며, 이후 사용자 지시에 따라 Docker 실험을 제외했다. 후보 경로를 재현했다고 주장하지 않는다.

### 비교군과 공정한 비교

| 비교군 | 역할 | 주의 |
|---|---|---|
| 타인 계정 + HTTP 200 | 가장 단순한 문제 확인 기준선 | 기존 도구 전체를 대표한다고 말하지 않음 |
| 타인 계정 + 대상 객체 일치 | 응답 확인 개선의 효과 분리 | 공개·공유 권한 근거 없음 |
| BACScan식 공개 필터 재구현 | 관찰 기반 공개 처리 비교 | 원도구 성능으로 표시하지 않음 |
| 설정 근거 기반 판정 | 제안 방법 | 설정 입력 비용도 포함 |
| 모든 평가 객체의 권한을 입력한 판정 | 성능·입력 비용의 상한 대조 | 객체별 수동 입력 시간을 측정 |

판정기 비교에서는 모든 방법에 동일한 요청·객체·응답을 제공한다.
탐색 도달 조건은 두 계정 모두 도달, 소유자만 도달, 공유자에게만 링크 누락의 세 조건으로 나눈다.
원도구를 실행한 전체 탐색 실험은 별도로 보고해 발견 범위 차이를 섞지 않는다.
한쪽에만 정답 근거를 더 준 실험이므로 성능 향상을 알고리즘 자체의 우월성으로 해석하지 않는다.

### 테스트 객체 수와 평가 객체 수

범주별 객체 1개는 초기 실행 점검에만 쓴다.
“공개 범주 수만큼이면 충분하다”는 보장은 없다.
필요한 설정은 객체 종류 × 공개 범주 × 계정 관계 × 엔드포인트 정책으로 달라진다.
준비한 대표 객체 수, 평가에 사용한 전체 객체 수, 요청 사례 수를 따로 센다.
반복 객체를 늘려도 독립 취약 경로 수가 늘어난 것으로 세지 않는다.

| 지표 | 계산·기록 방식 |
|---|---|
| 재현율 | 위반 확정 수 / 실제 위반 수. 보류한 위반도 분모에 포함 |
| 오탐률 | 정상 사례를 위반으로 판정한 수 / 전체 정상 사례 수 |
| 허용 접근 오탐률 | 정상 공개·공유 접근을 위반으로 판정한 수 / 허용된 객체 반환 사례 수 |
| 확정 정밀도 | 실제 위반인 확정 수 / 모든 위반 확정 수 |
| 보류율·판정률 | 보류 수 / 전체 유효 사례 수, 1 - 보류율 |
| 입력 비용 | 계정 수, 객체 수, 수동 설정 항목 수, 준비 시간, 추가 요청 수 |
| 검토 비용 | 보류 사유별 건수, 사람 확인 시간, 확인 후 판정 |

실행 실패 건수와 원인도 별도로 공개한다.
보류 집합의 평가 정답은 별도 보관하고 판정기에는 필요한 근거를 의도적으로 누락한다.
근거가 전부 있는 집합과 근거 일부를 가린 집합을 나눠 보고한다.
동일한 판정률로 조절할 수 있는 방법끼리만 같은 판정률에서 비교한다.
고정된 방법은 원래 판정률과 성능을 함께 보고한다.

가설은 “명시적 설정 근거를 쓰면 관찰 기반 판정보다 공개·공유 오탐을 줄이면서 실제 읽기 위반을 유지하고, 전체 권한 입력보다 준비 비용이 낮아진다”다.
오탐이 줄지 않거나, 보류 때문에 재현율이 낮아지거나, 준비 비용이 줄지 않으면 해당 부분의 가설은 지지되지 않는다.
작은 표본의 오탐 0건을 전체 앱의 오탐 0%로 일반화하지 않는다.
