# BOLA 구체화: 교수님 절차 적용

## 출발 가설

> 접근 성공 여부만으로 BOLA를 판정하면 공개·공유 객체 조회를 오탐한다. 객체의 공개 상태를 함께 고려하면 더 정확히 식별할 수 있다.

## 1단계. 이 가설을 직접 다룬 논문이 있는가

있다. "공개 자원 때문에 오탐이 난다"를 직접 다루고 거르는 방법까지 낸 논문이 두 편 있다.

| 논문 | 읽기 수준 | 공개 자원 처리 방식 | 원문 근거 |
|---|---|---|---|
| AuthScope (Zuo, Zhao, Lin, CCS 2017) | 1차 + 2차(§4.3) | 로그인하지 않은 상태로 앱을 한 번 더 돌려, 비로그인으로도 응답이 오는 **인터페이스**를 공개로 보고 제외 | "If we observe a previously identified vulnerable interface can actually serve the public resource, we will not flag it vulnerable." (§4.3) |
| BACScan (Liu et al., CCS 2025) | 1차 + 2차(§3.3, §4 RBAC 탐지, §5.1 표 1·2) | 공격자·피해자 세션으로 각각 크롤링해서 **URL과 내용이 같은 페이지**를 공개로 보고 제외 | "it compares each page in the attacker's and victim's navigation graphs, treating pages with identical URLs and content as public." (§4, RBAC Vulnerability Detection) |

참고(이미 읽은 것): 오탐 문제를 지적만 하고 푸는 방법은 없는 논문으로 EvoMaster(Sahin et al., 2604.00702, 1차 + 2차 §3.3)가 있다. 이 논문의 인가 누락 오라클은 PUT·PATCH·DELETE 수정 동사 전용이다.

## 2단계. 없으면

해당 없음. 직접 다룬 논문이 있으므로 3단계로 간다.

## 3단계. 있으면 그 논문 하나를 읽고 무엇이 부족한지

가장 직접적인 논문 하나로 **BACScan**을 골랐다. 최신(CCS 2025)이고, 블랙박스이며, 읽기 위반(RBAC)에 공개 필터를 실제로 적용하고, 정답 세트(Memos-0.9.0 포함)까지 공개했기 때문이다.

BACScan 읽기 위반 탐지 절차 (§4, 2차):
1. 피해자 세션과 공격자 세션으로 따로 크롤링해서 각자 도달한 페이지와 응답을 모은다.
2. 두 세션 모두에서 URL과 내용이 같은 페이지를 공개로 보고 뺀다.
3. 남은 "피해자만 보이는 페이지"를 공격자 세션으로 다시 요청하고, 응답 유사도가 0.7을 넘으면 위반으로 본다.

부족한 점:
1. **공개 여부를 "관찰"로 추정한다.** 공격자가 탐색 중에 그 페이지에 도달했는지로 공개를 정한다. 공개 객체인데 공격자 화면에 링크가 없으면 공개로 걸러지지 않고, 다시 요청했을 때 내용이 같으니 위반으로 잡힐 수 있다(오탐). 이것은 원문 절차에서 나오는 우리 추론이며 논문이 측정한 오류는 아니다.
2. **공개와 비공개 두 가지만 본다.** 특정 사용자에게만 공유된 객체(Gitea 협업자), 로그인 사용자 전체 공개(Memos PROTECTED)는 범주로 다루지 않는다. 계정도 피해자·공격자 쌍(수정 위반 탐지는 권한 높은 계정 포함 3개) 구조다.
3. **판정은 위반 아니면 정상 두 가지다.** 근거가 부족한 객체를 따로 표시하는 상태가 없다. 0.7 유사도 임계값은 선행 연구 값을 그대로 쓴다.
4. **크롤러에 의존한다.** 저자 스스로 크롤러가 못 간 페이지는 미탐이 된다고 밝힌다(§6). 화면 탐색이 없는 API는 이 절차의 1단계가 성립하지 않는다.

정정: 이전 노트에서는 BACScan 공개 필터를 "엔드포인트 단위"라고 썼다. 원문은 "URL과 내용이 같은 페이지" 단위다. 객체마다 URL이 다른 앱에서는 사실상 객체 단위로 동작한다. 그래서 우리 차이점은 "단위"가 아니라 **"공개 상태를 어디서 알아내느냐(관찰 추정 vs 사전 지정)"와 "공유·로그인 공개 범주, 보류"**로 바꿔야 한다.

## 4단계. 그 부족한 점을 우리는 어떻게 해결하나

| BACScan의 부족한 점 | 우리 해결 방법 | 검증 방법 |
|---|---|---|
| 공개 여부를 탐색 도달로 추정 | 테스트 객체를 만들 때 공개 상태를 지정해 독립적인 정답으로 쓴다 | Gitea, Memos에서 같은 객체에 대해 BACScan식 추정 라벨과 지정 라벨을 비교 |
| 공개·비공개 두 범주 | 앱의 공개 범주(공개, 로그인 공개, 비공개, 특정 사용자 공유)마다 테스트 객체 1개 | Memos PUBLIC/PROTECTED/PRIVATE, Gitea 공개/비공개/협업자 |
| 위반·정상 두 판정 | 근거 없는 객체는 보류로 분리하고 보류율을 보고 | 오탐률·재현율·보류율을 같은 판정률에서 비교 |
| 크롤러 의존 | 화면 탐색 없이 API 응답과 테스트 객체 ID로 판정 | 같은 앱의 API에 직접 적용 |

비교군:
- 단순 규칙(ICST'20 방식: 다른 토큰으로 성공하면 위반)
- BACScan식 공개 필터(두 세션 도달·내용 동일이면 공개). 원도구 실행이 어려우면 논문 절차대로 재구현하고 "재구현"으로 표시한다.

정답:
- 오탐률: Gitea 28.0.0, Memos 0.9.0의 테스트 객체 (예비 결과 단순 규칙 오탐 8/18, 3/6)
- 재현율: Memos 0.9.0의 알려진 취약점(BACScan 정답 세트 구성 앱, CVE-2022-4811 등). 취약 경로는 미확인. 막히면 Gitea에 권한 검사를 뺀 변형을 만든다.

## 5단계. 최종 문장

> 기존 연구는 공개 자원 때문에 생기는 오탐을 알고 있고, 비로그인 실행(AuthScope)이나 두 세션의 탐색 결과 비교(BACScan)로 공개 페이지를 걸러냈다.
> 우리는 공개 여부를 관찰로 추정하기 때문에 탐색에서 놓친 공개 객체, 특정 사용자 공유와 로그인 사용자 공개 같은 범주, 근거가 없는 객체를 구분하지 못하는 부분이 부족하다고 본다.
> 그래서 객체를 만들 때 공개 상태를 지정한 테스트 객체로 판정하고, 근거가 없는 객체는 보류로 분리해서, 단순 규칙과 BACScan식 공개 필터 대비 오탐률·재현율·보류율을 함께 잰다.

## 남은 확인

- BACScan식 필터가 실제로 Gitea·Memos에서 몇 건을 공개로 잘못 거르거나 놓치는지는 아직 측정하지 않았다. 4단계 첫 줄이 이 연구의 첫 실험이다.
- CVE-2022-4811 취약 경로(huntr 원 보고서, 2차 읽기 필요)
- BACScan 원도구 공개 여부(논문에 저장소 링크 확인 필요)
