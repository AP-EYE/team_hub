# 연구 주제 정의와 근거

## 주제 한 줄 정의

> **두 테스트 계정과 공개·비공개·공유 상태를 지정한 소수의 테스트 객체만으로, 권한표 전체를 작성하지 않고 API의 읽기 권한 위반(BOLA)을 확정하고, 근거가 없는 객체는 판정 보류로 분리하는 진단 방법을 만든 뒤, 그 확정 범위와 오탐률과 보류율을 측정한다.**

## 용어 정리

**API**
앱이 서버에 데이터를 요청하는 창구

**엔드포인트**
API의 주소와 동작 조합

**객체**
엔드포인트가 다루는 데이터 한 건. 기록·게시글·주문 한 건

**인가 (Authorization)**
로그인한 사용자가 특정 객체에 접근해도 되는지 서버가 판단하는 것

**BOLA (Broken Object Level Authorization)**
서버가 객체 주인을 확인하지 않아 남의 객체를 읽거나 바꿀 수 있는 취약점. OWASP API Top 10 1위

**읽기 권한 위반**
BOLA 중 남의 객체를 조회할 수 있는 경우

**테스트 계정**
진단용 계정. A는 주인, B는 권한 없는 사용자, C는 공유받은 사용자

**테스트 객체**
테스트 계정으로 직접 만든 객체. 공개·비공개·공유 상태를 미리 정해 둔다

**공개·비공개·공유**
공개는 누구나, 비공개는 주인만, 공유는 주인이 지정한 계정만 조회 가능

**권한표**
객체마다 누가 접근해도 되는지 사람이 전부 적은 표. ZAP 같은 기존 도구가 요구한다

**확정**
금지 근거가 있고 금지된 계정이 실제로 데이터를 받았을 때 위반으로 단정하는 것

**독립적인 근거**
응답 200과 별개로 접근 금지를 보여주는 증거. 예: 비공개 설정, 공유 목록에 B 없음

**미표시 객체**
테스트 객체가 아닌 나머지 객체. 공개 여부를 모른다

**판정 보류**
근거가 부족해 위반·정상 결론을 내리지 않는 판정

**확정 범위**
전체 검사 대상 중 결론을 낸 비율

**오탐률**
정상 접근(공개 조회, 공유받은 조회)을 위반으로 잘못 판정한 비율

**보류율**
전체 검사 대상 중 판정 보류로 남긴 비율

**재현율**
실제 위반 중 위반으로 확정한 비율

## 근거 1. 기존 판정은 "타인 객체 접근 = 위반"으로 단순화해 오탐을 만든다

- **"다른 토큰으로 요청이 성공하면 위반"으로 판정한다**
  > "this checker attempts to re-execute the valid last request of any test case executed by the main driver using a different authentication token. If this succeeds, an attacker with a different authentication token could hijack the objects used in the last request, and a user namespace violation is reported."
  >
  > → 이 검사기는 메인 드라이버가 실행한 테스트 케이스의 마지막 유효 요청을 다른 인증 토큰으로 다시 실행한다. 성공하면 다른 토큰을 가진 공격자가 그 요청이 사용한 객체를 가로챌 수 있다고 보고, 사용자 네임스페이스 위반으로 보고한다.
  >
  > (Atlidakis, Godefroid, Polishchuk, *Checking Security Properties of Cloud Service REST APIs*, ICST 2020, 3.B절)

- **그 단순 규칙이 오탐을 만든다고 최신 연구가 지적한다**
  > "Simply stating that a user should not access or manipulate resources of other users would just result in many false-positive faults."
  >
  > → 사용자가 다른 사용자의 리소스에 접근하거나 조작해서는 안 된다고 단순하게 규정하면 오탐 결함이 많이 생길 뿐이다.
  >
  > (Sahin, Zhang, Arcuri, *Enhancing REST API Fuzzing with Access Policy Violation Checks and Injection Attacks*, arXiv 2604.00702, 2026-04, 3.3절. 관리자, 모더레이터, 가족 공유 계정을 예로 든다)

- **정책을 추론하는 방법도 관찰한 401/403에 의존한다**
  > "No assumption on their relative access policies is needed, and no formal description of these policies is needed either. Such information is inferred dynamically based on the 401 (not authenticated) and 403 (not authorized) HTTP status codes received back during the fuzzing session."
  >
  > → 사용자들 사이의 접근 정책에 대한 가정도, 정책의 형식적 기술도 필요하지 않다. 그런 정보는 퍼징 중 돌아온 401(인증 안 됨)과 403(권한 없음) 응답 코드로부터 동적으로 추론한다.
  >
  > (arXiv 2604.00702, 3절)
  - 403을 한 번도 관찰하지 못한 읽기 API에는 판정 근거가 없다.

## 근거 2. 권한 의도를 모르면 도구가 스스로 정답을 만들지 못한다

- **OpenAPI 표준에는 객체 수준 권한을 적는 자리가 없다**
  > "The Open API Specifications security properties do not address object authorization and provide no standardized approach to define such object properties."
  >
  > → OpenAPI 명세의 보안 속성은 객체 수준 권한을 다루지 않으며, 그런 객체 속성을 정의하는 표준 방법도 제공하지 않는다.
  >
  > (*OpenAPI Specification Extended Security Scheme*, arXiv 2212.06606, 2022, 초록)

- **정답을 사람이 넣는 도구는 권한표 전체를 요구한다**
  > "In order to identify potential access control issues, ZAP needs to know which parts of the web application are supposed to be accessed by which user."
  >
  > → 잠재적인 접근 제어 문제를 찾으려면, ZAP은 웹 애플리케이션의 어느 부분에 어느 사용자가 접근해야 하는지 알아야 한다.
  >
  > (OWASP ZAP Access Control Testing 공식 문서)

- **블랙박스 도구는 목록 API로 소유권을 얻고, 목록이 없으면 테스트 대상이 사라진다**
  > "It therefore depends on the collection operation to discover ownership, or on explicit seeds in configuration when no suitable collection operation exists. An API that exposes no listing and uses unguessable identifiers will yield few objects to test."
  >
  > → 따라서 소유권을 알아내기 위해 목록 조회 작업에 의존하고, 적절한 목록 조회가 없으면 설정에 명시한 시드에 의존한다. 목록을 제공하지 않고 추측할 수 없는 식별자를 쓰는 API에서는 테스트할 객체가 거의 나오지 않는다.
  >
  > (*AuthProbe*, arXiv 2607.20574, 2026-07, VIII절)

## 근거 3. 트래픽 기반 판정은 앱마다 다시 맞춰야 하고, 평가도 제한적이다

- **규칙과 가중치를 앱마다 재조정해야 한다고 저자가 직접 인정한다**
  > "the prototype's evidence rules, risk weights, thresholds, and endpoint configuration are tied to the semantics of the testbed and require recalibration when transferred to another application."
  >
  > → 프로토타입의 증거 규칙, 위험 가중치, 임계값, 엔드포인트 설정은 테스트베드의 의미에 묶여 있어서, 다른 애플리케이션으로 옮길 때 재조정이 필요하다.
  >
  > (*A Non-Intrusive Traffic Analysis Framework for Authorization Risk Detection*, arXiv 2607.16754, 2026-07, 6.2절)

- **실험 데이터가 실제 환경과 다르다**
  > "the samples were generated by local testbed scripts and were balanced between positive and negative cases; this differs from production environments, where authorization-risk events are rare"
  >
  > → 표본은 로컬 테스트베드 스크립트로 생성했고 위반과 정상 사례를 같은 수로 맞췄다. 이는 권한 위험 사건이 드문 실제 운영 환경과 다르다.
  >
  > (arXiv 2607.16754, 6.2절)

- **공개 설계 API는 평가하지 않았다**
  - 본문에 "public"이라는 단어가 한 번도 나오지 않는다. 처리하지 못한다고 단정할 근거는 없고, 평가 범위 밖이다.

## 근거 4. 공개 페이지를 거르는 기존 방식은 엔드포인트 단위다

- **양쪽 계정이 모두 볼 수 있는 페이지를 공개로 보고 제외한다**
  > "We then analyze the URLs and contents of all pages, filtering out public pages that are accessible to both attackers and victims."
  >
  > → 이어서 모든 페이지의 URL과 내용을 분석해, 공격자와 피해자 모두 접근할 수 있는 공개 페이지를 걸러낸다.
  >
  > (*BACScan*, CCS 2025, 3.3절)
  - 같은 엔드포인트 안에 공개 객체와 비공개 객체가 섞인 경우는 이 방식으로 구분되지 않는다. 우리가 테스트 객체 단위로 공개·비공개를 지정하는 이유다.

## 근거 5. 문제는 실제로 흔하다

- **BOLA 실태에서 직접 객체 참조가 가장 큰 유형이다**
  > "Direct Object Reference is stable under weighting (36.9% raw, 37.5% weighted...)"
  >
  > → 직접 객체 참조 유형은 가중치를 적용해도 안정적이다(원래 36.9%, 가중 37.5%).
  >
  > (*Broken Object Level Authorization in the Wild*, arXiv 2605.25865, 2026-05, 5.10절)

- **국내 사고의 원인이 권한 검증 누락이다**
  - 강남언니(2026-09-08, 21만 9,665건): 조치 내용 "인증 절차 강화 및 권한 검증 로직 재정비"
  - 레쥬메나인(2026-09-15): 공표된 원인 "서버 권한 검증 누락"

## 근거 6. 응답에 권한 상태가 드러나는 API는 일부다 (우리 조사)

### 왜 조사했나

우리 방법은 테스트 객체가 아닌 객체(미표시 객체)를 판정할 때, 그 객체가 비공개인지 보여주는 단서가 있어야 한다.
가장 현실적인 단서는 API 응답에 들어 있는 필드다. 예를 들어 서버가 게시글을 돌려줄 때 `"visibility": "private"` 같은 값을 함께 준다면, 도구는 그 게시글이 비공개라는 것을 알 수 있다.
그래서 "실제 API들이 이런 필드를 응답에 얼마나 넣어 주는가"를 먼저 세어 봤다. 이 비율이 너무 낮으면 우리 방법이 쓸 수 있는 곳이 거의 없다는 뜻이기 때문이다.

### 무엇을 조사했나

- **OpenAPI 명세**: API가 어떤 주소로 무엇을 요청받고 어떤 모양의 데이터를 돌려주는지 적은 설계 문서다. JSON이나 YAML 파일로 되어 있다. 이 문서를 보면 실제로 서버에 요청을 보내지 않고도 응답에 어떤 필드가 들어가는지 알 수 있다.
- **APIs.guru**: 공개된 OpenAPI 명세를 모아 둔 사이트다. GitHub, Jira, Mastodon 같은 서비스의 명세 2,529개가 등록돼 있다(2026-09-29 기준).

실제 서비스에는 요청을 한 번도 보내지 않았다. 공개된 설계 문서만 읽었다.

### 어떻게 셌나

1. APIs.guru에 등록된 명세 2,529개를 전부 내려받았다. 2,521개가 성공했다.
2. 각 명세에서 **조회 요청(GET)이 성공했을 때 돌려주는 데이터**에 어떤 필드 이름이 있는지 모았다. 조회 요청이 하나도 없는 명세는 뺐다. 그래서 2,034개가 남았다.
3. 필드 이름이 아래 둘 중 하나와 **정확히 같으면** 권한 단서 후보로 셌다.
   - 공개·비공개 상태: `visibility`, `public`, `private`, `is_public`, `is_private`, `privacy` 등
   - 공유 대상: `shared_with`, `collaborators`, `acl`, `access_control` 등
4. `secret`, `access`, `permissions`처럼 여러 뜻으로 쓰이는 이름은 오해를 줄이려고 뺐다.
5. Azure, Google, AWS, Microsoft 명세 1,031개는 따로 뺀 결과도 냈다. 서버·저장소를 관리하는 API라서 "남의 게시글을 본다" 같은 상황과 거리가 멀고, 개수가 많아 전체 비율을 끌어내리기 때문이다.

### 결과

| 대상 | 조사한 명세 | 후보가 나온 명세 | 비율 |
|---|---|---|---|
| 전체 | 2,034 | 133 | 6.5% |
| 대형 클라우드 제외 | 1,003 | 95 | **9.5%** |

대형 클라우드를 뺀 명세 100개 중 약 9~10개의 응답에 공개·공유 상태로 보이는 이름의 필드가 있다는 뜻이다.

### 이름이 맞으면 정말 권한 필드인가: 30개 직접 확인

이름만 보고 센 숫자라서, 그 필드가 정말 "이 객체가 비공개인가"를 뜻하는지는 알 수 없다.
그래서 후보 95개 중 30개를 골라 명세 문서를 사람이 직접 열어 필드의 설명과 쓰임새를 확인했다.
같은 회사 명세가 몰리지 않도록 회사당 하나씩 골랐고, 무작위로 뽑되 누가 다시 뽑아도 같은 30개가 나오게 뽑는 방식을 고정했다.

| 확인 결과 | 개수 | 뜻 |
|---|---|---|
| 해당 | 17 | 실제로 객체의 공개·비공개·공유 상태를 뜻한다 |
| 무관 | 5 | 이름만 같고 권한과 관계없다. 예: `isPrivate`가 "사립학교인가"를 뜻함 |
| 판단 보류 | 8 | 명세 설명만으로는 뜻을 확정할 수 없다 |

30개는 전체를 대표하도록 뽑은 표본이 아니다. 그래서 "57%(17/30)가 진짜"라고 전체에 곱해서 말하면 안 된다. 이 확인의 목적은 **이름만으로 세면 틀리는 경우가 실제로 있다**는 것을 보이는 데 있다.

### 이 조사가 말해 주는 것

- 응답에 권한 단서를 넣어 주는 API는 일부다. 이름 기준으로도 10개 중 1개가 안 된다.
- 필드 하나만으로는 판정할 수 없다. 게시글이 `private`여도 계정 B가 공유받은 사람일 수 있다. 그래서 우리 방법은 **비공개 필드와 공유 대상 목록이 둘 다 보이고, 그 목록에 B가 없을 때만** 위반을 확정한다. 나머지는 판정 보류로 남긴다.
- 결국 미표시 객체를 확정할 수 있는 API는 9.5%보다 적다. 우리 연구가 "모든 API에서 된다"가 아니라 "확정 범위와 보류율을 함께 측정한다"고 말하는 이유다.

## 정리: 기존 연구가 비워 둔 자리

- 단순 타인 접근 규칙은 공유·공개 사례에서 오탐한다 (ICST'20, 2604.00702)
- 권한 의도를 표준 명세로 얻을 수 없다 (2212.06606)
- 권한표 전체 입력은 비용이 크고, 목록 API 기반 추론은 목록이 없으면 멈춘다 (ZAP, AuthProbe)
- 트래픽 가중치 방식은 앱마다 재조정이 필요하다 (2607.16754)
- 공개 구분은 엔드포인트 단위에 머문다 (BACScan)

**→ 우리가 검증할 것**: 소수의 공개·비공개·공유 테스트 객체만 지정했을 때, 어느 범위까지 위반을 확정할 수 있고, 오탐과 보류가 각각 얼마나 남는가.
