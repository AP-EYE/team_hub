# 한국어 API 응답 최소 문맥 분류 가설

## 주제 한 줄 정의

> **한국어 API 응답에서 로컬로 처리하는 필드 경로·형제 필드·값 문맥을 단계적으로 늘리고 불확실한 분류를 보류하면, 고위험 개인정보 누락을 억제하면서 잘못된 수정 우선순위를 줄일 수 있는지 검증한다.**

이것은 결과가 아니라 **검증 전 가설**이다. 2026-09-29 팀 기록에는 SemIf와 로컬 모델이 느리고 정확도가 기대보다 낮았다는 관찰만 있다. 평가 원본·표본 수·오탐률은 이 Vault에서 확인하지 못했으므로 한국어 처리 실패가 원인이라고 단정하지 않는다. [2026-09-29 멘토링 피드백](../../review/2026-09-29%20%EB%A9%98%ED%86%A0%EB%A7%81%20%ED%94%BC%EB%93%9C%EB%B0%B1.md)과 9/22 실험 원본 확보가 먼저다.

## 연구 흐름: 신뢰성부터 잰다 (2026-09-29 추가)

이 블록의 최종 결과물은 **엔드포인트별 수정 우선순위**다. 기획서 4단계 출력이 이것이고, 진단 업체와 기업이 실제로 보는 것도 이 순위다. 그래서 질문은 "분류기가 몇 % 맞히나"에서 끝나지 않는다. **"분류기가 틀려도 그 순위를 믿을 수 있나"**가 이 블록의 신뢰성 질문이다.

오탐을 줄이는 방법을 고르기 전에, 얼마나 줄여야 하는지부터 정한다. 세 단계로 진행한다.

| 단계 | 질문 | 결과물 | 문서 |
|---|---|---|---|
| 1. 신뢰성 기준선 | 분류 오류가 수정 우선순위를 얼마나 흔드나? 순위가 안정되려면 오탐률·미탐률이 몇 % 이하여야 하나? | 목표 기준선 (예: 상위 5 유지 90%에 필요한 오탐률) | [개인정보 분류 오류의 순위 영향](%EA%B0%9C%EC%9D%B8%EC%A0%95%EB%B3%B4%20%EB%B6%84%EB%A5%98%20%EC%98%A4%EB%A5%98%EC%9D%98%20%EC%88%9C%EC%9C%84%20%EC%98%81%ED%96%A5.md) |
| 2. 원인 진단 | 오탐의 원인이 한국어 이해인가, 정보주체 문맥인가, 라벨 모호함인가? | 원인별 오류 비율 | 아래 "보강: 원인 가르기" |
| 3. 해결책 선택 | 1의 기준선을 넘는 가장 단순한 방법은? | 정규식 / 한국어 인코더 미세조정 / 문맥 추가 / 보류 중 선택 | 아래 RQ1~RQ3, "비교할 구현 경로" |

이 순서가 주는 것:
- **목표가 숫자가 된다.** "오탐을 줄인다"가 아니라 "순위가 흔들리지 않는 X% 이하로 줄인다"가 된다. 교수가 요구한 "몇 %까지"에 대한 답이다.
- **비싼 방법을 정당화하거나 기각할 근거가 생긴다.** 정규식이 기준선을 넘으면 한국어 모델 미세조정은 필요 없다. 넘지 못하면 필요하다.
- **선행연구와 갈리는 지점이 분명해진다.** 가까운 개인정보 분류 연구(2605.06305, 2512.04120)는 분류 성능에서 멈추고 우선순위 영향은 평가하지 않았다. 입력 오류가 우선순위를 흔드는 문제는 CVSS 사람 채점 불일치(2308.15259, 같은 취약점에 68%가 다른 등급)로 확인됐지만, 자동 분류기 오류로 잰 연구는 이번 검색에서 찾지 못했다.

1단계는 합성 데이터 방법 시연까지 됐다. 가정 가중치 기준으로 오탐 5%만 섞어도 1순위 엔드포인트가 약 4번 중 1번 바뀌었다(76.3% 유지). 가중치가 정해지지 않아 실제 결과는 아니다.

## 왜 현재 설계에서 중요한가

[ARCHITECTURE](../../arch/2026-09-29%20%EA%B2%8C%EC%9D%B4%ED%8A%B8%EC%9B%A8%EC%9D%B4%20%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98.md) 5.2는 `ownerEmail` 등을 공통 이름으로 바꾸고 5.4는 그 **이름을 개인정보 유형으로 분류**한다. 이 방식은 이메일·주민등록번호처럼 이름과 형식이 뚜렷한 항목에 맞는다. `consultationReason`, `memo`, `reason`은 같은 이름이어도 상담 동기, 결제 취소 사유, 배송 메모일 수 있다. 이름만 보고 민감정보로 잡으면 잘못된 고위험 경보가 늘고, 반대로 전부 무시하면 자유서술 노출을 놓친다. 현재 6.6의 원칙은 **응답 값의 외부 반출 금지**이지 로컬 메모리에서 값의 일시적 분석 금지가 아니다.

인가 위반 여부와 개인정보 분류는 분리해야 한다. 독립적인 권한 근거로 위반이 확인된 응답에서만 노출 영향도를 계산하고, 개인정보 모델의 판단을 인가 판정 근거로 사용하지 않는다. 개인정보 분류의 불확실성도 확정된 위반 사실을 뒤집지 않는다.

**분류 단위**는 `(서비스, 엔드포인트, JSON 경로, 응답 값, 그 값이 가리키는 정보주체)`다. 같은 `name`이라도 `patient.name`과 `hospital.name`의 정답이 다를 수 있다. 정형 식별자의 문자열 검출과 자유서술 필드의 의미·법적 유형 판단은 별개 과제다. URL이 사진을 가리키는지만으로 사진의 내용까지 판정하지 않는다.

## 선행연구가 이미 한 일

| 근거 | 이미 구현·평가한 것 | AP-EYE에서 아직 검증할 부분 |
|---|---|---|
| [Cory·Küpper, 2026, §3·§6](https://arxiv.org/html/2605.06305) | HTTP 메시지의 정규화 → 유형 분류 → 값 추출 → 검토, 필드명·값·이웃 필드 이용, 분류체계 교체, 합성 트래픽 평가 | 평가 범위가 **요청 본문**이다. 응답 본문은 생성할 수 있지만 실제 분류 성능 평가에는 넣지 않았다. 한국어 API 응답과 국내 법 분류도 평가하지 않았다. 따라서 다단계 파이프라인 자체를 새 기여라고 주장할 수 없다. |
| [Telkamp·Hulsebos, 2025/26, §5](https://arxiv.org/html/2512.04120) | 표의 주변 문맥을 이용한 `detect-then-reflect`로 민감도 오탐을 낮춤. Qwen3 14B의 정밀도는 0.57→0.73, 재현율은 0.97→0.94. | 표 데이터 결과다. 한국어 JSON 응답, 로컬 처리 제약, 후속 수정 순위에 같은 효과가 있는지 평가하지 않았다. 숫자를 본 프로젝트 성능으로 전용하면 안 된다. |
| [Ntwali 등, 2025, §3·§5](https://arxiv.org/html/2506.22305) | 열 이름·값·다른 열·데이터셋 설명을 같이 사용한 구조화 데이터 개인정보 분류 | API 응답의 계층 구조 및 국내 법 범주는 평가 대상이 아니다. |
| [Choi 등, EACL 2026](https://aclanthology.org/2026.eacl-long.103/) | 한국어 법원 문서에서 경량 KLUEBERT-CRF가 자체 말뭉치의 엔티티 F1 0.9923 달성 | 한국어 경량 모델이 원리적으로 불가능하다는 주장은 틀리다. 다만 문서 내 엔티티 추출 결과를 API 필드 민감도 분류에 옮길 수는 없다. |
| [CAPID, EACL 2026](https://aclanthology.org/2026.eacl-srw.23/) | 문맥 의존 PII 판단을 위해 합성 데이터로 로컬 소형 모델을 미세조정 | 질문응답 입력의 비식별화 과제다. 한국어 API 응답과 수정 우선순위는 별도 문제다. |

가장 가까운 Cory·Küpper 논문의 한계는 명시적이다.

> “The present evaluation is further limited to explicitly transmitted PII values in HTTP request bodies.”
>
> → 현재 평가는 HTTP **요청 본문**에 명시적으로 실린 개인정보 값으로 제한된다.
>
> ([원문 §6.4](https://arxiv.org/html/2605.06305))

이 논문은 같은 모델로 모든 항목을 다시 검토하는 단계가 일관된 이득을 내지 못했고, 선택적·이질적 검토를 후속 방향으로 제시한다. 따라서 “같은 LLM을 두 번 부르면 오탐이 해결된다”는 가설도 약하다.

> “the review stage does not yield consistent improvements.”
>
> → 검토 단계가 일관되게 성능을 높이지는 않았다.
>
> ([원문 §6.3](https://arxiv.org/html/2605.06305))

## 검증할 연구 질문

**RQ1. 최소 문맥:** 필드명만 볼 때보다 `엔드포인트 템플릿+JSON 경로+형제 필드명`을 주면 한국어 API 응답의 비개인정보 오탐이 줄어드는가? 동적 경로의 실제 식별자와 값은 제외해야 외부 모델 입력 범위에 들며, 필드명의 의미가 모호하면 여전히 한계가 있다.

**RQ2. 로컬 값 문맥:** 위 입력만으로 부족한 필드에서, 응답 값을 진단 환경 **내부에서만 일시적으로 읽는 것**이 추가 이득을 주는가? 값은 로그·모델 외부·결과 파일에 남기지 않는다. 반대로 값 자체를 못 읽는 운영 정책이라면 자유서술의 의미 분류를 확정하지 않고 보류해야 한다.

**RQ3. 보류와 집계:** 불확실한 분류를 억지로 민감/비민감으로 확정하지 않고 보류할 때, 고위험 항목의 재현율·자동 처리율·상위 수정 대상의 정확성이 어떻게 변하는가? 보류를 성과에서 제외하지 않는다.

### 비교할 구현 경로

1. **강한 정형 기준선:** 필드 alias/CIM + 형식·체크섬 규칙 + [Presidio의 한국 식별자 인식기](https://presidio.dataprivacystack.org/supported_entities/). 주민등록번호 등에는 이미 한국 전용 규칙이 있으므로 “국내 인식기 부재”로 설명하지 않는다.
2. **결정 모델 기준선:** 현재 검토 중인 Jev/jeff/SemIf를 동일한 입력·하드웨어 조건에서 실행한다. Jev는 외부 호스티드 모델이므로 값은 주지 않고 경로/스키마만 쓴다. 일반 벤치마크 점수나 출력 확률은 이 과제의 한국어 분류 정확도·보정도를 보증하지 않는다.
3. **한국어 소형 인코더:** 정형 NER은 KoELECTRA/KLUEBERT 계열의 토큰 분류, 자유서술 필드의 의미는 문장 또는 필드 문맥 분류로 분리한다. [K-PII-Bench](https://huggingface.co/datasets/woohyun212/k-pii-bench)는 합성 한국어 문서의 학습 출발점일 뿐, API 응답 정답셋은 별도로 만들어야 한다.
4. **후보+검증:** 정형 규칙과 작은 분류기로 후보를 넓게 잡고, 애매한 사례에만 **다른 계열의 로컬 문맥 분류기** 또는 사람 검토를 적용한다. 모든 항목에 같은 모델을 반복 호출하는 방식과 비용·정밀도·재현율을 비교한다.

방법은 1→2→3→4 순서로 **실험**하고, 성능이 비슷하면 더 단순하고 빠른 방법을 채택한다. “LLM 사용”은 연구 기여가 아니다. 모델이 직접 법 조항이나 신고 의무를 선언하지 않도록, 검출된 증거 유형을 검토 가능한 국내 법 분류표에 매핑한다.

## 실험 설계

- **자료:** 자기 팀이 통제하는 API와 허가된 예제 API에서 응답을 수집한다. 원본 개인정보 대신 합성 값을 쓰고, 서비스·엔드포인트별로 템플릿을 다르게 만든다. 합성 자료만의 성능은 실제 기업 응답 일반화의 증거가 아니다. 가능하면 합법적으로 제공된 비식별 샘플로 별도 외부 검증한다.
- **정답:** 응답 필드/값마다 `비개인정보`, `일반 개인정보`, `고유식별정보`, `민감정보`, `판정 불충분`을 표기한다. 하나의 자유서술 값에 여러 유형이 있으면 다중 라벨로 남긴다. 두 평가자가 독립 판정하고 불일치를 조정한다. 민감정보의 법적 범주와 사업상 비밀·불편한 내용은 구별한다.
- **어려운 반례:** `patient.name`/`hospital.name`, 상담 이유/결제 취소 이유, 은행 계좌/서비스 계정, 공개 프로필/사적 상담, 숫자 식별자/주문 번호, 빈 값·가짜 데이터·집계 통계, 한영 혼합·오탈자. 특히 비개인정보 음성 표본을 충분히 넣어 오탐률을 잰다.
- **분할:** 같은 서비스·엔드포인트·템플릿의 필드가 학습과 시험에 동시에 들어가지 않도록 서비스 또는 엔드포인트 묶음 기준으로 나눈다. 키 이름만 바꾼 근접 복제본도 분리한다.
- **입력 절제:** A 필드명만, B 경로+메서드+형제 필드, C B+부분 마스킹된 값, D B+로컬 원문 값. A→D 성능과 개인정보 처리 범위를 함께 기록한다. B와 C만으로 충분하면 원문 접근을 줄일 수 있다.
- **측정:** 유형별 정밀도·재현율, 비개인정보 오탐률, 민감·고유식별정보 재현율, 보류율과 자동 판정 범위, 처리 지연 p95/메모리, 외부 전송 바이트와 원문 저장 여부. 실험 전에 목표치를 정하고 신뢰구간을 제시한다.
- **집계 영향:** 동일한 확인된 인가 위반 사례와 동일한 가중치 표를 고정한 뒤, 분류기별 **상위 k개 수정 대상의 오선정률과 전문가 순위와의 차이**를 비교한다. 미확정 개인정보는 0점 처리하거나 최고위험으로 단정하지 말고 점수의 하한·상한과 검토 필요 상태로 표현한다. 사람 순위도 법정 우선순위가 아닌 연구용 판정이다.

예비 목표의 예시는 “필드명 단독 기준선 대비 비개인정보 오탐률을 절반 이하로 낮추되 민감·고유식별정보 재현율 감소는 2%p 이내, 자동 처리 범위는 80% 이상”이다. **관측 결과가 아닌 사전 목표 예시**이며, 표본과 기초율을 본 후 등록해야 한다. 단순 정확도나 보류 제외 정확도만 보고하지 않는다.

## 아직 약한 점과 판단 기준

- `응답 본문 원문 미보관` 정책이 확정되지 않았다. 원문을 로컬 모델에 일시 입력할 수 있는지와 로그에서 값 대신 어떤 최소 증거를 보존할지 별도 설계가 필요하다. 원문을 저장하지 않으면 사후 재현 가능성도 낮아지므로 **합성 평가 원본**과 실제 진단 로그 정책을 구분한다.
- 예제 API가 대부분 영어 키와 명확한 정형 값이라면 한국어 문맥 가설을 검증할 수 없다. 한국어 서술과 의미가 뒤바뀌는 반례를 먼저 만들어야 한다.
- 개인정보 여부와 개인정보보호법상 민감정보 여부는 서로 다르다. 모델의 오류가 법률 매핑 오류인지, 탐지 오류인지, 점수 가중치 오류인지 분리해서 보고한다.
- 이 가설의 연구 기여 후보는 **한국어 API 응답에서 최소 문맥·선택적 검토·보류가 실제 수정 순위에 미치는 영향의 측정**이다. 문맥 분류, 로컬 소형 모델, 2단계 추출, 한국 식별자 규칙, 개인정보 점수화 그 자체는 이미 선행 연구·도구가 있다. 추가 선행연구와 실험 결과에 따라 이 후보도 폐기할 수 있다.

## 보강: 한국어가 원인인지 가를 근거와 진단 실험 (2026-09-29 추가)

위 문서는 "한국어 처리 실패가 원인"을 단정하지 않았다. 아래 두 연구는 **범용·다국어 모델이 한국어 고유 개인정보에서 약하다**는 쪽을 뒷받침한다. 동시에 9/22 실험의 실패 사례 일부는 언어가 아니라 **정보주체 문맥** 문제일 수 있다. 두 원인을 가르는 실험을 먼저 한다.

### 근거 A. 다국어 모델보다 한국어 전용 미세조정 모델이 구조화 데이터에서 낫다

> "In such cases, entities must be inferred directly from values, and languages like Japanese and Korean further complicate detection due to multi-byte characters."
>
> → 그런 경우(열 이름이 없는 구조화 데이터) 개체를 값에서 직접 추론해야 하고, 일본어·한국어는 멀티바이트 문자 때문에 **탐지가 더 어려워진다**.

> "Experimental results show that monolingual fine-tuned models significantly outperform both RegEx and multilingual models, achieving over 92 % accuracy across languages."
>
> → 실험 결과 **단일 언어로 미세조정한 모델이 정규식과 다국어 모델을 모두 크게 앞섰고**, 언어 전반에서 92% 이상의 정확도를 냈다.
>
> (Singh, Watanabe, Kashalikar, *Comprehensive Evaluation of Transformer Models for Multilingual PII Detection*, IEEE BigData Congress 2025, 초록. DOI 10.1109/BigData66926.2025.11400885)

- 한국어 모델은 KLUE-BERT다. 우리처럼 **구조화된 데이터**를 다룬 점이 가깝다.
- 한계: 합성 데이터이고, API 응답의 JSON 계층이나 국내 법 분류는 다루지 않았다. 초록만 확인했고 본문은 아직 못 읽었다(원문 PDF 미확보).

### 근거 B. 모델들은 보편적 개인정보보다 한국 고유 개인정보를 못 잡는다

> "most of them were significantly better at recognizing universal PII than language-specific PII, which indicates a prospective direction of expanding training data for implementing Korean-specific PII deidentification"
>
> → 대부분의 모델이 **언어별 고유 개인정보보다 보편적 개인정보를 훨씬 잘 인식했고**, 이는 한국 고유 개인정보 비식별화를 위해 학습 데이터를 늘리는 방향을 시사한다.
>
> (Li Fei 외, *KDPII: A New Korean Dialogic Dataset for the Deidentification of Personally Identifiable Information*, IEEE Access 2024, 초록. DOI 10.1109/ACCESS.2024.3461804)

- 대화 텍스트 데이터셋(KDPII)이다. API 필드와 형태가 다르지만 한국어 개인정보 유형 체계를 가져다 쓸 수 있다.
- 한국어 개인정보 개체명 인식(33개 태그, BERT·ELECTRA)도 있다: *The Development of a Named Entity Recognizer for Detecting Personal Information Using a Korean Pretrained Language Model*, Applied Sciences 2024, DOI 10.3390/app14135682.

### 원인 가르기: 언어 문제인가, 문맥 문제인가

9/22 실험(양유상, 공유된 대화 기준, 원본 파일은 vault에 없음)의 관찰:
- 문맥 대조쌍 14쌍 중 8쌍만 양쪽 다 맞힘. 예: "본인 천식 진단"과 "일반 천식 안내"를 둘 다 건강정보로 분류
- 선택지 점수 90% 이상인데 틀린 사례 12건

"본인 진단 vs 일반 안내"는 **말을 못 알아들은 것이 아니라 정보주체(특정 개인인가)를 판단하지 못한 것**일 수 있다. 영어였어도 같은 실수를 했을 수 있다. 원인이 다르면 해법도 다르다.

| 원인 | 해법 |
|---|---|
| 한국어 이해 부족 | 한국어 전용 모델로 교체, 한국어 데이터로 미세조정 (근거 A, B) |
| 정보주체 문맥 부족 | 형제 필드·엔드포인트 문맥 추가 (위 RQ1·RQ2), 2512.04120의 detect-then-reflect |
| 라벨 자체의 모호함 | 판정 보류 (위 RQ3) |

**진단 실험 (싸고 먼저 할 것)**: 9/22의 96개 사례를 영어로 번역해 같은 모델·같은 조건으로 다시 돌린다.
- 영어 정확도가 크게 오르면 → 한국어 이해가 주원인. 한국어 모델·미세조정 방향
- 영어도 비슷하게 틀리면 → 문맥 문제. 문맥 추가·보류 방향
- 틀린 사례를 원인별로 분류해 비율을 낸다

반나절이면 된다. 이 결과가 나오기 전에는 "한국어를 못 알아들어서 오탐이 높다"를 발표에서 단정하지 않는다.

### 비교에 넣을 모델 후보

| 계열 | 후보 | 이유 |
|---|---|---|
| 한국어 전용 인코더 + 미세조정 | KLUE-BERT, KoELECTRA | 근거 A에서 다국어 모델보다 우수. CPU에서도 빠르다 |
