## For future Claude

[개인정보 분류 오류의 순위 영향](%EA%B0%9C%EC%9D%B8%EC%A0%95%EB%B3%B4%20%EB%B6%84%EB%A5%98%20%EC%98%A4%EB%A5%98%EC%9D%98%20%EC%88%9C%EC%9C%84%20%EC%98%81%ED%96%A5.md)을 출발점으로 개인정보 집계의 전제 20개, 연구 후보 7개, 기존 질문 25개를 조사했다. 핵심 추천은 같은 검토 비용에서 순위에 영향을 주는 분류부터 재검토하는 방법을 실증하는 것이다.
법 분류에 숫자를 붙이기, 문맥 분류, 위험도 점수화, 그래프 결합, 보류 자체는 이미 선행한다. 실제 한국어 모델 성능과 제안 검토 방법의 개선 효과는 아직 측정하지 않았으며, 합성 반례와 문헌 근거를 그 결과로 대신하지 않는다.

# 개인정보 집계 연구 총정리

## 1. 결론부터

**‘한국어를 잘 못해서 오탐이 많다’는 한 가지 설명으로는 부족하다.** 언어, 입력 문맥, 정보주체 연결, 법적 라벨, 중복 집계, 가중치, 검토 방식 중 어디서 실패하는지 먼저 나눠야 한다.

현재 가장 좋은 연구 후보는 다음과 같다.

> **한국어 API 응답의 개인정보 분류에서, 수정 대상 선택을 바꿀 수 있는 항목을 우선 재검토하면 같은 검토 예산으로 불확실성만 기준으로 고른 재검토보다 상위 수정 대상의 선택 손실을 줄일 수 있는가?**

이는 아직 입증되지 않은 가설이다. 입력 오류가 순위에 미치는 영향을 재는 기존 질문은 이 가설의 **문제 확인 실험**으로 유지한다. 순위가 안정되는 보편적 오탐률 하나를 구한다는 목표는 철회한다.

다른 후보도 남긴다. ‘정보주체별 중복 제거’, ‘불확실한 순위의 보류’, ‘최소 문맥을 통한 한국어 분류’는 별도의 질문이다. 이들을 모두 새로운 알고리즘으로 만들기보다, 한 가설을 평가할 수 있게 기반 집계를 먼저 올바르게 구현한다.

인가 연구의 최종 주제를 자동으로 교체하는 제안은 아니다. [교수 요구사항 총정리](../plan/%EA%B5%90%EC%88%98%20%EC%9A%94%EA%B5%AC%EC%82%AC%ED%95%AD%20%EC%B4%9D%EC%A0%95%EB%A6%AC.md)와 현재 인가 가설을 유지한 채 **4단계 Privacy Scorer의 병렬 후보**로 비교한다.

## 2. 왜 기존 설명을 좁혀야 하나

[개인정보 집계 선행연구 대조표](%EA%B0%9C%EC%9D%B8%EC%A0%95%EB%B3%B4%20%EC%A7%91%EA%B3%84%20%EC%84%A0%ED%96%89%EC%97%B0%EA%B5%AC%20%EB%8C%80%EC%A1%B0%ED%91%9C.md)에 원문·확인 수준·한계를 모았다. 특히 다음 선행연구를 빼면 연구 갭을 잘못 잡는다.

| 기존에 하기 쉬운 주장 | 이번 확인 후 쓸 수 있는 주장 |
|---|---|
| 개인정보 분류 연구는 F1에서 끝난다 | 일부 HTTP·표 분류 연구는 수정 순위를 평가하지 않았다. 점수와 연결한 다른 연구는 이미 있다 |
| 취약점과 PII를 결합한 점수화가 없다 | [PII-aware pentest 연구](https://www.ijsr.net/archive/v15i5/SR26430035842.pdf)가 존재한다 |
| 분류 오류가 위험 점수를 바꾸는지 아무도 안 봤다 | [라트비아 하이브리드 연구](https://www.mdpi.com/1999-5903/18/7/354)는 미검출 때문에 점수가 낮아진 사례를 설명한다 |
| 민감도 라벨을 오류 주입하는 것만으로 새롭다 | [DS-GNN의 §5.1](https://link.springer.com/article/10.1007/s44163-026-02198-9)이 바로 그 후속 실험을 제안한다 |
| 필드들을 그래프로 연결하면 새롭다 | [SRP-Net](https://www.nature.com/articles/s41598-026-53482-8?error=cookies_not_supported)과 [Identity Ecosystem 연구](https://arxiv.org/html/2508.04542)가 있다 |
| 한국어니까 대형 LLM만 가능하다 | [K-LegalDeID](https://aclanthology.org/2026.eacl-long.103/) 등 한국어 경량 모델 사례가 있다. API 전이는 별도 평가해야 한다 |
| F1 대신 순위를 보는 발상 자체가 새롭다 | [Smart Predict, then Optimize](https://arxiv.org/html/1710.08005) 등 의사결정 중심 예측 평가가 선행한다 |

우리가 아직 확인하지 못한 조합은 **한국어 API의 실제 분류 오류, 중복 없는 노출 단위, 수정 대상 선택, 제한된 검토 비용을 함께 평가한 실증**이다. 이 조합의 자료를 이번 범위에서 찾지 못했다는 뜻이며, 조합이 다르다는 사실만으로 학술적 기여가 생기는 것은 아니다. 강한 기준선보다 낫다는 결과 또는 재현 가능한 새로운 실패 분석이 필요하다.

## 3. 아키텍처에서 무엇을 집계하는가

현재 [ARCHITECTURE](../../arch/2026-09-29%20%EA%B2%8C%EC%9D%B4%ED%8A%B8%EC%9B%A8%EC%9D%B4%20%EC%95%84%ED%82%A4%ED%85%8D%EC%B2%98.md) 5.4는 정규화한 필드를 개인정보 유형으로 분류하고 점수로 합친다. 연구용으로는 그 사이에 빠진 의미를 명시해야 한다.

```mermaid
flowchart LR
    A[확인된 인가 위반 응답] --> B[필드와 실제 값의 증거]
    B --> C[개인정보 유형과 정보주체]
    C --> D[중복 없는 노출 사실 집합]
    D --> E[명시한 가중치와 불확실성]
    E --> F[수정 후보와 검토 필요 항목]
```

이것은 **연구 평가용 분해 제안**이며 현재 구현됐다는 표시가 아니다. 비공개인지 모르는 응답은 인가 위반으로 확정하지 않는다. 정상 응답의 PII 인벤토리는 만들 수 있지만 ‘확인된 유출’ 집계와 섞지 않는다.

같은 사건을 적어도 다음 여섯 단위로 분리한다.

| 단위 | 뜻 | 서로 바꿔 쓰면 생기는 문제 |
|---|---|---|
| 요청·응답 수 | 수집한 메시지 횟수 | 재전송 100회를 피해자 100명으로 오해 |
| 레코드 수 | 반환된 주문·상담·게시물 등 객체 수 | 한 사람의 상담 10건과 사람 10명을 혼동 |
| 필드 등장 수 | JSON 값·엔티티가 나타난 횟수 | 중첩 필드와 반복 페이지 때문에 위험이 부풀음 |
| 고유 노출 사실 | 특정 주체의 특정 속성·값·시점에 관한 구별 가능한 사실 | 같은 이메일 반복과 서로 다른 진료 사실을 같은 중복으로 처리 |
| 정보주체 수 | 서로 다른 사람 수, 또는 확인 가능한 주체 식별자 수 | 사용자 계정·가족·공용 계정·동명이인을 동일시 |
| 수정 대상 | 엔드포인트 또는 확인된 공통 원인 | 하나의 수정으로 여러 API가 해결되는데 중복 비용을 계산 |

출력은 ‘고유 주체 17명’처럼 확정하기 전에 그 주체가 **실제 사람인지, 확인된 계정인지, 추정 클러스터인지** 표시해야 한다. 부분 트래픽에서 얻은 수는 관측 범위의 수이지 전체 피해 규모 추정치가 아니다.

아래의 ‘검증’은 모두 필요한 점검 항목이다. 모두를 논문의 기여로 내세우지는 않는다.

| A07 | 모든 값은 응답 소유자에 관한 것이다 | 환자 메모에 어머니의 병력, 주문의 수령인과 구매자 | 정보주체 관계 주석과 불확실 연결 보류 |

| A10 | 같은 문자열이면 같은 사람이다 | 가족 공용 전화·주소, 동명이인 | 검증된 주체 키 우선. 값 일치만으로 합치지 않음 |
| A11 | 서로 다른 키이면 다른 정보다 | `email`과 `contact.email`에 같은 사실 | 경로·주체·속성 관계를 고려한 중복 제거. 새 시점의 다른 사실은 보존 |
| A12 | 데이터 유형 점수를 더하면 실제 피해다 | 주민번호 한 개와 일반 속성 여러 개 중 우선순위 | 점수는 명시한 효용 모형. 실제 피해액·법정 등급과 구별 |
| A13 | 민감10·고유식별5는 법에서 정한 비율이다 | 법에 그런 기수적 비율이 없음 | 가중치 여러 조건·전문가 판단과의 일치·우선순위 안정성을 따로 검증 |
| A14 | 분류 정확도나 FPR 하나면 순위 신뢰성을 안다 | 똑같은 혼동행렬인데 오류 위치가 달라 1위가 바뀜 | 엔드포인트별 오류 집중, 점수 간격, 상위 선택 손실 측정 |
| A15 | 모델 확률은 실제 정답 확률이다 | 0.9 이상 확신한 오답 | 보정용 검증셋, 신뢰도 도표·Brier·유형별 보정, 이동 환경 재점검 |
| A16 | 분류 오류는 독립적이다 | 잘못된 CIM 별칭 하나가 수백 필드로 전파 | 서비스·스키마·개체 유형에 묶인 상관 오류 실험 |
| A17 | 보류 항목을 버리면 성능이 좋아진 것이다 | 어려운 민감 사례를 전부 보류 | 보류율·자동 처리 범위·전체 미탐·검토 비용을 함께 보고 |
| A18 | 항목별로 안전하면 결합해도 안전하다 | 시간·위치·직무 조합이 특정인을 좁힘 | 동일인 연결과 추가 지식을 명시한 별도 결합 위험 실험 |
| A19 | 엔드포인트 순위가 실제 수정 효과 순위다 | 공통 미들웨어 한 번 수정으로 여러 API 해결 | 초기에는 동일 수정 비용 가정. 공통 원인·비용이 확인될 때만 조치 단위 평가 |
| A20 | 수집 누락·스키마 변화·보관 정책은 점수와 무관하다 | 사진은 URL만, 과거 페이지 누락, 필드 의미 변경 | 관측 범위·모델/규칙/법령 버전·미확인 내용 표시, 장기 동일 수치로 오해하지 않기 |

**해시나 HMAC은 A10을 해결하지 않는다.** 동일한 입력을 비교하는 수단일 뿐 사람의 동일성을 증명하지 않는다. HMAC 키 유출·연결 가능성·정규화 오류도 남는다. 이를 썼다고 익명정보가 되는 것도 아니다.

**엔트로피 역시 실제 피해의 정답은 아니다.** 유형 다양성이 높다는 것과 높은 피해는 다르며, 단 하나의 심각한 사실은 다양성이 낮아도 중요할 수 있다. P08의 엔트로피를 가져올 때 이 목적을 고정해야 한다.

## 5. 어느 가설에 시간을 쓸 것인가

### H1. 분류 오류의 위치와 점수 간격이 선택 손실을 설명한다

**한 줄:** 전체 F1이 같아도 오류가 일부 엔드포인트에 몰리거나 상위 점수 간격이 작으면 수정 대상 선택 손실이 커지는가?

- 근거: 기존 파일의 합성 시연, P06의 정확한 민감도 라벨 가정, M01의 의사결정 중심 평가.
- 이번 확인: 같은 혼동행렬인데 결과가 다른 결정적 반례와 합성 비교를 실행했다. [개인정보 분류 오류의 순위 영향](%EA%B0%9C%EC%9D%B8%EC%A0%95%EB%B3%B4%20%EB%B6%84%EB%A5%98%20%EC%98%A4%EB%A5%98%EC%9D%98%20%EC%88%9C%EC%9C%84%20%EC%98%81%ED%96%A5.md)에 수치·코드가 있다.
- 반박: 합성 노이즈를 넣으면 순위가 바뀌는 것은 자명할 수 있다. 실제 모델도 같은 방식으로 틀리는지 확인해야 한다.
- 역할: **문제 확인 실험**으로 채택. 이것만으로 새로운 해결책이라고 주장하지 않는다.
- 폐기 조건: 실제 모델의 오류가 거의 없거나, 관측된 선택 손실이 없으면 이 문제를 프로젝트의 중심으로 키우지 않는다.

### H2. 불확실성보다 ‘선택을 바꿀 가능성’을 보고 검토한다

**한 줄:** 같은 시간 또는 검토 건수에서 순위 변화 가능성과 영향 크기로 항목을 골라 재검토하면 낮은 확신도 순 검토보다 상위 수정 대상의 선택 손실이 줄어드는가?

- 직관: 20위와 21위 사이의 모호한 이름보다 5위와 6위를 뒤바꾸는 건강정보 판단이 오늘 고칠 5개를 바꾼다.
- 기준선: 검토 없음, 무작위, 확신도 낮은 순, 최대 잠재 민감도 순, 제안 방식. 보정 여부와 검토자 능력을 동일하게 맞춘다.
- 방법 후보: 불확실한 라벨을 가능한 다른 값으로 바꿔 보며 top-k 선택이 달라지는지 계산하고, 달라질 때의 손실 대용값을 검토 비용으로 나눈다.
- 반박: 확신도 자체가 틀리면 대상을 놓친다. 여러 오류가 함께 작용하면 한 필드씩 바꾸는 방식도 놓친다. 한 스키마 수정이 여러 항목을 고치면 단위 비용이 달라진다.
- 검증: 실제 로컬 모델 출력과 독립 정답, 동일 예산의 개선 곡선. 사람 또는 이질적인 모델의 재검토 오답도 별도 측정한다.
- **추천:** 현재 가장 구체적인 방법 비교 후보다. ‘새로운 value-of-information 이론’이 아니라 이 문제에 맞춘 선택 규칙과 실증으로 기여를 제한한다.
- 폐기 조건: 확신도 순 검토보다 이득이 없거나 순위 재계산 비용이 이득을 상쇄하면 더 단순한 기준선을 채택한다.

### H3. 불확실한 순위를 억지로 확정하지 않는다

**한 줄:** 유형·주체·가중치의 불확실성을 점수 구간으로 남기면 동일한 자동 확정 범위에서 잘못된 고위험 우선순위 확정이 줄어드는가?

- 방법 후보: 모든 가능한 점수에서 i가 j보다 큰 경우만 확정하고 나머지는 공동 우선 검토군으로 표시한다.
- 근거: M02·M04·M06, P05의 가중치 민감도 분석. 구간과 보류는 선행 방법이다.
- 반박: 구간을 넓혀 아무것도 말하지 않으면 오류는 0이 된다. 가중치 범위 자체가 임의면 구간도 임의다.
- 검증: 확정 비교쌍 오류율과 확정 비율, top-k 가능한 집합 크기, 검토 비용. 구간 포함률도 따로 평가한다.
- 역할: H2의 출력 방식 후보. 초기부터 conformal 보장을 붙일 필요는 없다.

### H4. 중복을 제거하면서 새로운 노출은 보존한다

**한 줄:** 주체·속성·값·시점을 구분한 집계는 메시지나 필드 수 합산보다 재전송·페이지 중첩에 의한 순위 변동을 줄이고 새로운 사람·사실의 노출에는 반응하는가?

- 반례: 같은 상담 내용 50회와 서로 다른 사람 50명의 상담은 달라야 한다. 한 사람의 서로 다른 상담 50건도 전부 하나로 지우면 안 된다.
- 기준선: 필드 등장 수, 고유 문자열 수, 고유 유형 수, 확인된 주체와 사실 기반 집합.
- 평가: 재전송 불변성, 잘못 합침·잘못 분리함, 고유 사실 수 오차, 합성 정답 기준 주체 수 오차.
- 반박: 중복 제거는 통상적인 데이터 처리다. 이것만으로 신규 연구라고 하기 어렵고, 올바른 주체 키가 없으면 관측만으로 풀 수 없다.
- 역할: **필수 집계 정확성 요건**. 원문을 보관하지 않는 제약 아래의 정확성·비용 절충까지 입증하면 독립 연구 후보로 검토한다.

### H5. 한국어 자체보다 정보주체 문맥이 오류를 설명할 수 있다

**한 줄:** 언어를 통제한 상태에서 정보주체·필드 관계 문맥을 추가하는 것이 단순 모델 크기 증가보다 민감정보 오탐과 선택 손실을 더 줄이는가?

- 설계: 한국어/영어 × 문맥 없음/있음. 번역 전후 의미와 명시성을 사람이 확인한다. 모델 크기 비교는 별도 요인이다.
- 근거: P01~P03의 문맥 활용, K01~K05의 경량·한국어 연구.
- 반박: 번역은 문장을 더 명료하게 만들 수 있으므로 영어 성능 상승만으로 한국어가 원인이라고 결론 내릴 수 없다.
- 역할: H2에 사용할 분류기를 고르는 **원인 진단**. 순수 언어 효과가 크면 한국어 인코더 미세조정·대조 학습을 검토한다.
- 폐기 조건: 문맥 추가가 지연·원문 접근만 늘리고 보류 포함 성과를 높이지 못하면 필수 입력으로 채택하지 않는다.

### H6. 개별 항목보다 결합 노출의 위험이 크다

**한 줄:** 같은 사람의 여러 API에 분산된 사실을 연결한 평가가 개별 엔드포인트 가중합보다 추가 식별·추론 성공을 더 잘 설명하는가?

- 근거: P09의 속성 관계 위험도, P10의 정보주체 수준 평가, 국내 G05. 그래프·조합 자체는 이미 선행한다.
- 요구 입력: 확인 가능한 동일인 관계, 공격자가 가진 추가 지식, 평가할 추론 과제와 정답.
- 반박: 관계를 잘못 합치면 존재하지 않는 고위험 인물을 만든다. 많이 연결할수록 위험하다고 자기 점수로 평가하면 순환한다.
- 판단: 가치 있지만 현 학기 범위를 크게 늘린다. **확장 후보**로 남기고 단순 엔트로피나 그래프 점수를 실제 재식별 확률로 부르지 않는다.

### H7. 엔드포인트보다 공통 수정 원인을 고른다

**한 줄:** 동일한 수정 시간에서 공통 원인과 노출 중복을 고려한 조치 선택이 엔드포인트 독립 순위보다 더 많은 고유 노출 사실을 차단하는가?

- 근거: P06도 복수 조치의 결합을 미해결 범위로 둔다. 자원 배분·집합 커버라는 기존 최적화 문제와 가깝다.
- 필요 입력: 실제 공통 취약 코드·설정 연결과 수정 비용. 트래픽만으로 자동 확보된다고 가정하지 않는다.
- 검증: 통제된 API에서 수정 전후 확인된 고유 노출 감소를 측정한다. 비용 추정이 없으면 동일 비용 조건에 한정한다.
- 판단: **현재는 보류**. 인가 진단과 분류 검증부터 끝낸 뒤 시스템 확장 때 검토한다.

## 6. 모델은 어떤 순서로 비교하나

1. **형식 규칙+CIM 기준선:** 정규식·체크섬·한국 식별자 인식기를 먼저 둔다. 반례와 언어별 포맷을 포함하고 형식 일치만으로 실제 사람의 정보임을 확정하지 않는다.
2. **작은 지도학습 기준선:** 문자 n-gram/TF-IDF+로지스틱 회귀 또는 선형 SVM을 같은 분할에서 비교한다. 숫자 패턴과 흔한 문구를 충분히 해결하면 복잡한 모델의 명분이 줄어든다.
3. **한국어 인코더:** KLUEBERT·KoELECTRA 계열의 토큰 분류와 문장/필드 의미 분류를 구별한다. NER 헤드의 이름 검출 성능으로 건강정보 맥락 판단을 대체하지 않는다.
4. **현재 로컬 결정 모델:** jeff/SemIf의 실제 실행 버전을 고정한다. 기존 Jev 검토를 재사용하되 호스티드 Jev로 원문을 보내는 비교는 하지 않는다.
5. **기성 로컬 개인정보 모델:** 공식 [privacy-filter](https://huggingface.co/openai/privacy-filter)도 후보가 된다. 출력 8유형이 국내 법 범주와 다르므로 그대로 완성 분류기로 쓰지 않는다.
6. **선택적 재검토·미세조정:** 앞 단계의 오류 분포를 본 뒤 H2와 한국어 대조 사례 학습을 평가한다. 새 모델을 무작정 더 늘리지 않는다.

RAG는 법령·라벨 정의·검수한 예시를 참조하게 할 수 있다. 입력에 없는 정보주체 관계를 만들어 주지는 않는다. RAG, LoRA, 지식 증류, 대조 학습, 비용 민감 학습 중 무엇을 쓸지는 **같은 실패 사례를 해결하는지**로 선택한다. 다수결도 모델들이 같은 오류를 내면 소용없다.

모든 점수·지연·메모리·한국어 성능은 AP-EYE 시험셋에서 다시 측정한다. 모델 카드의 일반 벤치마크 수치는 이 프로젝트의 결과가 아니다.

| 18. 원문을 외부 LLM에 줘야 하나? | 아니다. 현재 설계 원칙에 맞춰 내부에서만 처리한다. 필드명·동적 URL도 개인정보를 담을 수 있어 정규화 범위를 검증한다 |
| 19. 보안 게이트웨이가 더 위험해지지 않나? | 토큰·원문 집중, 로그 잔존, 관리 API, LLM 입력 공격을 별도 통제·측정한다. Scorer를 운영 차단 경로에 넣을 필요는 없다 |
| 20. 원문을 안 남기면 재현은? | 합성 연구 원본은 버전 고정해 보존한다. 운영 증거는 최소 메타데이터·제한된 증거 참조와 보존기간을 따로 정한다. 완전 재현과 최소 보관 사이의 절충을 기록한다 |
| 21. 이미지 URL은 민감 사진이라고 세나? | URL만으로 내용은 알 수 없다. 사진 내용은 미확인으로 남긴다. OCR/VLM은 추가 수집 권한과 별도 평가가 필요한 확장이다 |
| 22. 애매한 것을 빼면 오탐이 줄지 않나? | 제외한 수와 고위험 미탐까지 공개해야 한다. 전부 보류한 시스템은 성공으로 평가하지 않는다 |
| 23. 합성 데이터로 논문이 되나? | 통제 실험은 가능하다. 합성만으로 실제 회사에 일반화됐다고 쓰면 안 된다. 템플릿·서비스 분리와 외부 자료 검증을 별도로 설계한다 |
| 24. SI 프로젝트와 무엇이 다른가? | 기능 통합 외에 반증 가능한 H2, 강한 기준선, 독립 정답, 비용을 맞춘 비교, 실패 조건을 갖춘다. 결과가 없으면 연구 기여는 아직 후보다 |
| 25. 중간·최종 발표에 무엇을 내나? | 중간에는 기존 실험 재현·오류 원인·조건별 선택 손실, 최종에는 검토 예산별 기준선 대비 개선·신뢰구간·미탐·처리 범위·비용을 제시한다 |

법률 부분은 [법적 근거](../plan/%EB%B2%95%EC%A0%81%20%EA%B7%BC%EA%B1%B0.md)와 원문 확인을 위한 연구 설계상의 경계다. 사건별 자동 법률 판단 기능의 완성을 뜻하지 않는다.

## 8. 교수에게 제안할 한 문단

> 개인정보 분류와 위험도 점수화는 이미 선행연구가 있어서 그 자체를 새 기여로 잡지는 않았습니다. 최근 유출 경로 순위화 연구도 민감도 라벨이 정확하다는 가정을 두고 있어, 저희는 한국어 API 응답의 실제 분류 오류가 수정 대상 선택에 미치는 영향을 먼저 측정하려고 합니다. 이어서 같은 검토 비용에서 단순히 확신도가 낮은 항목을 보는 방법과, 수정 순위를 바꿀 수 있는 항목을 먼저 보는 방법을 비교하겠습니다. 중복 집계와 가중치 영향을 분리하고 상위 수정 대상의 선택 손실, 고위험 미탐, 검토 시간으로 평가하겠습니다.

‘해결했다’가 아니라 ‘무엇을 비교해 입증하겠다’는 단계의 설명이다.
