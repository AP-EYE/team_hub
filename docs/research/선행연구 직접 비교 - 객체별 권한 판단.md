# 선행연구 직접 비교: 객체별 권한 판단

## 2026-10-02 보강: 같은 객체 사례에 판정 절차 대입

아래는 논문 원문 절차를 조건에 대입한 분석표다. 실제 도구 실행 결과가 아니다.
이 절의 해석과 [BOLA 판정 연구 구체화](BOLA%20%ED%8C%90%EC%A0%95%20%EC%97%B0%EA%B5%AC%20%EA%B5%AC%EC%B2%B4%ED%99%94.md)가 아래 9/30 조사에서 충돌하는 문장보다 우선한다.
특히 블랙박스 전체가 HTTP 성공만으로 판정한다는 표현, BACScan이 공유를 처리하지 못한다는 표현은 철회한다.

### 비교에 쓰는 조건

A는 객체 생성자, B는 로그인한 다른 계정이다.
“공통 관찰”은 BACScan에서는 두 탐색에 URL·내용이 같은 페이지가 있고, AuthProbe에서는 객체 ID가 두 목록에 모두 있다는 뜻이다.
각 방법의 관찰 단위는 다르므로 조건을 따로 제공해야 한다.
BACScan의 위반 보고 조건은 제외되지 않은 대상 페이지의 재요청 응답 유사도가 0.7을 넘는 경우로 고정한다.
AuthProbe는 §V-B Algorithm 2의 객체 간 교차 조회만 비교한다. 비로그인·열거 탐지 등 다른 검사 결과는 섞지 않는다.

### 원문 근거와 해석 범위

- BACScan §4는 공통 탐색의 URL·내용으로 공개를 거르고, 나머지 GET 재실행의 유사도로 읽기 위반을 판정한다. 위 표의 관찰 누락 오탐·공통 누출 미탐은 이 절차에서 도출한 조건부 추론이다. 논문이 같은 사례의 오류를 실측했다고 말하지 않는다. [저자 원문](https://seclab.cse.cuhk.edu.hk/papers/ccs25-BACScan.pdf)
- AuthScope §4.3은 응답을 정렬·비교해 후보를 찾은 다음 비로그인 앱 실행으로 공개 자원 인터페이스를 제거한다. 로그인 공개·선택 공유에서 비로그인 필터가 도움을 주지 못한다는 것과 최종적으로 항상 오탐한다는 것은 다르다. [저자 원문](https://bruceqczhao.github.io/assets/ccs17/CCS17.pdf)
- AuthProbe §III는 목록에 나타난 객체를 읽기 자격으로 정의하고 §V-B Algorithm 2는 A 목록에는 있지만 B 목록에는 없는 객체를 B로 조회한다. 목록이 의도한 권한의 완전한 표현인지가 위 사례의 전제다. [원문](https://arxiv.org/html/2607.20574)

### 부족한 점에서 개선안으로 연결

| 비교로 드러난 전제 | 개선안 | 반드시 확인할 반증 조건 |
|---|---|---|
| 허용된 객체가 두 관찰에 나타나야 공개·공유로 걸러짐 | 객체 생성·공유 설정을 별도 근거로 기록 | B 탐색·목록을 정상적으로 완성하면 기존 방법도 정확한가? |
| 잘못 공개된 응답·목록을 권한 근거로 사용하면 의도와 관찰이 혼동될 수 있음 | 요청 성공과 독립된 금지 설정을 보존 | 설정 자체가 틀렸거나 오래됐을 때 제안 방법이 오탐하지 않는가? |
| 관찰 기반 방법은 적은 사전 입력을 쓰는 장점이 있음 | 입력 비용과 성능을 함께 평가 | 제안 방법의 입력 비용이 모든 평가 객체를 직접 라벨링하는 비용과 같은가? |
| 테스트 객체 밖에는 독립 근거가 없음 | 보류와 적용 범위 제한을 공개 | 실제 위반을 보류해서 재현율이 낮아지는가? |

개선의 핵심은 “공개·공유를 처음 처리한다”가 아니라 관찰한 허용과 의도한 허용을 구분할 설정 근거를 추가하는 것이다.
그러나 이것만으로 새 연구라고 확정할 수 없다. 객체별 수동 권한 입력과 같은 작업이라면 추가 기여가 부족하다.
다음 실험은 같은 객체·요청 집합의 정상 허용 관찰 누락과 실제 금지 객체 누출을 함께 평가하고, 추가 설정 시간이 성능 개선에 비해 어떤 비용인지 확인한다.

## 비교 질문

> **공개·비공개·공유 객체가 섞여 있을 때, 기존 도구와 논문은 객체 하나하나의 접근 허용 여부를 어떻게 판단하는가?**

## 한눈에 보기

- **기대 권한의 출처는 셋으로 갈린다.** 사람이 정책을 적거나(ZAP, AuthMatrix, IDORacle), 소스 코드에서 뽑거나(BolaZ, IDORacle), 관찰한 응답에서 추정한다(AuthProbe, EvoMaster, 2607.16754).
- **공개·그룹·테넌트·관리자를 명시적으로 처리하는 연구는 소스 접근이 필요하다**(IDORacle, BolaZ). 소스 없는 연구는 이를 오탐 원인으로 지적하거나(EvoMaster), 페이지 단위로만 거르거나(BACScan), 범위 밖으로 뺀다(BACFuzz).
- **블랙박스의 기본 판정은 "다른 계정으로 접근에 성공했다"이다**(ICST'20, BACScan 읽기, AuthProbe). 이 규칙이 공유·관리자 사례에서 오탐한다는 것은 EvoMaster가 직접 밝혔다.
- **"판단 근거가 없다"를 출력하는 것은 도구 화면과 IDORacle뿐이다.** ZAP의 Unknown, Autorize의 "Is enforced???", IDORacle의 Audit 결정이다. 읽은 논문 9편의 평가에서 보류율이나 판정 불가 비율을 지표로 보고한 것은 찾지 못했다.
- **우리 자리는 블랙박스 + 객체 단위 라벨 확보 + 보류 지표다.** 이 조합은 이번 조사에서 찾지 못했다. 구체적인 개선안 6개는 아래 "무엇을 개선할 수 있나"에 있다.

## 비교 기준

- **기대 권한 출처**: 이 계정이 이 객체를 봐도 되는지의 정답을 어디서 얻는가
- **공개·공유·관리자**: 이 세 경우를 어떻게 다루는가
- **근거 없을 때**: 정답을 알 수 없는 객체에서 무엇을 출력하는가
- **필요 입력**: 소스, 명세, 사람의 입력 중 무엇이 필요한가

| BolaZ | 소스의 데이터 흐름(P-API가 반환한 ID) | 관리자 API 제외. 공유는 데이터 흐름으로 | 판별 불가 사례를 한계로 서술 | 소스 코드 |
| IDORacle | 테이블별 정책 메타데이터 | 공개·그룹·테넌트·관리자를 등록해 처리 | Allow / Rewrite / Block / Audit | 소스·JDBC 계측, 정책 |
| BACScout (초록만) | 프런트엔드 관찰 + 외부 효과 오라클 | 초록에 언급 없음 | 오라클이 없으면 발견으로 안 침 | 본문 미확인 |

## 논문별 근거

### 패턴 1. 사람이 권한을 적는다

- **ZAP: 접근 규칙을 사람이 정한다**
  > "In order to identify potential access control issues, ZAP needs to know which parts of the web application are supposed to be accessed by which user."
  >
  > → 잠재적인 접근 제어 문제를 찾으려면, ZAP은 웹 애플리케이션의 어느 부분에 어느 사용자가 접근해야 하는지 알아야 한다.
  >
  > (ZAP Access Control Testing 문서, Access Rules)

- **규칙에는 "정보 없음" 값이 있고, 규칙 단위는 페이지다**
  > "Unknown - there is no information regarding whether the resource should or shouldn't be accessible to the User to which the rule refers"
  >
  > → Unknown: 이 리소스가 해당 사용자에게 접근 가능해야 하는지에 대한 정보가 없다.
  >
  > (ZAP 문서, Access Rules)
  - 규칙은 사용자별로 각 Site Node(웹 페이지)에 붙는다. 객체 인스턴스 단위 규칙은 문서에서 찾지 못했다.
  - 결과 탭은 규칙을 따랐는지(성공)와 아닌지(실패)로 표시한다. Unknown 규칙이 결과에서 어떻게 나오는지는 문서에서 확인하지 못했다.

- **AuthMatrix: 요청마다 허용 역할을 사람이 체크한다**
  > "In the Request Table of AuthMatrix, select the checkboxes for all roles that are authorized to make each HTTP request."
  >
  > → AuthMatrix의 요청 표에서, 각 HTTP 요청을 보낼 권한이 있는 모든 역할의 체크박스를 선택한다.
  >
  > (AuthMatrix README)
  - 사용자별 단일 사용자 역할을 자동으로 만들어 교차 사용자 자원 테스트를 돕는다. 공개·공유 객체 설명은 README에 없다.

- **Autorize: 판별 패턴을 사용자가 정하고, 확신 불가 상태를 낸다**
  > "Autorize could not reliably determine enforcement and requires manual fingerprint configuration."
  >
  > → Autorize가 강제 여부를 신뢰성 있게 판단하지 못했으며, 수동으로 fingerprint 설정이 필요하다.
  >
  > (Autorize README, "Is enforced???" 상태)

  > "false positives or false negatives are possible."
  >
  > → 오탐이나 미탐이 있을 수 있다.
  >
  > (Autorize README, 한계)

### 패턴 2. 다른 계정 접근 성공을 위반으로 본다

- **ICST'20: 고정 규칙이다**
  > "User-namespace rule. A resource created in a user namespace must not be accessible from another user namespace."
  >
  > → 사용자 네임스페이스 규칙. 한 사용자 네임스페이스에서 만든 리소스는 다른 사용자 네임스페이스에서 접근할 수 없어야 한다.
  >
  > (Atlidakis, Godefroid, Polishchuk, ICST 2020, III장)
  - 논문에서 공개·공유·그룹·테넌트·관리자를 다루는 문장은 검색되지 않았다. 규칙에 예외가 없다.

- **BACScan: 읽기 위반은 응답 비교 오라클을 그대로 쓴다**
  > "BACScan employs the state-of-the-art (SoTA) response-based oracle for detecting RBAC vulnerabilities where the direct HTTP response provides feedback."
  >
  > → BACScan은 직접적인 HTTP 응답이 피드백을 주는 RBAC 취약점에는 최신 응답 기반 오라클을 사용한다.
  >
  > (Liu 외, BACScan, CCS 2025, 서론)
  - 표 2 기준 읽기 유형(RBAC)의 전체 결과는 참양성 36, 거짓양성 8, 정밀도 81.82%다.
  - 공개는 페이지 단위로 거른다: "filtering out public pages that are accessible to both attackers and victims"(3.3절). 같은 페이지 안의 공개 객체와 비공개 객체는 구분하지 않는다.

- **AuthProbe: 목록에 나타난 객체가 곧 자격이다**
  > "We define ownership as the ground truth that the API itself asserts through its collection operation. If principal u lists the collection and the object o appears, then u is entitled to read o."
  >
  > → 소유권을 API가 목록 조회를 통해 스스로 주장하는 정답으로 정의한다. 계정 u가 목록을 조회해 객체 o가 나타나면, u는 o를 읽을 자격이 있다.
  >
  > (AuthProbe, arXiv 2607.20574, III장)
  - 모델은 "객체마다 소유자가 한 명"이다: "Each object o of type R has an owner own(o) ∈ U". 공유 객체를 소유자 여러 명이나 공유 대상으로 두는 설명은 찾지 못했다.

  > "The design deliberately trades some completeness for a low false-positive rate, because a scanner that cries wolf is quickly ignored inside a build pipeline."
  >
  > → 이 설계는 누락을 일부 감수하고 오탐률을 낮춘다. 오탐을 내는 스캐너는 빌드 파이프라인에서 곧 무시되기 때문이다.
  >
  > (AuthProbe, VIII장)
  - 판정이 어려운 사례를 "보류"로 분리하지 않고 놓치는 쪽으로 조용히 실패시킨다. 놓친 비율은 지표로 보고되지 않았다.

### 패턴 3. 관찰한 응답으로 정책을 추정한다

- **EvoMaster: 정책 명세가 없으면 200 응답의 옳고 그름을 알 수 없다고 직접 밝힌다**
  > "Without a formal specification telling us what are the access policies for a REST API, how can a fuzzer identify that a resource should had not been accessed?"
  >
  > → REST API의 접근 정책을 알려주는 형식 명세가 없다면, 퍼저는 어떤 리소스에 접근하면 안 되었는지 어떻게 알아낼 수 있는가?

  > "For example, if a user A accesses resource X and they get a 200 HTTP status code, how can a fuzzer tell that being a fault (i.e., a 403 was expected with no returned data)?"
  >
  > → 예를 들어 사용자 A가 리소스 X에 접근해 200을 받았을 때, 퍼저는 그것이 결함(403이 기대되고 데이터가 없어야 했던 경우)인지 어떻게 알 수 있는가?
  >
  > (Sahin, Zhang, Arcuri, arXiv 2604.00702, 3.3절)

- **공유·그룹 사례가 단순 규칙의 오탐 원인이라고 명시한다**
  > "groups of users (e.g., guardians for a child, typically their parents) share the same rights and resources, but cannot access the resources of other groups (i.e., other families)."
  >
  > → 사용자 집단(예: 아이의 보호자, 대개 부모)은 같은 권리와 리소스를 공유하지만 다른 집단(다른 가족)의 리소스에는 접근할 수 없다.
  >
  > (arXiv 2604.00702, 3.3절)

- **그래서 읽기가 아니라 쓰기 동사의 불일치로 오라클을 세우고, 오탐을 감수한다**
  > "Our hypothesis is that, if any two of these operations are forbidden (i.e., 403), but the third is allowed (i.e., 2xx), then it is most likely a misconfiguration of the API."
  >
  > → 우리의 가설은, PUT·PATCH·DELETE 중 둘이 금지(403)인데 셋째가 허용(2xx)이면 API 설정 오류일 가능성이 크다는 것이다.

  > "a non-zero amount of false-positive identified faults could be tolerable in practical contexts."
  >
  > → 실무 맥락에서는 0이 아닌 수준의 오탐 결함은 감수할 수 있다.
  >
  > (arXiv 2604.00702, 3.3절)
  - 이 오라클은 남의 객체를 읽을 수 있는지를 판정하지 않는다. 읽기 객체별 공개·비공개 판정은 다루지 않는다.

- **2607.16754: 규칙과 가중치를 앱마다 다시 맞춘다**
  > "the prototype's evidence rules, risk weights, thresholds, and endpoint configuration are tied to the semantics of the testbed and require recalibration when transferred to another application."
  >
  > → 프로토타입의 증거 규칙, 위험 가중치, 임계값, 엔드포인트 설정은 테스트베드의 의미에 묶여 있어서, 다른 애플리케이션으로 옮길 때 재조정이 필요하다.
  >
  > (arXiv 2607.16754, 6.2절)
  - 본문에 "public"이라는 단어가 한 번도 나오지 않는다.

### 패턴 4. 소스 코드에서 소유 관계를 뽑는다

- **BolaZ: 생산 API가 반환한 ID를 그 사용자의 접근 범위로 본다**
  > "Therefore, BolaZ uses SELECT statements of P-APIs as MSG intervals of resource IDs."
  >
  > → 따라서 BolaZ는 P-API의 SELECT 문을 리소스 ID의 MSG 구간(접근 범위)으로 사용한다.
  >
  > (Rethinking BOLA under Zero Trust, arXiv 2507.02309, 3.4절)

  > "If an attacker gains administrator privileges, he has permission to operate on all resources and does not need to launch BOLA attacks."
  >
  > → 공격자가 관리자 권한을 얻으면 모든 리소스를 조작할 권한이 있으므로 BOLA 공격을 할 필요가 없다.
  >
  > (arXiv 2507.02309, 5.1절)
  - 관리자 API는 검사 대상에서 뺀다. 공유 객체는 공유 API가 반환한 ID의 데이터 흐름으로 처리한다(공유 패널 CVE 사례).

  > "BolaZ sometimes was unable to determine which resource IDs produced by P-APIs are passed to C-APIs solely by analyzing condition code"
  >
  > → BolaZ는 조건 코드만 분석해서는 P-API가 만든 리소스 ID 중 어떤 것이 C-API로 전달되는지 판단하지 못할 때가 있었다.
  >
  > (arXiv 2507.02309, 평가)
  - 판단하지 못한 사례를 한계로 서술할 뿐, 별도 출력이나 비율로 보고하지 않는다.

- **IDORacle: 공개·그룹·테넌트·관리자를 정책으로 등록해 처리한다**
  > "Public dictionary or configuration tables should be allowed when they are not registered as protected objects."
  >
  > → 공개 사전이나 설정 테이블은 보호 대상 객체로 등록되지 않은 경우 허용되어야 한다.

  > "Group- and tenant-derived cases require the oracle to validate whether the target group or tenant is in the current subject’s permission scope."
  >
  > → 그룹·테넌트에서 파생된 사례는, 오라클이 대상 그룹이나 테넌트가 현재 주체의 권한 범위에 있는지 확인해야 한다.
  >
  > (IDORacle, arXiv 2609.12426, 5.4절)

  > "IDORacle does not infer ownership from arbitrary column names alone, because such inference would create both false positives and unsafe bypasses."
  >
  > → IDORacle은 임의의 컬럼 이름만으로 소유권을 추론하지 않는다. 그런 추론은 오탐과 안전하지 않은 우회를 모두 만들기 때문이다.
  >
  > (arXiv 2609.12426, 4장)
  - 우리가 필드 이름만으로 권한을 확정하지 않기로 한 결정과 같은 방향의 외부 근거다.
  - 정책 메타데이터는 사람이 등록하고, Java 소스와 JDBC 계측이 필요하다. 진단이 아니라 런타임 차단이다. 정상 업무의 예외는 shadow 모드에서 "explicit policy exceptions"로 사람이 추가한다.

### 패턴 5. 범위 밖으로 둔다

- **BACFuzz: 객체 상태에 따른 권한은 다루지 않는다**
  > "Other models, such as context-based or attribute-based access control [41], which regulate whether users are allowed to access certain objects based on the state of the users, are out of the scope."
  >
  > → 사용자의 상태에 따라 객체 접근을 허용하는 맥락 기반이나 속성 기반 접근 제어 같은 다른 모델은 범위 밖이다.
  >
  > (BACFuzz, arXiv 2507.15984, 3.3절)

  > "Solely relying on web response messages can be less effective since the WUTs may reply with unclear information."
  >
  > → 웹 응답 메시지에만 의존하면 대상 앱이 불분명한 정보를 돌려줄 수 있어서 효과가 떨어질 수 있다.
  >
  > (arXiv 2507.15984, 3장)

### 참고. 워크플로 수준 증거 (초록만 확인)

- **BACScout: 증거가 없으면 발견으로 치지 않는다**
  > "Existing black-box BAC testing remains largely request-centric, and therefore struggles with cases whose target and oracle only become clear at the workflow level."
  >
  > → 기존 블랙박스 BAC 테스트는 대체로 요청 중심이라, 대상과 오라클이 워크플로 수준에서야 분명해지는 사례에 어려움을 겪는다.

  > "treats a mutation as a finding only when a planned external-effect oracle shows that the mutated subject affected a protected object or function."
  >
  > → 계획한 외부 효과 오라클이 변형된 주체가 보호 대상 객체나 기능에 영향을 줬음을 보일 때만 변형을 발견으로 취급한다.
  >
  > (Wang, Gong, BACScout, ECNCT 2026, 초록)
  - 초록의 수치: 알려진 대상 13건 중 7건 재현(BACScan은 0건), 후보 34개 중 23개가 진짜(BACScan은 288개 중 7개). 요청 중심 도구가 후보를 많이 내고 대부분 거짓이라는 근거다.
  - 초록에 공개·공유 언급이 없다. 본문은 유료라 확인하지 못했다.

### 참고. 실제 BOLA는 사용자 한 명의 소유로 끝나지 않는다

> "If User A reads User B’s data, that is Direct Object Reference; if Organization A reads Organization B’s data, that is Tenant Isolation."
>
> → 사용자 A가 사용자 B의 데이터를 읽으면 직접 객체 참조이고, 조직 A가 조직 B의 데이터를 읽으면 테넌트 격리 위반이다.
>
> (Broken Object Level Authorization in the Wild, arXiv 2605.25865, 4.3절)

> "The violated boundary is organizational membership specifically, not just user identity."
>
> → 위반된 경계는 사용자 신원만이 아니라 조직 소속이다.

- 소유자를 사용자 한 명으로 두는 모델(AuthProbe)로는 조직 소속 경계를 담지 못한다.

## 기존 연구에서 부족한 점

1. **객체 단위 기대 권한을 얻는 방법이 제한적이다.** 사람이 적거나, 소스에서 뽑거나, 관찰로 추정한다. AuthProbe는 목록이 없을 때 설정에 시드 객체를 줄 수 있다고 하지만, 시드에 공개·비공개·공유 상태를 붙인다는 설명은 없다.
2. **공개·공유·조직 소속을 명시적으로 다루는 연구는 소스 접근이 필요하다.** 블랙박스에서 객체 단위로 다룬 연구는 찾지 못했다. BACScan은 페이지 단위로 공개를 거르고, BACFuzz는 범위 밖으로 뺀다.
3. **기본 모델이 단순하다.** ICST'20은 예외 없는 규칙이고, AuthProbe는 소유자 한 명 모델이다. 조직 소속이나 공유를 표현하지 못한다.
4. **"모른다"가 성능 지표가 아니다.** 근거가 부족한 사례는 오탐을 감수하거나(EvoMaster), 조용히 놓치거나(AuthProbe), 발견으로 치지 않거나(BACScout), 한계로 서술된다(BolaZ). 보류율을 재현율·오탐률과 함께 보고한 논문은 찾지 못했다.
5. **평가가 좁다.** AuthProbe와 2607.16754는 합성·스크립트 데이터를 썼고, IDORacle의 정상 흐름은 대부분 자기 객체 접근이다. 같은 필드 형태에서 공개·비공개·공유가 섞인 조건을 오탐 기준으로 잰 평가는 찾지 못했다.

## 무엇을 개선할 수 있나

아래는 직접 연결된 논문과 도구마다 **무엇을 어떻게 개선하고, 무엇으로 증명하는지**를 정리한 제안이다. 전부 실험 전이다. 각 개선안에는 "이 결과가 나오면 개선이 없다고 판단한다"는 조건을 붙였다. 기준선으로 돌려볼 코드는 AuthProbe(Apache 2.0, GitHub 공개, 계정 2개와 OpenAPI 명세로 실행), BACScan(소스 공개), EvoMaster(논문 초록에서 오픈소스 퍼저로 명시), ZAP·AuthMatrix·Autorize(오픈소스 도구)이다. 2607.16754의 코드 공개 여부는 확인하지 못했다.

### 개선 1. ZAP·AuthMatrix: 규칙표를 사람이 쓰는 대신 객체 생성 기록에서 만든다

- **부족한 점**: 규칙이 페이지(URL 노드)나 요청 단위라서 객체별 공개·공유를 담으려면 사람이 규칙을 직접 써야 한다. (ZAP: "each Site Node (web page) will be associated to one of the following values", AuthMatrix: "select the checkboxes for all roles that are authorized to make each HTTP request")
- **개선안**: 테스트 계정이 객체를 만들 때 공개·비공개·공유를 지정하면서 (객체 ID, 소유자, 공개 상태, 공유 대상)을 자동 기록한다. 이 기록을 ZAP 접근 규칙이나 AuthMatrix 표 형식으로 내보낸다. 사람은 객체 생성 시나리오만 쓴다.
- **검증**: 같은 API에서 사람이 표를 직접 작성한 경우와 자동 생성한 경우의 준비 시간, 입력 항목 수, 두 표가 같은 판정을 내는 비율을 비교한다.
- **개선이 없다고 판단할 조건**: 자동 생성한 표가 사람이 만든 표와 자주 다르거나, 시간 절감이 작을 때
- **한계**: 공개 상태를 API로 지정할 수 없는 서비스와 객체 생성 API가 없는 서비스에는 못 쓴다.

### 개선 2. AuthProbe: 세 번째 계정과 상태 라벨을 시드에 붙인다 (핵심)

- **부족한 점**: 소유권을 "목록에 나타난 객체는 읽을 자격이 있다"로 정의하고 객체마다 소유자를 한 명으로 둔다(own(o)∈U). 판정은 성공 응답의 id가 피해자 객체 id와 같은지다(V-B절). 두 계정 목록에 같은 객체가 동시에 나타나는 경우를 어떻게 다루는지는 논문에서 설명을 찾지 못했다. 시드는 목록이 없을 때 설정에 넣는 객체 ID이고, 공개 상태를 붙인다는 설명은 없다. 공개 객체에서 실제로 오탐하는지는 평가된 적이 없다.
- **개선안**:
  1. 계정을 소유자 A, 비공유 B, 공유 C 세 개로 늘려 공유 대상의 정당한 접근을 대조군으로 쓴다.
  2. 시드를 사람이 넣는 대신 객체를 만들면서 자동 확보하고, 공개·비공개·공유 라벨을 붙인다.
  3. 정당한 접근(공개 조회, 공유받은 조회)을 위반에서 뺀다.
- **검증**: 공개·비공개·공유가 섞인 자체 API에서 AuthProbe를 그대로 돌려 기준선을 만든다. 같은 재현율에서 공개·공유 호출을 위반으로 잘못 센 수를 비교한다. 공개 벤치(crAPI의 커뮤니티 게시글은 공개, 차량 위치는 비공개)에서도 확인해 우리가 만든 API에 유리하다는 비판을 줄인다.
- **개선이 없다고 판단할 조건**: AuthProbe가 공개·공유 호출에서 오탐이 거의 없을 때. 이 경우 이득이 작다고 그대로 보고한다. 오탐이 생길지는 돌려봐야 안다.
- **한계**: 공정한 비교를 위해 AuthProbe 설정을 최대한 그 저자의 권장 방식으로 둬야 한다.

### 개선 3. EvoMaster(2604.00702): 읽기 오라클의 빈자리를 라벨로 채운다

- **부족한 점**: 저자가 200 응답이 결함인지 알 수 없는 오라클 문제를 밝혔다(3.3절). 대신 PUT·PATCH·DELETE 중 일부만 403인 불일치를 오라클로 쓰고 오탐을 감수한다. 읽기(GET)로 남의 객체를 조회하는 경우의 판정 규칙은 제시하지 않았다.
- **개선안**: 읽기 요청에 대해 생성자가 설정한 공개·비공개·공유 상태를 독립 근거로 쓰는 오라클을 추가한다. 쓰기 불일치 규칙이 적용되지 않는 읽기 전용 엔드포인트가 대상이다.
- **검증**: 읽기 전용 엔드포인트가 있는 자체 API에서 EvoMaster 오라클이 적용 불가로 남는 비율과 우리 방법의 확정 범위를 비교한다.
- **개선이 없다고 판단할 조건**: 읽기 엔드포인트에서 EvoMaster 오라클이 이미 적용되고 결과가 우리와 비슷할 때
- **한계**: EvoMaster를 직접 붙여 돌리는 작업이 크다. 최소 버전은 논문 설명 기준의 적용 가능 범위 분석이며, 이 경우 직접 실행 비교가 아니라고 명시한다.

### 개선 4. BACScan: 공개 판정을 관찰이 아니라 설정으로 정한다

- **부족한 점**: 공개를 "공격자와 피해자 모두 접근할 수 있는 페이지"로 관찰해 거른다(3.3절). 읽기 유형(RBAC)의 전체 결과는 표 2에서 거짓양성 8건, 정밀도 81.82%다.
- **개선안**: 공개 여부를 관찰이 아니라 객체를 만들 때 설정한 라벨로 정한다.
- **검증**: 자체 API에서 "두 계정 모두 성공하면 공개로 간주"하는 단순 규칙과 라벨 기반 규칙의 공개·비공개·공유 분류 오류율을 비교한다.
- **개선이 없다고 판단할 조건**: 두 규칙의 분류 오류율 차이가 작을 때
- **한계**: 단순 규칙은 BACScan 자체가 아니므로 이 실험만으로 "BACScan보다 낫다"고 주장할 수 없다. BACScan 소스가 공개돼 있어 후속으로 직접 실행할 수 있다.

### 개선 5. 2607.16754: 재조정을 가중치 튜닝에서 객체 준비로 바꾼다

- **부족한 점**: 증거 규칙, 위험 가중치, 임계값, 엔드포인트 설정을 앱마다 재조정해야 한다(6.2절).
- **개선안**: 연속값 가중치 대신 라벨 일치 여부라는 이산 규칙으로 판정하고, 앱마다 필요한 준비를 테스트 객체 생성으로 한정한다.
- **검증**: 앱마다 사람이 정해야 하는 값의 개수와 준비 시간을 비교한다. 상대 논문은 논문에 적힌 설정 항목 수로 센다.
- **개선이 없다고 판단할 조건**: 우리 준비 시간이 더 길거나 값의 개수가 비슷할 때
- **한계**: 우리도 준비 비용이 0이 아니다. 노력의 종류가 다를 뿐이다. 코드 공개 여부를 모르므로 직접 실행 비교는 못 한다.

### 개선 6. 모든 연구의 공통 빈자리: 보류를 이유와 함께 결과로 보고한다 (핵심)

- **부족한 점**: 근거가 부족한 사례가 오탐 감수(EvoMaster), 조용한 누락(AuthProbe), 발견 제외(BACScout), 한계 서술(BolaZ)로 처리된다. 비율은 보고되지 않는다.
- **개선안**: 보류에 사유 코드를 붙인다.
  - 공개 상태 신호 없음
  - 공유 목록 신호 없음
  - 응답에 객체 식별자 없음
  - 쓰기라서 실행하지 않음

  재현율, 오탐률, 보류율을 함께 보고하고 사유별 분포를 낸다. 사유는 "테스트 객체를 하나 더 만들면 확정으로 바뀌는가"를 알려 준다.
- **검증**: 보류 중 테스트 객체를 추가하면 확정으로 바뀌는 비율을 잰다.
- **개선이 없다고 판단할 조건**: 보류의 대부분이 객체를 더 만들어도 풀리지 않을 때
- **한계**: 사유 분류가 세밀해질수록 분류 기준을 정하는 데 주관이 들어간다.

### 한눈에 보기: 개선안, 기준선, 지표

| 개선안 | 기준선 | 지표 | 개선이 없다고 판단할 조건 |
|---|---|---|---|
| 1 규칙표 자동 생성 | 사람이 쓴 표 | 준비 시간, 항목 수, 표 일치율 | 표가 자주 다르거나 절감이 작음 |
| 2 세 계정 + 상태 라벨 (핵심) | AuthProbe 그대로 실행 | 공개·공유 오탐, 재현율 | AuthProbe도 오탐이 거의 없음 |
| 3 읽기 오라클 | EvoMaster 오라클 적용 범위 | 읽기 엔드포인트 확정 범위 | 이미 적용 가능하고 결과가 비슷함 |
| 4 설정 기반 공개 | 두 계정 성공 = 공개 규칙 | 분류 오류율 | 오류율 차이가 작음 |
| 5 준비 비용 | 상대 논문의 설정 항목 수 | 값의 개수, 시간 | 우리 준비가 더 오래 걸림 |
| 6 보류 사유 (핵심) | 사유 없는 보류 | 보류 중 확정 가능 비율 | 대부분 풀리지 않음 |

**핵심 주장은 2번과 6번 둘로 잡는다.** AuthProbe가 가장 가까운 블랙박스 연구이고 코드가 공개돼 있어 같은 조건에서 직접 비교할 수 있다. 6번은 읽은 논문에서 보고된 적이 없는 지표다. 나머지는 보조 실험이다.

## 우리 쪽의 약한 점

- **미표시 객체 대부분이 보류될 수 있다.** 이러면 자동 판정을 핵심 기여로 주장하지 못한다. 중단 기준은 [2607.16754 쉬운 정리와 우리 가설](2607.16754%20%EC%89%AC%EC%9A%B4%20%EC%A0%95%EB%A6%AC%EC%99%80%20%EC%9A%B0%EB%A6%AC%20%EA%B0%80%EC%84%A4.md) 7.2절에 있다.
- **입력이 0이 아니다.** 테스트 객체 준비와 라벨링에 사람의 시간이 든다. ZAP·AuthMatrix 대비 줄어드는 양은 실험으로 재야 한다.
- **자체 API 평가가 순환일 수 있다.** 공개·비공개·공유를 우리가 직접 만든 API에서 재면 스스로 만든 정답을 스스로 맞히는 셈이다. 실제 API의 분포(공개 명세의 권한 단서 후보 9.5%)로 설계의 현실성을 보완하되, 외부 검증이 필요하다.
- **비교가 표면적일 수 있다.** 이 표는 논문에 적힌 것을 기준으로 했다. 각 도구를 같은 벤치마크에 돌려 직접 비교한 것이 아니다.

## 검색 범위와 확인 상태

- **원문 PDF로 확인**: ICST'20, 2604.00702, AuthProbe, 2607.16754, BACScan, BACFuzz, BolaZ, IDORacle, 2605.25865
- **도구 문서로 확인**: ZAP Access Control Testing(본문과 상태 탭), AuthMatrix README, Autorize README
- **초록만 확인**: BACScout(IEEE ECNCT 2026, 본문 유료. 학교 도서관 접속으로 DOI 10.1109/ECNCT70535.2026.11661439 확인 필요)
- **2차 인용으로만 확인**: BolaRay. BolaZ 논문이 "BOLARAY also requires developers to mark DAL specifications, and does not support the detection of BOLA vulnerabilities in SELECT statements"라고 설명한다(7.2절). 원문은 읽지 못했다.
- **확인하지 못한 곳**: Akto, StackHawk, Burp Auth Analyzer 등 상용·확장 도구의 세부 동작, 로그인이 필요한 논문 검색 서비스(elicit, DBpia, KCI)
- **키워드 검색 범위**: 위 PDF 전체에서 shared, public, group, tenant, admin, abstain, inconclusive, undetermined 등을 검색했다. "언급 없음"은 이 검색 결과 0건을 뜻한다.
