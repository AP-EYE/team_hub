# 2607.16754 쉬운 정리와 우리 가설

## 1. 논문 한 줄

API 앞에 경비원을 세워, 앱 코드를 고치지 않고 트래픽만 보고 권한 위반을 실시간으로 막는 방법이다.

## 2. 경비원 비유

| 논문 용어 | 경비원 버전 |
|---|---|
| x_obj 객체 접근 증거 | 이 사람이 전에 이 집을 정상적으로 드나든 적 있나 |
| x_id 신원 일관성 | 출입증 이름과 얼굴이 맞나 |
| x_beh 행위 이상 | 여러 집 문을 빠르게 두드리고 다니나 |
| x_auth 인증 맥락 | 중요한 방에 들어갈 때 최근 본인 확인을 했나 |
| x_net 네트워크 | 평소와 다른 곳에서 왔나 |
| s_ep 엔드포인트 위험 | 들어가려는 곳이 금고방인가 창고인가 |

6개 점수에 비중을 곱해 더하고, 한 항목이 아주 심각하면 합산이 낮아도 위험으로 본다. 점수에 따라 통과, 경보, 차단을 고른다.

## 3. 우리가 알아야 할 것 두 개

**① 핵심 판단은 "전에 드나든 적 있나"(x_obj)다.** 이 항목을 빼면 F1이 99.90%에서 81.31%로 떨어진다.

**② 규칙과 가중치를 사람이 테스트 앱에 맞춰 정했다.**
> "evidence rules, risk weights, thresholds, and endpoint configuration are tied to the semantics of the testbed and require recalibration when transferred to another application" (6.2절)

그 밖에 저자가 인정한 한계: 위반·정상 반반의 스크립트 데이터, URL 규칙과 빈도 방식뿐인 비교 대상. 본문에 "public"이 한 번도 나오지 않는다.

## 4. 접은 가설과 이유

**접은 가설**: 응답 필드 비교로 공개 API 오탐과 앱별 재조정 문제를 해결한다.

**이유**: 필드 비교는 *무엇이 반환됐는지*는 보여주지만 *반환돼도 되는지*는 알려주지 않는다. 정상 공개 프로필과 취약한 비공개 프로필이 두 계정에 똑같은 응답을 주면 트래픽만으로 둘을 구분할 근거가 없다.

같은 문제를 2026년 API 퍼징 논문도 지적한다.
> "Simply stating that a user should not access or manipulate resources of other users would just result in many false-positive faults." (2604.00702, 3.3절. 관리자, 모더레이터, 가족 공유 계정을 예로 든다)

이 논문은 다른 요청에서 관찰한 401/403을 접근 제한의 증거로 쓴다.
> "No assumption on their relative access policies is needed... Such information is inferred dynamically based on the 401 and 403 HTTP status codes" (2604.00702, 3절)

이 방법도 모든 읽기 API의 의도를 알아내지는 못한다. 문제는 실제로 있고, 필드 비교 하나로 해결된 상태는 아니다.

## 5. 새 가설

> **권한표 전체를 작성하지 않고, 최소 두 테스트 계정으로 확보한 소수의 "접근이 허용되면 안 되는 사례"를 기준으로 인가 위반을 판정할 수 있는가? 이때 공개·공유 API의 오탐과 앱별 설정 비용은 얼마나 줄어드는가?**

- "허용되면 안 되는 사례"의 예: A가 **비공개로 만든 테스트 객체**에 B가 접근하는 경우.
- 공개로 만든 객체도 함께 둔다. 공개 대조군이 있어야 공개 API 오탐을 잴 수 있다.
- 비공개 설정이나 접근 의도를 확인할 수 없는 API는 취약하다고 단정하지 않고 **판정 보류**로 낸다.
- 필드 비교는 인가 판정 기준에서 뺀다. 위반이 확인된 뒤 **실제로 노출된 개인정보 항목을 산정하는 단계**에 둔다.

**솔직히 밝힐 것**: 최소한의 테스트 객체와 그 공개 여부는 사람이 입력한다. 기획서의 "정답을 사람이 입력하지 않는다"는 주장은 "입력을 최소화하고 그 비용을 측정한다"로 바뀐다.

## 7. 적용 범위 결정: 객체와 엔드포인트를 구분한다 (2026-09-29)

**연구 질문**: 소수의 명시적 접근 근거와 관찰 가능한 객체 상태를 이용할 때, 읽기 BOLA를 어느 범위까지 확인할 수 있으며 판단 불가 사례가 얼마나 남는가?

같은 엔드포인트의 객체라도 공개·비공개·공유 상태가 다를 수 있다. 공개 객체와 비공개 객체가 같은 응답을 내는 경우에는 두 계정의 요청·응답만으로 의도된 권한을 식별할 수 없다. 소유자가 처음 호출한 객체라는 사실도 비공개의 증거가 아니다. 따라서 엔드포인트 경로나 응답 필드가 같다는 이유만으로 테스트 객체의 허용·금지 라벨을 다른 객체에 복사하지 않는다.

### 7.1 판정 범위

| 대상 | 사용할 수 있는 근거 | 자동 출력 |
|---|---|---|
| 공개·비공개·공유 의도를 확인한 테스트 객체 | 해당 객체·호출자 관계·읽기 작업의 기대 권한, 응답의 실제 객체 확인 | 금지된 호출자가 객체 데이터를 받으면 **확인된 위반**. 공개 또는 공유 권한이 있으면 BOLA로 보지 않음 |
| 같은 엔드포인트의 미표시 객체 | 테스트 객체의 결과는 후보를 고르는 신호. 미표시 객체의 독립적인 비공개·공유 상태 증거가 추가로 있으면 그 객체를 별도로 검증 | 독립적인 금지 근거와 실제 객체 반환이 함께 있을 때만 **확인된 위반**. 그 외는 **검토 후보/판정 보류** |
| 다른 엔드포인트의 같은 객체 | 객체 ID의 연결은 검사 대상 선정에 사용. 작업별 공개 범위나 필드별 권한이 다를 수 있음 | 대상 엔드포인트의 기대 권한을 별도로 확인하기 전에는 **검토 후보/판정 보류** |
| 객체를 만들거나 접근 의도를 확인할 수 없는 엔드포인트 | 응답 차이·접근 이력·개인정보 여부만 있음 | **판정 보류**. 위험 신호를 표시할 수 있지만 BOLA 확정 불가 |

독립적인 금지 근거는 소유자가 직접 설정한 비공개 상태, 공유 해제 기록, 테스트 시나리오의 명시적 권한 등이다. 단순 401/403 관찰이나 목록 API 부재는 모든 객체의 정책을 증명하지 않는다.

**응답 필드를 금지 근거로 쓰는 조건 (2026-09-29 추가).** 미표시 객체의 응답에서 관찰한 공개 상태 필드 하나로는 특정 계정의 접근 금지를 확정하지 않는다. `private=true`여도 테스트 계정 B가 공유 대상일 수 있기 때문이다. 다음 두 조건을 모두 만족할 때만 그 객체·계정 쌍을 `deny`로 기록한다.
1. 객체가 비공개임을 뜻하는 필드가 있고, 그 필드의 의미를 사람이 한 번 확인했다. 같은 이름이 인가와 무관한 뜻일 수 있다(예: `isPrivate`가 사립학교 여부).
2. 같은 객체의 공유 대상 목록이 응답에서 관찰되고, 그 목록에 테스트 계정 B가 없다.

공유 목록이 보이지 않으면 비공개 필드가 있어도 `unknown`으로 두고 판정 보류한다. 이 조건 때문에 응답 단서만으로 확정 가능한 API는 이름 기준 후보(공개 명세 1,003개 중 9.5%, [2026-09-29 권한 단서 조사 재검증](2026-09-29%20%EA%B6%8C%ED%95%9C%20%EB%8B%A8%EC%84%9C%20%EC%A1%B0%EC%82%AC%20%EC%9E%AC%EA%B2%80%EC%A6%9D.md))보다 적다. 그 비율은 예비 실험에서 따로 잰다. 응답이 200이어도 요청한 객체의 식별자 또는 소유자만 아는 표식이 반환됐는지 확인한다. 정상 응답과 오류 응답의 상태·형태 차이는 검토 근거이며, 접근 의도를 대신하지 않는다.

**이번 프로젝트의 자동 확정 범위는 읽기 요청의 테스트 객체 및 독립적인 금지 근거가 확인된 미표시 객체까지로 제한한다.** 같은 엔드포인트로의 전파 성능은 연구 가설로 평가하고, 다른 엔드포인트 전파는 탐색적 분석으로만 보고한다. 이는 범위를 좁히는 결정이지, 이미 성능이 입증됐다는 뜻이 아니다.

예를 들어 A가 비공개로 설정한 `GET /records/17`을 B가 호출해 17번 객체가 반환되면 위반을 확인한다. 같은 경로의 18번이 공개 객체로 확인됐다면 B의 성공 조회는 정상이다. 19번은 공개 여부를 모르면 B에게 같은 필드가 반환돼도 보류한다. 17번과 같은 객체를 `GET /records/17/export`로 조회할 때도 그 작업의 기대 권한을 따로 확인한다.

### 7.2 최소 실험과 중단 기준

자체 API에는 같은 `GET /records/{id}`에서 동일한 필드 형태로 응답하는 공개·비공개·특정 계정 공유 객체를 만든다. 소유자 A, 비공유 계정 B, 공유 계정 C를 사용한다. B가 비공개 객체를 읽을 수 있는 취약 버전과 차단하는 정상 버전을 모두 둔다. 공유 해제 전후와 같은 객체를 조회하는 다른 엔드포인트도 별도 사례로 둔다. crAPI·VAmPI는 가능한 읽기 BOLA의 추가 확인에 쓰고, 자체 API의 공개·공유 일반화 결과를 대신하지 않는다.

테스트 객체의 ID와 권한 라벨을 입력으로 주고, **평가할 미표시 객체의 ID별 정답 라벨은 진단기에 주지 않는다.** 객체 단위 분리와 엔드포인트 단위 분리를 따로 수행한다. 단, 소유자 조작이나 응답에서 실제 관찰되는 공개·공유 상태는 입력 특징으로 허용하고 그 수집 비용을 기록한다. 결과는 미표시 객체의 상태 단서가 관찰 가능한 경우와 불가능한 경우로 나눠 보고한다. 독립적인 권한 단서가 없는 사례의 보류는 정답 라벨을 맞힌 성공으로 세지 않으며, 실제 위반이라면 전체 재현율의 놓친 건에 포함한다.

| 지표 | 계산·의미 |
|---|---|
| 전체 위반 재현율 | 확인된 위반 수 / 평가 대상의 실제 위반 수. 보류한 실제 위반은 놓친 건으로 계산 |
| 확인 판정의 정밀도와 공개·공유 오탐률 | 확정 위반 중 실제 위반 비율, 정상 공개·공유 호출 중 잘못 확정한 비율 |
| 판정 보류율과 자동 확정 범위 | 전체 대상 중 보류 비율과 확정 판정을 내린 비율을 함께 제시 |
| 사람 설정 시간·추가 요청 수 | 테스트 객체 준비·권한 확인에 든 시간, 교차 재생 횟수. 전체 권한표 작성 및 단순 계정 교차 방식과 비교 |

예비 실험에서 **독립적인 객체 상태를 얻지 못한 미표시 객체가 대부분 보류된다면**, 미표시 객체의 자동 판정을 핵심 기여로 주장하지 않는다. 그때 연구 질문은 최소 권한 근거를 얻는 비용과 확정 가능한 범위의 관계로 축소한다. 목표 수치는 예비 실험 후 평가셋을 열기 전에 고정한다.

### 7.3 선행연구가 주는 경계

- [2607.16754](https://arxiv.org/html/2607.16754)는 접근 이력·신원·행동 등을 결합하지만, 저자도 다른 앱에서 규칙과 가중치를 재조정해야 한다고 명시한다. 접근 이력만으로 의도된 소유권이 확정된다는 근거는 아니다.
- [AuthProbe](https://arxiv.org/html/2607.20574)는 목록 API에 나타난 객체를 계정별 접근 근거로 사용하고, 타 계정 요청의 객체 반환을 확인한다. 우리와 비교할 때 명세·목록 입력의 차이와 추가 테스트 요청 수를 함께 보고해야 한다.
- [EvoMaster 접근정책 오라클](https://arxiv.org/html/2604.00702)은 공유·관리자 등 복잡한 권한에서 단순 타인 객체 규칙이 오탐을 만든다고 설명한다. 403과 다른 작업의 2xx를 비교하는 방식도 특정 조건의 이상을 포착할 뿐 모든 읽기 API 정책을 복원하지 않는다.
- [접근 로그 기반 ABAC 정책 추론](https://arxiv.org/abs/1403.5715)은 로그와 속성으로 정책을 채굴하는 선행 분야다. 따라서 '소수의 예시에서 정책을 일반화한다' 자체를 최초 기여로 주장하지 않는다.
