## For future Claude

API-인가-취약점-진단의 10/02 교수 브리핑 최종 방향입니다. 사용자가 제공한 팀원의 AuthzTrace 0.6.0 가짜 API 보고를 근거로, [2026-10-02 팀 조사 반영·차별성 재점검](2026-10-02%20%ED%8C%80%20%EC%A1%B0%EC%82%AC%20%EB%B0%98%EC%98%81%C2%B7%EC%B0%A8%EB%B3%84%EC%84%B1%20%EC%9E%AC%EC%A0%90%EA%B2%80.md)의 비용 중심 후보를 목록 요청 성공과 객체별 허용을 분리하는 판정 문제로 좁혔습니다. 원본 계약·실행 결과를 확인하지 않았고 실제 Memos 재현 및 개선안의 성능은 검증 전입니다.

## 발표할 연구 질문

목록 조회의 성공과 객체별 읽기 허용을 구분하면, 정상적인 200 응답의 오탐을 줄이면서 실제 비공개 객체 누출을 계속 탐지할 수 있는가를 검증합니다.

핵심 입력은 같은 테스트 객체의 권한 근거이며, 핵심 비교는 상태 코드 중심 판단과 반환 객체·보호 내용 대조입니다. 작은 권한 계약, 합성 표식, 다중 계정, 본문 확인 자체는 선행 방법에 있습니다. AuthzTrace와 AuthProbe가 제공하는 기능을 새로 발명했다고 주장하지 않습니다.

## 근거 수준과 팀원 보고

사용자가 대화에 제공한 ‘AuthzTrace 한계와 테스트 결과’ Markdown 본문을 바탕으로 했습니다. 사용자는 원본 파일 탐색 대신 보고서 내용만으로 판단하도록 지시했습니다. 이번 자료 반영은 재실행이나 로그 검증이 아닙니다.

- 도구는 AuthzTrace 0.6.0입니다.
- 대상은 실제 Memos가 아니라 Memos 0.9.0의 개별·목록 조회 규칙을 모사한 가짜 API입니다.
- 취약 모드와 가상의 수정 모드, 계정 3개·메모 4개로 모드당 18건, 합계 36건을 검사했다고 합니다.
- 개별 조회는 모드당 12건, 합계 24건을 모두 맞게 판정했다고 합니다.
- 취약 모드의 목록 거부 검사 4건은 비공개 내용이 반환되어 정탐 4건입니다.
- 수정 모드의 목록 거부 검사 4건은 200+빈 목록인데도 BOLA로 분류되어 오탐 4건입니다.
- 목록 허용 검사는 모드당 6건 중 거부 4건을 뺀 2건이며, 두 모드 합계 4건으로 설명합니다.
- 전체 정탐 4·미탐 0·오탐 4에 대해 재현율 4/4=100%, 정밀도 4/8=50%입니다. 가짜 API 1개의 사례 집계이며 일반 성능이 아닙니다.

팀원은 2xx를 먼저 BOLA로 분류하고 표식 결과는 메모에만 반영한다고 설명했습니다. 이는 팀원 보고의 원인 설명이며 이번에 소스 함수 실행을 독립 검증한 결과가 아닙니다. 처음 실패한 실행의 JSON이 보존되지 않은 전체 검사 중단 사례는 핵심 실험 근거에서 제외합니다. 로컬 20ms는 실제 앱 성능으로 사용하지 않습니다.

## 판정 범위와 선행 방법

[AuthzTrace](https://github.com/Asttr0/AuthzTrace)는 사람이 권한 계약과 객체 표식을 입력하는 공개 도구입니다. [AuthProbe](https://arxiv.org/html/2607.20574)는 계정별 목록으로 객체 자격을 추정하고 반환 객체를 확인합니다. 기존 논문 근거와 기능 중복 검토는 [2026-10-02 팀 조사 반영·차별성 재점검](2026-10-02%20%ED%8C%80%20%EC%A1%B0%EC%82%AC%20%EB%B0%98%EC%98%81%C2%B7%EC%B0%A8%EB%B3%84%EC%84%B1%20%EC%9E%AC%EC%A0%90%EA%B2%80.md) 및 [2026-10-02 문서 허브 논문 대조](2026-10-02%20%EB%AC%B8%EC%84%9C%20%ED%97%88%EB%B8%8C%20%EB%85%BC%EB%AC%B8%20%EB%8C%80%EC%A1%B0.md)를 유지합니다.

목록 API 호출 자체는 허용되면서 특정 객체의 내용은 금지될 수 있습니다. 따라서 계약 설정을 잘못 작성한 효과와 도구 판정 규칙의 한계를 분리해야 합니다. 기존 기능·응답 검증 설정·객체별 명시 계약으로 해결되는지 먼저 확인합니다. 상태 코드 조건 하나를 바꾸는 수정만으로 끝난다면 연구 기여가 약할 수 있습니다.

## 같은 조건에서 비교할 계획

1. 단순 2xx 규칙, AuthzTrace 원형, 기존 설정·계약 보완, 목록 반환 객체 대조 개선안을 비교합니다.
2. 계정·객체 ID·권한 근거·조회 요청을 고정합니다. 추가 권한 입력과 객체 발견 범위 증가의 효과를 분리합니다.
3. 유효한 200 응답에서 빈 목록, 허용 객체만 반환, 금지 객체만 누출, 허용·금지 객체 혼합을 비교합니다.
4. 공개된 ID·제목과 보호된 본문을 구분합니다. 응답 구조·계정·객체 준비 상태가 불명확하면 정상으로 확정하지 않습니다.
5. 실제 Memos의 정상 목록·보호 내용 누출을 확인하고 접근 거부 대조군과 대조합니다. 가짜 fixed는 공식 수정 버전이 아닙니다.
6. Gitea는 공개·비공개·공유와 저장소·이슈 조건의 보조 평가 대상입니다. 실제 가능한 목록 누락 조건인지 확인합니다.
7. 평가 정답은 앱 정책과 설정 상태를 따로 검토하며 판정기 입력을 복사해 정답으로 삼지 않습니다.
8. 오탐·재현율·보류율·입력 및 검토 비용을 함께 제시합니다. 실제 위반의 보류·미검사도 재현율 분모에 남깁니다.

## 교수님께 확인할 사항

목록 요청 성공과 객체별 권한을 분리하는 실패 조건을, 실제 앱과 혼합 응답에서 비교·검증하는 것이 연구 질문으로 충분한지 의견을 요청합니다. 현재는 개선 후보이며 기법의 새로움이나 기존 방법 대비 우월성이 입증된 상태가 아닙니다.
