심재훈이 참여하는 CCIT-2 팀 프로젝트(4인)의 주제 기획서다. 2026-09-17 팀 빌딩에서 재훈에게 배정됐던 리눅스 서버 랜섬웨어 실시간 차단이 2026-09-18 폐기되면서, 그 자리를 대체하기 위한 교체 제안으로 작성됐다. # CCIT 주제 기획서 - API 인가 취약점 진단 및 개인정보 노출 영향도 산정

## Context

2026년 하반기 국내에서 API를 통한 개인정보 유출이 연쇄적으로 발생했다. 6주 사이 5건이다.

| 시점 | 사고 | 규모 | 공표된 원인 |
|---|---|---|---|
| 2026-08-30 | 29CM | 15만 9852건 | 주문조회 API |
| 2026-09-08 | 위버스 | 42만 2584건 | 결제 처리 API |
| 2026-09-08 | 강남언니(힐링페이퍼) | 21만 9665건 | 상담 내역 조회 API |
| 2026-09-08 | 화해 | 미공개 | 비정상 접근 경로 |
| 2026-09-15 | 레쥬메나인 | 미공개 | 서버 권한 검증 누락 |

출처: 보안뉴스 데일리 캡처, `99_Knowledge/news/` 참고. 원문 링크는 각 날짜 노트에 보존돼 있다.

힐링페이퍼는 조치 내용을 "인증 절차 강화 및 권한 검증 로직 재정비"라고 공지했다. OWASP API Security Top 10 2023의 API1 BOLA(객체 수준 인가 실패)에 해당한다. 유출 항목에 상담 등록 사진, 시술 의사 식별값, 상담 동기가 포함된 것은 API3 BOPLA(응답 과잉 노출)가 함께 작동했음을 뜻한다. 힐링페이퍼는 ISMS 인증을 보유한 상태였다. 인증 체계가 객체 수준 인가 검증을 실질적으로 커버하지 못한다는 증거다.

**기존 도구는 인가를 다루기는 한다. 다만 정답을 사람이 넣어야 한다.** 2026-09-18 공식 문서와 저장소로 직접 확인한 결과다.

| 도구 | 인가 테스트 | 민감정보 분류 | 확인 |
|---|---|---|---|
| ZAP Access Control Testing | 있음. 사용자별 Allowed/Denied 표를 사람이 작성해야 동작 | 없음 | 공식 문서 |
| Autorize, AuthMatrix | 있음. 역할·세션 수동 설정 | 없음 | 도구 성격 |
| Akto | 있음. OWASP Top 10 커버 명시 | 있음. 정규식 + 태그 + 3단계 등급 | 저장소 |
| Wallarm API Firewall, open-appsec | 없음. 런타임 차단 | 없음 | 저장소 |
| Schemathesis | 없음. 명세 위반·서버 오류 | 없음 | README |

ZAP 공식 문서의 문장이 핵심이다. "In order to identify potential access control issues, ZAP needs to know which parts of the web application are supposed to be accessed by which user." 테스터가 사용자별로 페이지마다 Allowed, Denied, Unknown을 지정해야 위반을 판정한다. (as of 2026-09-18, https://www.zaproxy.org/docs/desktop/addons/access-control-testing/)

open-appsec은 요청 단위 방어다. 공식 설명에 따르면 "Upon every HTTP request, all parts are decoded"한 뒤 공격 지표, IP, user agent, 핑거프린트 등을 머신러닝 모델에 넣어 악성 여부를 판정한다. **BOLA는 형식이 완전히 정상인 요청이므로 공격 지표가 남지 않는다.** 런타임 방어 계층에서 구조적으로 잡히지 않는 이유다. (as of 2026-09-18, https://github.com/openappsec/openappsec)

Akto는 `pii-types/`에 정규식 기반 민감정보 정의를 둔다. 항목마다 `tagsLists`(PII, FINANCE, HEALTHCARE)와 `dataTypePriority`(CRITICAL, HIGH, MEDIUM)를 갖는다. **민감정보 등급을 이미 매긴다.** 다만 정의된 유형은 인도 PAN, 미국 Medicare, 영국 NI, 핀란드, 캐나다 SIN, 독일, 일본, IBAN, 미국 주소 등이고 **한국 유형은 없다. 주민등록번호도 없다.** (as of 2026-09-18, https://github.com/akto-api-security/akto/tree/master/pii-types)

**뚫렸을 때 얼마나 새는지, 그래서 무엇부터 고쳐야 하는지는 어느 도구도 정량화하지 않는다.** 강남언니 사고의 본질은 API 하나가 뚫린 것이 아니라, 그 하나가 의료 상담 사진까지 내려줬다는 데 있다. 취약점은 하나인데 유출 범위를 결정한 것은 응답 스키마다.

이 프로젝트는 그 공백을 메운다.

## 한 줄 정의

프록시로 수집한 실제 트래픽에서 API 엔드포인트를 복원하고, 다른 사용자의 토큰으로 호출 가능한지를 LLM 판정으로 탐지한 뒤, 유출되는 응답 필드를 개인정보보호법 분류 체계로 가중 점수화해 수정 우선순위를 산출한다.

## 시스템 구성

### 기술 선택 - 프록시 엔진은 만들지 않는다 (2026-09-19 결정)

교수 요구로 게이트웨이를 자체 구축하기로 했으나, HTTP 프록시 엔진까지 직접 만들면 TLS 종단, 스트리밍, 헤더 처리, 연결 관리에 학기가 소모된다. 보안 기여는 남지 않는다.

**mitmproxy의 리버스 프록시 모드를 엔진으로 쓴다.** 공식 문서 확인 내용이다.

```shell
mitmdump --mode reverse:https://upstream@80
```

> In reverse proxy mode, mitmproxy acts as a normal server. Requests by clients will be forwarded to a preconfigured target server, and responses will be forwarded back to the client.
> (as of 2026-09-19, https://docs.mitmproxy.org/stable/concepts/modes/)

이것이 곧 인라인 게이트웨이다. `@포트`로 리슨 포트를 지정하고 `--mode`를 반복해 여러 포트를 동시에 띄울 수 있다. Host 헤더는 자동 재작성된다.

우리 모듈은 애드온으로 붙인다. 애드온 API는 모듈 스코프 함수로 이벤트를 받는다.

```python
def request(flow):
    flow.request.headers["myheader"] = "value"
```

(as of 2026-09-19, https://docs.mitmproxy.org/stable/addons/overview/)

**이 선택이 뒤집는 것.** "게이트웨이를 만든다"의 의미가 "HTTP 프록시를 구현한다"에서 "보안 검사 로직을 구현한다"로 바뀐다. 웹 서버를 소켓부터 짜지 않고 FastAPI를 쓰는 것과 같은 판단이다. 게이트웨이는 여전히 우리가 만든다.

1단계 위험이 사실상 사라진다. 프록시가 안 떠서 전체가 멈추는 시나리오가 없어진다.

**남는 제약.** mitmproxy는 운영 트래픽 처리 성능이나 고가용성을 목표로 하는 도구가 아니다. 사내 스테이징과 진단 환경을 전제로 하며, 이는 원래 범위 밖으로 선언한 항목과 일치한다.

### 1단계 - 엔드포인트 복원 (입력: 프록시 트래픽)

- mitmproxy 또는 HAR 파일로 실제 앱과 웹 사용 트래픽을 수집한다
- 요청 URL에서 경로 변수를 일반화해 엔드포인트 템플릿을 복원한다 (`/orders/1234` 에서 `/orders/{id}`)
- 인증 헤더, 쿠키, 커스텀 토큰 헤더를 자동 식별해 세션 컨텍스트로 분리한다
- 산출물: 엔드포인트 인벤토리 (경로, 메서드, 파라미터, 응답 스키마, 필요 세션)

OpenAPI 스펙을 받으면 보조 입력으로 병합하되, 스펙이 없어도 동작하는 것이 기본 전제다. 강남언니와 화해 같은 실사고 대상은 스펙을 공개하지 않는다.

### 2단계 - 인가 취약점 탐지 (LLM 판정)

두 개의 테스트 계정(A, B)을 준비하고 다음을 수행한다.

- A 세션으로 리소스를 생성하거나 조회해 객체 식별자를 수집한다
- 같은 요청을 B 세션 또는 무인증으로 재전송한다
- LLM이 세 가지를 판정한다
  - 이 파라미터가 테넌트 경계인가 (경로명, 필드명, 응답 구조로 추론)
  - 응답 차이가 권한 위반인가, 정상적 개인화인가
  - 판정 근거를 응답 본문에서 인용한다 (근거 강제로 오탐 억제)

판정 경로는 두 개를 모두 구현한다. 착수 검증에서 확인된 사실이다.

- **경로 A - 신원 불일치 검출.** 응답 본문에 소유자 식별자(이메일, 이름)가 실려 있고 토큰의 `sub`와 다르면 그 자체로 인가 위반이다. 정답을 주지 않아도 판정된다
- **경로 B - 응답 차이 비교.** 응답에 식별자가 안 실리는 엔드포인트에서는 A 세션과 B 세션의 응답을 비교해 판정한다

비용 통제를 위해 LLM은 판정에만 쓴다. 후보 선별은 정적 규칙으로 먼저 거른다. 식별자 형태 파라미터를 가진 엔드포인트, 인증 헤더가 있는 엔드포인트를 우선한다.

BFLA(관리자 전용 엔드포인트를 일반 사용자가 호출)도 같은 틀로 처리한다. 경로명과 응답 구조에서 관리자 의도를 LLM이 추론한다.

### 3단계 - 개인정보 노출 영향도 산정 (프로젝트의 본체)

초안에서는 부가 기능이었으나 본체로 승격한다. 인가 탐지는 이 단계를 먹이는 입력이다.

유출된 응답 본문의 각 필드를 개인정보보호법 분류로 매핑하고 가중한다.

| 분류 | 예시 | 가중 |
|---|---|---|
| 민감정보 (법 제23조) | 건강·의료, 성생활, 유전, 범죄경력, 사상·신념 | 최고 |
| 고유식별정보 (법 제24조) | 주민등록번호, 여권번호, 운전면허번호, 외국인등록번호 | 높음 |
| 일반 개인정보 | 이름, 연락처, 주소, 생년, 정밀 위치 | 중간 |
| 비식별 | 통계값, 내부 코드 | 낮음 |

- 필드명 사전과 값 패턴(정규식)으로 1차 라벨링, 애매한 필드는 LLM이 맥락으로 판정한다
- 강남언니 유출 항목(상담 사진, 시술 의사 식별값, 상담 동기)이 민감정보 최고 등급으로 자동 분류되는지가 이 단계의 1차 검증 기준이다
- 열거 가능성을 곱해 최종 노출 규모를 추정한다. 순차 정수 ID는 대량 수집이 가능하고 UUID는 별도 식별자 유출원이 필요하다
- **응답 안에 새어나온 내부 순차 ID는 인접 열거 표면의 신호로 가중한다.** 착수 검증에서 실제로 관측됐다

정량 근거는 개인정보보호위원회 공표 처분 사례에서 수집한다. 실제 과징금 사례와 점수 순위의 상관을 확인한다.

### 4단계 - 두 가지 출력

같은 엔진에서 두 개의 산출물이 나온다. 제품화의 핵심 구조이기도 하다.

**평시 - 수정 우선순위 리포트**

- 엔드포인트별로 (인가 취약 여부 곱하기 영향도 점수 곱하기 열거 가능성) 랭킹
- 각 항목에 재현 요청, 유출 필드 목록, 법적 분류 근거를 첨부

**사고시 - 유출 범위 산정서**

- 침해된 엔드포인트를 지정하면 그 응답이 반환하는 개인정보 항목을 법 조항별로 분류해 출력
- 개인정보보호위원회 신고 양식에 대응하는 초안 생성

## 독자 기여

1. **인가 판정의 오라클 자동 생성.** 기존 도구는 "누가 무엇에 접근해도 되는가"를 사람이 입력해야 동작한다. 그 입력을 응답 본문의 신원 불일치와 A/B 응답 차이로 자동 생성한다
2. **한국 법 체계 기반 가중.** Akto도 민감정보 등급을 매기지만 데이터 타입 자체의 등급이다. 개인정보보호법 제23조 민감정보와 제24조 고유식별정보 구분이 없고 한국 유형 자체가 정의돼 있지 않다
3. **스펙 없는 API 커버.** 트래픽 기반이므로 실사고 대상과 같은 조건에서 동작한다
4. **정규식으로 안 잡히는 필드 처리.** Akto는 값의 패턴으로 유형을 찾는다. 강남언니에서 유출된 "상담 동기", "시술 의사 식별값", "상담 등록 사진"은 값 패턴이 없다. 필드명과 맥락을 읽어야 하며 LLM 판정이 필요한 지점이다
5. **사고 대응 시간 단축.** 유출 범위 산정을 수작업에서 자동화로 옮긴다

## 제품화 경로

연구 산출물을 본줄기로 유지하되, 제품 가설을 함께 검증한다. 이 장은 창업 트랙 지원 시 그대로 떼어 쓴다.

### 시장 현실

API 보안 플랫폼 시장은 이미 포화다. Salt Security, Traceable, 42Crunch, Escape, StackHawk, Wallarm, Cequence가 경쟁하고 Noname Security는 2024년 Akamai에 인수됐다. Akto는 오픈소스와 상용을 병행한다.

기능으로는 이길 수 없다. **다만 이들 중 누구도 한국 개인정보보호법 분류를 하지 않는다.**

### 틈 세 개

**틈 1 - 사고 대응 시계.** 2026-09-19에 조문을 직접 확인했다. 상세는 [법적 근거](%EB%B2%95%EC%A0%81%20%EA%B7%BC%EA%B1%B0.md)에 있다.

시행령 제40조제1항은 **민감정보 또는 고유식별정보가 유출되면 건수와 무관하게 72시간 내 신고**하도록 한다(제2호). 1천명 이상이라는 건수 요건은 제1호이고 제2호에는 없다. 제3호는 외부로부터의 불법적인 접근에 의한 유출인데 BOLA 공격이 여기 해당한다.

신고서 제1호 기재사항이 "유출등이 된 개인정보의 항목"이다(법 제34조제1항제1호). **어떤 필드가 나갔는지를 72시간 안에 특정해야 한다.**

시행령 제40조제2항은 항목을 확인하지 못한 경우 우선 신고 후 보완하도록 한다. **제도가 이미 "항목 특정이 72시간 안에 안 되는 경우"를 전제하고 있다.** 그 공백이 이 도구의 자리다.

**틈 1-2 - 2026년 9월 11일부터 하나 더 생겼다.** 법 제34조제2항이 신설돼 유출 "가능성"만 있어도 통지 의무가 발생한다. 가능성 판단 기준(시행령 제39조의2제1항제1호)이 "불법적인 접근이 발생하여 유출등이 의심되나 정보주체를 특정하기 곤란한 경우"인데, BOLA 사고의 전형적 초기 상황이다.

그때 적어야 하는 첫 항목이 "유출등의 **가능성**이 있는 개인정보의 항목"이다. **사고 후에는 알아낼 수 없다. 그 엔드포인트가 평소에 무엇을 반환하는지를 미리 알고 있어야 쓸 수 있다.** 평시 모드가 필요한 법적 이유다.

**틈 2 - 구매자가 다르다. 이제 법으로 뒷받침된다.** 개인정보보호위원회 2026-09-10 보도자료에 따르면 개정법은 CPO의 직무권한을 강화해 **전문인력 관리와 예산 확보** 권한을 부여했고, CPO 지정·변경·해제 시 이사회 의결과 신고를 의무화했다. 구매 결정권이 실제로 CPO에게 이동했다.

같은 보도자료에 **사전 예방적 개인정보 보호 투자와 연계한 과징금 의무 감경제**가 도입됐다고 명시돼 있다. 도구 도입이 비용이 아니라 과징금 감경 사유가 된다. 반대편에는 반복·고의·중과실 유출에 대한 징벌적 과징금이 전체 매출액 10퍼센트 이내로 설정돼 있다.

**틈 2-2 - 수요 발생 일정이 확정돼 있다.** 같은 보도자료에서 공공·민간 부문 중요 개인정보처리자에 대한 ISMS-P 인증 의무화가 **2027년 7월 1일 시행**으로 예고됐다. 인증 준비 과정에서 API 단위 개인정보 노출 점검 수요가 발생한다. 이 프로젝트가 2026년 2학기에 시작해 2027년에 산출물을 내면 시기가 맞는다.

**틈 3 - 국내 진단 시장의 고정 수요.** ISMS-P 인증, 정보보호 공시, 취약점 진단은 규제로 수요가 고정돼 있다. 진단 업체가 지금 사람으로 하는 작업이다. B2B2B 경로로 진단 업체에 도구를 공급하는 방식은 고객 수가 적고 단가가 높으며 영업 사이클이 짧다.

### 포지셔닝

**스캐너가 아니라 개인정보 노출 진단으로 명명한다.** 같은 기술이라도 구매자와 예산 라인이 달라진다.

### 방어 가능성

- 법 분류 사전은 판례와 처분 사례를 축적해야 만들어진다. 시간이 해자다
- 외산 벤더가 한국 법 매핑을 하려면 국내 법무 리소스를 사야 한다. 국내 시장 규모상 하지 않는다
- 반대로 분류 체계만 교체하면 일본 APPI, EU GDPR로 확장된다

### 배포 형태

고객 API를 외부 SaaS가 스캔하면 계약과 인가 범위가 무겁다. 서면 위임 없는 스캔은 무단 접근이다.

**온프레미스 에이전트 + SaaS 대시보드**로 간다. 트래픽은 고객 망 안에서 처리하고 분류 결과만 올린다. 개인정보를 다루는 도구가 개인정보를 밖으로 빼면 안 된다.

### 재학 중 도달 가능한 지점

매출이 나는 SaaS는 재학 중 불가능하다. 영업, 계약, 고객이 요구하는 보안 인증이 기술보다 크다. 도달 가능한 것은 셋이다.

1. 오픈소스 코어 공개 + 벤치마크 수치를 논문으로
2. 창업 트랙 공모전(예비창업패키지, K-Startup, 학내 창업경진대회) 제출. 위 틈 논리가 그대로 사업계획서가 된다
3. 진단 업체 PoC 1곳. 매출 없이 현장 적용 사실만 확보해도 이력의 무게가 다르다. 산학협력단 또는 멘토 조재현 경유 접촉 가능성을 확인한다

## 평가 설계

상세는 [평가 설계](../../arch/%ED%8F%89%EA%B0%80%20%EC%84%A4%EA%B3%84.md)에 분리했다. 2026-09-19에 벤치마크 취약점 개수를 실측한 결과 설계를 바꿨다.

**실측 결과: 인가 취약점이 공개 벤치마크 전체에 다섯 개뿐이다.**

| 벤치마크 | 인가 취약점 | 과잉 노출 |
|---|---|---|
| crAPI | BOLA 2(챌린지 1·2), BFLA 1(챌린지 7) | 2(챌린지 4·5) |
| VAmPI | BOLA 1, 비밀번호 무단 변경 1 | 1(`/users/v1/_debug`) |

다섯 개로 recall을 재면 한 개 차이가 20퍼센트포인트다. **단순 탐지율 비교로는 결론이 안 난다.** 설계를 셋으로 바꾼다.

1. **조건 비교.** 성능이 아니라 사람의 입력량을 비교한다. ZAP에 Access Rules를 다 채운 조건(A), 안 채운 조건(B), 우리 도구에 계정 두 개만 준 조건(C)을 비교한다. C가 B보다 낫고 A에 근접하면 표본이 작아도 결론이 선다. Access Rules 작성에 든 시간도 함께 잰다
2. **오탐 별도 측정.** VAmPI는 `vulnerable=0`으로 안전 버전을 같은 구조로 띄울 수 있다. 거기서 나오는 경보는 전부 오탐이다. 정답을 만들기 어려운 지표인데 벤치마크가 구조적으로 제공한다
3. **필드 분류는 표본이 충분하다.** 엔드포인트당 응답 필드가 수십 개이므로 필드 단위로는 수백 개가 된다. Presidio를 베이스라인으로 삼아 회귀(정형 PII 누락률), 기여(Presidio 미탐지 필드 중 탐지 비율), 법적 등급 3분류 정확도를 잰다

**정답 라벨은 사람이 임의로 정하지 않는다.** [법적 근거](%EB%B2%95%EC%A0%81%20%EA%B7%BC%EA%B1%B0.md)의 조문으로 정한다. 애매한 필드는 별도 등급으로 빼고 정확도 계산에서 제외한다.

**과적합 방지.** 튜닝은 crAPI, 채점은 VAmPI와 자체 구축 API로 분리한다. 자체 API는 강남언니 구조를 모사해 비정형 민감정보 필드를 넣는다. 공개 벤치마크에 없는 것이 정확히 그것이다.

## 역할 분담 (4인)

| 담당 | 영역 |
|---|---|
| 심재훈 | 2단계 인가 탐지 로직과 LLM 판정 엔진 |
| 곽민경 | 1단계 트래픽 파싱, 엔드포인트 복원, 세션 관리 |
| 임성빈 | 3단계 개인정보 분류 사전, 법 분류 매핑, 처분 사례 수집 |
| 양유상 | 벤치마크 환경 구축, 평가 자동화, 비교군 실험 |

4단계 출력과 통합은 공동 작업으로 한다.

**제품화 전환에 따른 조정.** 3단계가 본체로 승격되면서 임성빈이 맡은 법 분류 사전이 프로젝트에서 가장 값나가는 자산이 된다. 인력 배분을 재검토할 여지가 있다.

**심재훈 역할 관련 미결 사항.** 초안에서는 LLM 판정 엔진 단독이었으나 인가 탐지 로직을 포함하도록 조정했다. LLM 프롬프트 설계는 캡스톤 PromptShield에서 이미 수행 중이라 새로 얻는 학습이 적고, 웹 취약점 감각은 탐지 로직 쪽에서 붙는다. 팀 논의로 확정 필요.

## 리스크

1. **상태 의존 요청 순서.** BOLA 테스트는 A로 생성한 리소스 ID를 B로 접근해야 한다. 생성과 참조의 의존 순서를 자동으로 푸는 것이 최대 난관이다. 트래픽 기반이면 이미 관측된 ID를 재사용할 수 있어 부담이 줄지만, 완전 자동화는 포기하고 반자동으로 시작한다
2. **LLM 비용.** 엔드포인트 수 곱하기 역할 수 곱하기 변조 시나리오로 증가한다. 정적 프리필터 없이는 감당하지 못한다
3. **법 분류의 경계.** 화해 유출 항목인 "피부 고민 및 타입"이 건강정보인지 판단이 갈린다. 판례나 개인정보보호위원회 해설서로 근거를 확보하고, 애매한 항목은 별도 등급으로 분리한다
4. **진단 대상의 인가 범위.** 벤치마크 외의 실제 서비스에 도구를 돌리려면 서면 동의가 필요하다. 동의 없는 스캔은 그 자체가 위법이다. 실증은 자체 구축 환경과 공개 취약 앱으로 한정한다
5. **캡스톤과의 구분.** PromptShield는 LLM을 방어하는 것, 이 프로젝트는 LLM으로 API를 진단하는 것이다. 제안서에 한 줄로 명시한다
