## For future Claude

2026-09-18 최한림 교수가 ChatGPT "API 보안 오픈소스 비교" 링크를 보내며 "이런거랑은 다른거야?"라고 물은 데 대한 답으로, 심재훈이 선행 솔루션 6종을 공식 문서와 저장소로 직접 확인한 기록이다. 교수에게 그대로 보낼 수 있는 형태로 정리했다. 핵심 결론은 "인가 테스트 도구는 이미 있으나 전부 정답을 사람이 먼저 입력해야 한다"이며, 이 프레임이 [API 인가 취약점 진단 및 개인정보 노출 영향도 산정](API%20%EC%9D%B8%EA%B0%80%20%EC%B7%A8%EC%95%BD%EC%A0%90%20%EC%A7%84%EB%8B%A8%20%EB%B0%8F%20%EA%B0%9C%EC%9D%B8%EC%A0%95%EB%B3%B4%20%EB%85%B8%EC%B6%9C%20%EC%98%81%ED%96%A5%EB%8F%84%20%EC%82%B0%EC%A0%95.md)의 독자 기여 1항 근거다. 2026-09-19에는 팀원 양유상의 요구로 국산 제품 3종을 추가 조사했고, "한국 솔루션이 없다"가 아니라 "국산 DLP와 국제 API 보안 사이가 비어 있다"로 주장을 좁혔다. 모든 확인은 해당 날짜 기준이며 이후 제품 업데이트로 달라질 수 있다.

# 선행 솔루션 조사 (국제 2026-09-18, 국산 2026-09-19 기준)

## 요약

인가를 테스트하는 도구는 이미 존재한다. 다만 **"누가 무엇에 접근해도 되는가"라는 정답을 사람이 먼저 입력해야 동작한다.** 민감정보 분류도 Akto에 이미 있다. 다만 한국 법 체계 기준이 아니고 정규식 기반이다.

## 비교표

| 도구 | 인가 테스트 | 민감정보 분류 | 사람이 넣어야 하는 것 |
|---|---|---|---|
| ZAP Access Control Testing | 있음 | 없음 | 사용자별로 페이지마다 Allowed, Denied, Unknown |
| Autorize (Burp) | 있음 | 없음 | 저권한 세션 헤더, 판정용 응답 매칭 필터 |
| Akto | 있음 | 있음 | 인증 컨텍스트 |
| Wallarm API Firewall | 없음 | 없음 | OpenAPI 명세 |
| open-appsec | 없음 | 없음 | 해당 없음 (런타임 방어) |
| Schemathesis | 없음 | 없음 | OpenAPI 또는 GraphQL 스키마 |

## 도구별 확인 내용

### ZAP Access Control Testing

https://www.zaproxy.org/docs/desktop/addons/access-control-testing/

공식 문서 원문:

> In order to identify potential access control issues, ZAP needs to know which parts of the web application are supposed to be accessed by which user.

테스트 절차도 문서에 나열돼 있다. 테스터가 사용자 집합과 인증 방식을 정의하고, 비인가 요청을 식별하는 방법을 정의하고, **각 사용자에 대해 Access Rules를 직접 작성한다.** 그 표가 있어야 위반 판정이 나온다.

규칙 값은 Allowed, Denied, Unknown 세 가지다. URL 트리 구조를 이용해 상위 노드 규칙을 하위로 추론하지만, 최초 정의는 사람이 한다.

### Autorize (Burp 확장)

https://github.com/PortSwigger/autorize
원본 저장소: https://github.com/Quitten/Autorize

동작 방식은 README의 Basic Workflow에 있다. 테스터가 **저권한 사용자의 인증 헤더(쿠키 또는 Bearer 토큰)를 직접 입력**하고, 고권한 사용자로 애플리케이션을 브라우징한다. Autorize가 요청을 저권한 헤더로 바꿔 재전송하고 응답을 비교한다.

판정은 자동으로 나온다. `Bypassed!`(인가 미적용), `Enforced!`(정상 적용) 상태로 표시된다. 다만 이 판정은 테스터가 설정한 응답 매칭 필터를 기준으로 하므로, 필터 설계가 결과를 좌우한다.

### Akto

https://github.com/akto-api-security/akto
민감정보 정의: https://github.com/akto-api-security/akto/tree/master/pii-types

README 원문:

> Akto offers coverage for all OWASP top 10 and HackerOne Top 10 categories including BOLA, authentication, SSRF, XSS, security configurations, etc.

**BOLA 테스트를 제공한다.** 트래픽 데이터를 읽어 패턴을 이해하는 방식으로 오탐을 줄인다고 설명한다.

민감정보 분류도 있다. `pii-types/fintech.json` 실제 항목 예시:

```json
{"name": "US Medicare Health Insurance Claim Number",
 "regexPattern": "[0-9]{9}[A-Za-z]{1}[0-9a-zA-Z]?",
 "sensitive": false, "onKey": false, "active": false,
 "tagsLists": ["PII", "HEALTHCARE"],
 "dataTypePriority": "HIGH"}
```

`tagsLists`로 PII, FINANCE, HEALTHCARE를 구분하고 `dataTypePriority`로 CRITICAL, HIGH, MEDIUM 등급을 매긴다.

**정의된 유형에 한국이 없다.** 확인한 항목은 인도 PAN, 미국 Medicare, 인도 UHID, 영국 National Insurance, 핀란드 개인식별번호, 캐나다 SIN, 독일 보험번호, 일본 사회보험번호, IBAN, 미국 주소다. 주민등록번호는 없다. 개인정보보호법 제23조 민감정보와 제24조 고유식별정보 구분도 없다.

항목 다수가 `"active": false`로 기본 비활성 상태다.

### Wallarm API Firewall

https://github.com/wallarm/api-firewall

저장소 설명 원문:

> Fast and light-weight API proxy firewall for request and response validation by OpenAPI specs.

OpenAPI 명세에 맞는지 대조해 검증하고 차단한다. 명세가 있어야 하고, 인가 테스트는 하지 않는다.

### open-appsec

https://github.com/openappsec/openappsec

공식 설명 원문:

> Upon every HTTP request, all parts are decoded, JSON and XML sections are extracted, and any IP-level access control is applied.
>
> Multiple variables are fed to the machine-learning engine. These variables... include attack indicators, IP addresses, user agents, fingerprints, and many other considerations.

**요청 단위로 공격 지표를 찾는 런타임 방어다.** BOLA 공격 요청은 형식이 완전히 정상이라 공격 지표가 남지 않는다. 이 계층에서는 구조적으로 탐지되지 않는다.

NGINX, Kong, APISIX, Envoy에 애드온으로 배포된다. 저장소 토픽에 `waf`, `web-application-firewall`, `threat-prevention`이 달려 있다.

### Schemathesis

https://github.com/schemathesis/schemathesis

README의 "What problems does it solve?" 항목 전체:

- 500 errors that crash your API on edge case inputs
- Schema violations where your API returns different data than documented
- Validation bypasses where invalid data gets accepted
- Integration failures when responses don't match client expectations
- Stateful bugs where operations work individually but fail in realistic workflows

인가는 목록에 없다.

## PII 가드레일 계열 (2026-09-19 확인)

팀원 양유상이 "PII 가드레일 냄새가 난다"고 지적해 확인했다. 정확한 지적이었다.

### Microsoft Presidio

https://github.com/microsoft/presidio

스타 10.9k. 저장소 설명 원문:

> Context aware, pluggable and customizable PII de-identification service for text and images.

> Predefined or custom PII recognizers leveraging Named Entity Recognition, regular expressions, rule based logic and checksum with relevant context in multiple languages.

저장소 토픽에 `guardrails`, `pii-detection`, `named-entity-recognition`이 달려 있다. **정규식뿐 아니라 NER로 맥락까지 본다.**

**이 발견이 주장 하나를 무너뜨린다.** "비정형 필드는 정규식으로 못 잡으니 LLM이 필요하다"는 논리는 Presidio 앞에서 약하다. Presidio가 이미 맥락 인식 NER을 한다.

### 축을 다시 좁힌다

Presidio는 **값이 어떤 엔티티인가**를 판정한다. `PERSON`, `PHONE_NUMBER`, `LOCATION` 같은 유형을 찾는다.

강남언니 유출 항목은 다르다.

```
"상담_동기": "코가 낮은 게 신경 쓰여서요"
"시술_의사_식별값": "DR-2841"
```

**이 값에는 PII 엔티티가 없다.** 이름도 번호도 주소도 없어서 Presidio를 돌려도 아무것도 안 나온다. 그런데 성형외과 상담 기록이므로 개인정보보호법 제23조 민감정보(건강)에 해당한다.

**값이 아니라 필드가 놓인 맥락이 법적 등급을 결정한다.** 이 지점이 남은 공백이다.

| | 판정 대상 | 강남언니 상담 동기 |
|---|---|---|
| Presidio | 값이 어떤 엔티티인가 | 탐지 안 됨 |
| Akto | 값이 어떤 패턴인가 | 탐지 안 됨 |
| 이 프로젝트 | 이 필드가 어떤 법적 등급인가 | 민감정보 제23조 |

### 평가 설계에 반영

**Presidio를 베이스라인으로 삼는다.** 같은 응답 본문을 Presidio와 우리 분류기에 각각 넣고, Presidio가 놓친 필드를 우리가 잡는지 수치로 비교한다. 주장이 아니라 측정으로 답할 수 있게 된다.

Presidio 문서의 경고도 그대로 쓸 수 있다.

> there is no guarantee that Presidio will find all sensitive information

### 한국어 지원 확인 (2026-09-19)

**한국어 Presidio 작업은 이미 존재한다.** 확인한 것들이다.

- `siwoo-jung/microsoft_presidio_kr_rrn_tutorial` - 주민등록번호 인식기 튜토리얼 저장소
- wikidocs "AI에 올리기 전 개인정보 지우기" - 한국어 책. 03장이 Presidio Analyzer, 03-2가 주민등록번호 인식기 직접 만들기
- "Building a Korean PII Detection Pipeline with Presidio + spaCy" 기술 글

즉 **정형 개인정보는 Presidio에 한국 recognizer를 붙이면 해결된다.** 우리가 새로 만들 영역이 아니다.

### 이것이 3단계 설계를 바꾼다

정규식 계층을 직접 구현하지 않는다. **Presidio와 공개된 한국 recognizer를 가져다 쓰고, 그 위에 법적 등급 판정 계층만 올린다.**

| 계층 | 담당 | 출처 |
|---|---|---|
| 정형 PII 탐지 | Presidio + 한국 recognizer | 기존 오픈소스 |
| 비정형 필드 맥락 판정 | LLM | 이 프로젝트 |
| 개인정보보호법 등급 매핑 | 분류 사전 | 이 프로젝트 |
| 신고 의무 발생 판정 | 시행령 제40조제1항 적용 | 이 프로젝트 |

범위가 줄어든다. 2026-09-17 팀 빌딩에서 받은 "범위를 좁혀라" 지적에 부합한다.

### 구현 함정: 주민등록번호 체크섬

wikidocs 문서에서 확인한 내용이다.

> 2020년 10월부터 뒷자리 부여 방식이 바뀌었습니다. 성별 표시 첫 자리를 제외한 나머지 6자리가 임의번호로 부여되면서 지역표시번호가 사라졌습니다. 마지막 검증번호 자리도 이 6자리 안에 들어 있으므로, 그 이후 신규 발급·변경된 번호는 옛 체크섬 규칙과 맞지 않을 수 있습니다.

**체크섬을 통과 조건으로 쓰면 2020년 10월 이후 번호를 놓친다.** 탐지 도구에서 놓침은 곧 유출이다.

해당 문서의 처리 방식은 체크섬을 가중치로만 쓰는 것이다. 통과하면 점수를 올리고, 실패해도 탐지는 유지한다. `validate_result`가 `True`/`False`/`None` 세 값을 반환하며, 체크섬 실패 시 `False`가 아니라 `None`을 돌려 기본 점수를 유지한다.

**우리 분류 사전도 같은 방식을 따라야 한다.** 이 함정을 모르고 만들면 최근 발급 주민등록번호를 통째로 놓친다.

### Presidio 관리 주체 변경

2026년 현재 Microsoft에서 커뮤니티 조직 Data Privacy Stack으로 이관 중이다. 저장소 주소와 컨테이너 레지스트리가 바뀌었다. `github.com/microsoft/presidio` 접근 시 `data-privacy-stack/presidio`로 리다이렉트되는 것을 직접 확인했다. **오래된 블로그의 설치 명령을 그대로 쓰면 안 된다.**

### 한계

- Presidio의 한국어 NER 모델 품질은 확인하지 못했다. 커스텀 recognizer로 한국 유형을 추가할 수 있으므로, 누군가 그 작업을 이미 했는지는 별도 확인이 필요하다
- Lakera Guard, Nightfall 등 상용 가드레일 제품은 확인하지 않았다

## 국산 제품 (2026-09-19 확인)

팀원 양유상이 "한국에 대한 솔루션이 부족한 부분이 명확해지면 결정하자"고 요구해 추가 조사했다. **결론부터: 한국 솔루션이 없는 것이 아니다. 축이 다르다.**

### 이지서티 U-PRIVACY SAFER V3.0

https://www.easycerti.com/02-04.product_up3.0.html

개인정보 필터링 솔루션이다. 제품 페이지 원문:

> HTTP/HTTPS 구간에서 개인정보를 실시간으로 탐지하고 차단합니다. 웹사이트 게시판, 첨부파일 업로드 등 다양한 경로를 감지해 사고 발생 전, 선제적으로 대응할 수 있습니다.

> Web/WAS 환경은 물론, Proxy, In-Line, API 방식까지 지원하여 클라우드 등 모든 플랫폼에서도 안정적으로 운영할 수 있습니다.

> 개정되는 개인정보보호법의 가이드를 따를 수 있습니다.

**배치가 우리와 겹친다.** 인라인 프록시로 HTTP 구간을 검사하고 개인정보보호법 준수를 내세운다. 경찰청 온나라 2.0, 외교부, 경기 생성형AI 플랫폼에 공급된 실적이 보도돼 있다.

같은 회사의 다른 제품으로 UBI SAFER-PSM(개인정보 접속기록관리), IDENTITY SHIELD(가명·익명처리), UBI SAFER-IMS(소명관제)가 있다.

**차이는 목적이다.** 이지서티는 DLP다. 개인정보가 밖으로 나가는 것을 막는다. 게시판 업로드, 첨부파일, 다운로드 이력이 대상이다.

**인가 판정 기능은 확인되지 않는다.** 개인정보가 API로 오가는 것은 정상 업무다. 문제는 그것이 요청자의 것이 아닐 때인데, DLP는 그 구분을 하지 않는다. open-appsec과 같은 구조적 한계다. 정상 형식의 요청은 걸러지지 않는다.

### 소프트프릭 파핌 게이트웨이

http://softfreak.kr/

API 게이트웨이 보안 솔루션으로 GS인증 1등급을 획득했다고 보도됐다. **홈페이지에 제품 상세 설명이 없어 기능은 미확인이다.** 국산 API 게이트웨이 보안 제품이 실재한다는 사실만 확인했다.

### 위베어소프트

API 보안 솔루션 개발사로 스파크랩 시드투자를 유치했다고 보도됐다. **제품 내용 미확인.**

### 정리

| 구분 | 보는 것 | 목적 | 인가 판정 |
|---|---|---|---|
| 국산 DLP (이지서티 등) | 이 트래픽에 개인정보가 있나 | 유출 차단 | 없음 |
| 국제 API 보안 (Akto 등) | 이 엔드포인트가 남의 토큰으로 열리나 | 취약점 발견 | 있음 |
| 이 프로젝트 | 둘 다. 그리고 곱한다 | 수정 우선순위 | 자동 생성 |

주장을 다시 좁힌다.

| 쓰면 안 되는 말 | 써도 되는 말 |
|---|---|
| 한국에는 솔루션이 없다 | 국산 DLP는 개인정보를 보지만 그것이 남의 것인지는 구분하지 않는다 |
| 아무도 영향도를 안 센다 | 인가 취약 여부와 유출 범위를 묶어 엔드포인트 단위 순위를 내는 것이 비어 있다 |

### 리스크

이지서티가 이미 `API 방식 지원`을 광고한다. **그쪽에서 인가 판정까지 확장하면 정면 경쟁이 된다.** 현재는 하지 않지만 못 할 이유가 없다. 제안서와 발표에서 이 사실을 숨기지 않는다.
