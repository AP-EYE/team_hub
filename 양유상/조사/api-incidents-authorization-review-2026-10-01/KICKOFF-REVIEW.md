## 3. 왜 정책 근거가 전혀 없으면 확정이 어려운가

동일한 관측을 만드는 두 서비스를 생각할 수 있다.

- 서비스 A: 문서 소유자가 B에게 공유했다. B의 요청에 문서 본문이 반환된다.
- 서비스 B: 공유하지 않았는데 객체 권한 검사가 빠졌다. B의 요청에 똑같은 본문이 반환된다.

진단기에 공유 상태·정책·생성 조건이 주어지지 않고 두 HTTP 트래픽이 같다면, 트래픽만 사용하는 방법은 두 사례에 같은 결론을 낼 수밖에 없다. 하나를 정상, 하나를 위반으로 구분하려면 추가 근거 또는 적용 범위의 가정이 필요하다. 이는 이 보고서의 구별 불가능성 설명이며 새 정리나 실험 결과를 주장하는 것은 아니다.

실제로 [RoleCast, OOPSLA 2011, §3.3](https://www.cs.utexas.edu/~mckinley/papers/rolecast-oopsla-2011.pdf)은 정책·annotation 없이 보호가 필요한 조회와 정상 공개 조회를 구별하기 어렵다는 이유로 해당 분석에서 SELECT/SHOW를 제외한다. [AuthScope, §4.3](https://acmccs.github.io/papers/p799-zuoA.pdf)는 공개 응답으로 인한 오탐을 줄이기 위해 비로그인 실행도 비교한다. 다만 비로그인 접근이 거부되어도 로그인 사용자 간 합법 공유 여부까지 해결되는 것은 아니다.

따라서 유망한 질문은 “정책을 완전히 없앨 수 있는가?”보다 **“어떤 최소 근거를 언제 추가하면 얼마의 설정 비용으로 어떤 오탐·누락을 줄일 수 있는가?”**다. 소수 테스트 객체의 비공개 선언도 정책 입력이다. 이를 숨기지 않고 정책 정보량과 설정 시간을 함께 측정해야 학술 비교가 가능하다.

## 4. 현재 코드와 발표 목표의 관계

[현재 아키텍처](../../데모코드/docs/architecture.md)는 FastAPI/HTTPX 로컬 프록시, 합성 업무 API, 검토된 정책·필드 매핑, PostgreSQL, 로컬 분류기를 설명한다. 인가 위반 확정은 정책과 실제 응답 증거를 요구하고 LLM은 확정 주체가 아니다. 공개·공유 반례와 `needs_review`가 이미 존재한다.

이번 조사로 확인한 것은 설계·코드 문서의 범위와 문헌·사건 근거다. 이번에 새로 운영 배포, 외부 API 공격, 모델 추론, 정확도 실험, 법적 분류 검증을 실행한 것은 아니다. 제안은 [통합 보고서](RESEARCH-REPORT.md)의 반증 가능한 실험으로 다음 검증을 진행해야 한다.
