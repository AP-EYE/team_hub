# API 인가 진단 선행연구의 발전과 판정 근거의 한계

조사 기준일: **2026-10-01, 한국 시간**. 논문·학회·저자·연구기관의 원문을 우선 확인했다. 아래는 대표 연구를 선별한 서술형 조사이며, 모든 연구를 빠짐없이 포함하는 체계적 문헌고찰은 아니다. 논문에서 실제 확인한 범위를 `원문`, 이를 AP-EYE에 적용하면서 도출한 판단을 `분석`으로 구분한다. 연구 성과 수치는 저자 보고이며 AP-EYE 재현 결과가 아니다.

## 1. 먼저 구분해야 할 네 가지 문제

인가 연구는 한 방향으로 교체된 것이 아니라 다음 네 갈래가 병행 발전했다.

1. **정책 표현·집행:** 누가 어떤 자원에 어떤 행위를 해도 되는지를 RBAC·ABAC·ReBAC 등으로 표현하고 집행한다. 모델이 풍부해졌다고 실제 서비스의 누락된 인가 검사가 저절로 발견되는 것은 아니다.
2. **명시 정책의 검증:** 작성한 정책에 모순·과도한 권한·금지된 상태가 없는지, 구현이 정책을 따르는지 검사한다. 잘못된 정책을 정확히 집행하는 문제는 구현 검사만으로 해결되지 않는다.
3. **명세가 부족한 구현의 진단:** 코드의 일관성, 클라이언트 제약, 사용자별 트래픽 차이, 객체 관계를 이용해 누락된 검사를 찾는다. 사전 권한표를 줄여도 다른 가정이나 관측 조건은 남는다.
4. **실제 노출·변경 영향의 확인:** 거부되어야 할 호출에서 어떤 객체·필드가 실제 반환되거나 변경됐는지, 어느 요청자에게 노출됐는지 확인한다. 엔드포인트 발견률·HTTP 500 탐지·테스트 성공률과 별도의 평가 과제다.

AP-EYE가 연구 가치를 주장하려면 이 중 **어느 문제의 어떤 오류를 줄이는지**를 정해야 한다. “API 트래픽을 수집한다”, “토큰을 교환한다”, “응답을 비교한다”, “권한표 작성을 줄인다”는 기능만으로는 신규성을 주장하기 어렵다. 아래 RoleCast·AuthScope·RESTler 보안 checker·정책 역공학 연구가 이미 각각의 선행 근거다.

## 2. 발전 흐름

| 시기 | 해결하려던 문제 | 대표 연구 | 다음 단계로 남은 문제 |
|---|---|---|---|
| 1990년대–2010년대 초 | 권한을 사용자별 목록보다 일관되게 표현·관리 | RBAC, ReBAC; 이후 ABAC 정리 | 표현된 정책의 정확성과 실제 구현의 누락은 별개 |
| 2009–2011 | 정책을 검증하거나, 정책을 모두 작성하지 않고 검사 후보를 찾기 | ACPT, NoTamper, WAPTEC, RoleCast | 추론한 제약이 업무상 의도와 일치하는지; 실제 효과 확인 |
| 2016–2019 | 전형적 패턴·다중 사용자·서비스 간 일관성으로 인가 누락 찾기 | SPACE, AuthScope, ACMiner | 공개·공유의 예외, 읽기/쓰기 범위, 언어·플랫폼 종속성 |
| 2019–2022 | API 명세에서 유효한 호출 순서를 생성하고, 특정 보안 속성·실제 정책을 검사 | RESTler, 보안 checker, RESTTESTGEN, RESTest, RBAC 정책 역공학 | 요청 생성의 품질과 인가 정답 판정의 품질을 분리해야 함 |
| 2024–2026 | 객체 관계 복원, 명세–로그 적합성, 다중 계정의 구체적 증거를 강화 | BolaRay, Links2CPN, AuthProbe | 가정·명세·로그의 불완전성, 정상 공유·상태 변화, 외적 타당성 |

## 3. 정책 모델과 명시 정책 검증: 진단기와 구별할 선행연구

### H01. RBAC — Ferraiolo·Kuhn, 1992; Sandhu 등, 1996

- **출판 상태·분야:** 1992 National Computer Security Conference 논문; 1996 IEEE Computer의 RBAC 모델 계열. 인가 **모델** 연구다.
- **입력·접근권한:** 사용자–역할–권한 관계와 제약. 서비스 소스나 트래픽을 자동으로 발견하는 방법이 아니다.
- **방법·판정 기준:** 역할을 통해 권한을 부여하고, 계층·제약·세션 활성화 등을 모델링한다.
- **원문 경계:** 역할은 필요한 조건으로 쓰이며 추가 제약을 붙일 수 있다. “RBAC은 객체별 관계를 원리상 표현할 수 없다”는 식의 설명은 부정확하다.
- **AP-EYE 분석:** 같은 `user` 역할의 A·B 사이에도 소유·공유·조직 조건이 다르므로, 역할표만으로 객체 인가의 정답을 채우면 안 된다.
- **근거:** [NIST 1992 논문·서지](https://www.nist.gov/publications/role-based-access-controls), [NIST의 1992/1996 모델 및 추가 제약 설명](https://csrc.nist.gov/Projects/role-based-access-control/faqs).

### H02. ReBAC — Fong, 2011

- **출판 상태·분야:** *Relationship-Based Access Control: Protection Model and Policy Language*, CODASPY 2011. 관계 기반 정책 모델·언어 연구다.
- **입력·접근권한:** 주체와 자원 소유자 사이의 관계 및 정책. 사전 의미를 가진 관계 그래프가 필요하다.
- **방법·판정 기준:** 관계를 명시적으로 표현해 접근 결정을 내린다.
- **원문 경계:** 출판사 서지와 저자 연구 목록에서 제목·연도·학회는 확인했으나, 이번 조사에서 저자 페이지의 전체 PDF 링크는 열리지 않았다. 세부 알고리즘·성능 수치를 추정하지 않았다.
- **AP-EYE 분석:** `actor != owner`라는 사실은 인가 위반의 충분조건이 아니다. 정상 공유·대리·구성원 관계를 나타내는 증거가 별도로 필요하다.
- **근거:** [학회 공식 프로그램](https://www.codaspy.org/2011/program.html), [저자 연구 목록](https://cspages.ucalgary.ca/~pwlfong/Research/), [출판 DOI](https://doi.org/10.1145/1943513.1943539).

### H03. ABAC — NIST SP 800-162, 2014, 2019 갱신

- **출판 상태·분야:** NIST 기술 지침. 학회 진단 논문이나 ABAC의 최초 발명 시점으로 세지 않는다.
- **입력·접근권한:** 주체·객체·요청 행위·환경 속성과 정책.
- **방법·판정 기준:** 속성 조합을 정책 규칙에 대조해 허용 여부를 결정한다.
- **원문 경계:** 정책을 정의하는 접근이다. 속성 출처가 정확한지, 응답이 다른 사용자의 데이터인지 자동 입증하는 스캐너가 아니다.
- **AP-EYE 분석:** 인가 판단의 맥락은 토큰의 역할 외에도 테넌트, 자원 상태, 공유 조건, 적용 시점을 포함할 수 있다. 필요한 속성이 로그에 없으면 `needs_review`를 허용해야 한다.
- **근거:** [NIST 설명·2019 갱신](https://www.nist.gov/publications/guide-attribute-based-access-control-abac-definition-and-considerations-0), [SP 800-162 원문](https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-162.pdf).

### H04. ACPT — Hwang·Xie·Hu·Altunay, POLICY 2010; NIST SP 800-192, 2017

- **입력·접근권한:** 사용자가 기술한 정책 모델·안전 속성·입력 변수 영역.
- **방법:** 정책 모델 검사와 조합 테스트 생성 등을 결합해 정책 검증과 구현 테스트를 지원한다.
- **인가 oracle:** 명시한 정책·안전 요구사항. 여기서 oracle은 **기대 허용/거부 결과를 정하는 근거**를 뜻한다.
- **원문 경계:** NIST는 정책 자체의 잘못된 설정과 구현 실패를 구분하고, 정책이 작성자 의도를 제대로 담는지 검증할 필요를 설명한다.
- **AP-EYE 분석:** 사람이 승인한 정책을 쓰는 방식은 비교 기준선으로 유효하다. 다만 그 정책을 절대적 진실로 놓지 말고, 정책 버전·검토 상태·업무 담당자 합의를 기록해야 한다.
- **근거:** [소속 대학 서지: POLICY 2010, DOI 10.1109/POLICY.2010.22](https://experts.illinois.edu/en/publications/acpt-a-tool-for-modeling-and-verifying-access-control-policies/), [NIST ACPT 설명](https://www.nist.gov/programs-projects/access-control-policy-testing-acpt), [SP 800-192 §6](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-192.pdf).

## 4. 정책이 불완전할 때 구현을 진단하는 연구

### H05. NoTamper — Bisht 등, CCS 2010

- **입력·접근권한:** 웹 클라이언트의 폼·입력 제약과 서버에 요청을 보낼 수 있는 테스트 환경. 서버 소스 불필요.
- **방법:** 클라이언트가 제한한 입력을 변조해 서버가 받아들이는지 검사한다.
- **인가 oracle:** 클라이언트 제약과 서버 수용의 불일치. **변조 기회**를 찾는 기준이며 모든 결과가 인가 취약점이라는 뜻은 아니다.
- **원문 한계:** 논문은 수용된 입력을 사람이 검토해 실제 취약점·익스플로잇을 확인하는 단계를 설명한다.
- **AP-EYE 분석:** “서버가 200을 반환했다”와 “금지된 데이터/행위가 실제 발생했다”를 분리해야 한다는 초기 선행 근거다. 파라미터 변조 연구 전체를 BOLA 전용 연구로 소개하지 않는다.
- **근거:** [저자 PDF, 평가 부분](https://www.cs.uic.edu/~venkat/research/papers/NoTamper-ccs2010.pdf), [CCS 2010 공식 논문 목록](https://www.sigsac.org/ccs/CCS2010/paper_list.shtml).

### H06. WAPTEC — Bisht 등, CCS 2011

- **입력·접근권한:** 클라이언트 제약과 서버 소스. 화이트박스 분석이다.
- **방법:** 클라이언트·서버 검증을 분석하고 제약을 풀어 파라미터 변조 익스플로잇을 구성한다.
- **인가 oracle:** 클라이언트보다 약한 서버 검증 및 분석으로 구성한 구체적 취약 실행. 임의의 조직별 업무 권한표 전체를 추론하는 방식은 아니다.
- **원문 범위:** 6개 오픈소스 애플리케이션에서 평가했다. NoTamper의 후보 검토 부담을 줄이려는 후속 방향이다.
- **AP-EYE 분석:** 소스 없는 게이트웨이 방식과 입력 접근권한이 다르다. 동일 도구끼리처럼 숫자를 직접 비교하지 말고, 소스 접근 비용과 런타임 증거를 별도 축으로 비교한다.
- **근거:** [연구실 제공 전체 PDF](https://sisl-lab.red.uic.edu/wp-content/uploads/sites/330/2018/07/WAPTEC.pdf), [저자 서지·DOI](https://www.cs.uic.edu/~venkat/publications.html).

### H07. RoleCast — Son·McKinley·Shmatikov, OOPSLA 2011

- **입력·접근권한:** PHP/JSP 서버 소스. 사전에 보안 검사 함수 목록이나 외부 권한 정책을 모두 작성할 필요가 없다.
- **방법:** 보안상 중요한 DB 변경 연산, 역할에 대응하는 코드 문맥, 인가 관련 변수·분기를 찾아 역할 내부의 검사 일관성을 비교한다.
- **인가 oracle:** 같은 역할 문맥에서 기대되는 검사 패턴. 실제 업무 권한의 독립적 정답과 동일하지 않다.
- **원문 한계:** §3.3은 **정책/주석 없이 보호할 조회와 합법 공개 조회를 구분하기 어려워 SELECT/SHOW를 제외**한다고 설명한다. §5는 어떤 변수를 검사하는지만 보고 검사식 자체가 틀린 경우를 놓칠 수 있다고 명시한다.
- **AP-EYE 분석:** “기존 도구는 모두 사람이 권한표를 먼저 작성해야 한다”는 주장의 반례다. 동시에 정책을 줄이는 과정에서 어떤 범위를 포기했는지 밝혀야 한다는 근거다.
- **근거:** [저자 PDF, §3.3·§5·§9](https://www.cs.utexas.edu/~mckinley/papers/rolecast-oopsla-2011.pdf), [OOPSLA 공식 프로그램](https://2011.splashcon.org/details/oopsla-2011-papers/62/RoleCast-Finding-Missing-Security-Checks-When-You-Do-Not-Know-What-Checks-Are).

### H08. SPACE — Near·Jackson, ICSE 2016

- **입력·접근권한:** Ruby on Rails 소스와 애플리케이션 타입을 보안 패턴 타입으로 연결하는 사용자 매핑.
- **방법:** 심볼릭 실행으로 데이터 읽기·쓰기 노출 조건을 뽑고, 소유·공개 객체·명시 권한·관리자 등의 패턴과 Alloy bounded verification으로 대조한다.
- **인가 oracle:** 내장 보안 패턴과 사용자 제공 타입·관계 매핑. 저자의 `specification-free`는 어떤 의미 가정도 없다는 뜻이 아니다.
- **원문 범위:** 50개 Rails 저장소에서 33개 후보 중 23개 새 보안 버그와 10개 오탐을 보고했다.
- **AP-EYE 분석:** 응답 데이터에 소유·공유 관계를 매핑하는 발상은 선행이 있다. 차별점은 운영 관측의 누락·상충·버전 변화에서 오류나 검토 비용을 얼마나 줄이는지로 정해야 한다.
- **근거:** [저자 원문, §2–§5](https://groups.csail.mit.edu/sdg/pubs/2016/access-control-patterns-icse2016.pdf), [DOI 10.1145/2884781.2884836](https://doi.org/10.1145/2884781.2884836).

### H09. AuthScope — Zuo·Zhao·Lin, CCS 2017

- **입력·접근권한:** Android 앱, 테스트 계정 두 개, 앱 실행 및 HTTP/HTTPS 트래픽 관측·변조. 서버 소스 불필요.
- **방법:** 차분 트래픽 분석으로 사용자 관련 필드를 식별하고 교환한 뒤, 피해자 계정의 기준 응답과 비교한다.
- **인가 oracle:** 사용자 특정 데이터가 기준 응답과 일치하는지 확인하며, 비로그인 실행으로 공개 리소스 후보를 제거한다.
- **원문 한계:** §4.3은 공개 리소스 오탐을 직접 다룬다. §7은 Facebook 로그인 중심의 탐색, 미탐, 비인가 쓰기 자동 추론 미지원, Android·HTTP/HTTPS 범위를 명시한다.
- **AP-EYE 분석:** **트래픽 기반 다중 사용자 비교와 실제 타 사용자 응답 확인은 2017년에 이미 존재**한다. 정상 공유·위임과 잘못된 공개 설정까지 일반적으로 해결됐다고 확대할 수도 없다. 후자는 본 조사자의 적용 범위 분석이다.
- **근거:** [학회 제공 원문, §4.3·§5·§7](https://acmccs.github.io/papers/p799-zuoA.pdf), [DOI 10.1145/3133956.3134089](https://doi.org/10.1145/3133956.3134089).

### H10. ACMiner — Gorski 등, CODASPY 2019

- **입력·접근권한:** Android 시스템 이미지/미들웨어 코드 표현, 분석 설정과 문맥 쿼리 정의.
- **방법:** 프로그램·텍스트 분석으로 인가 검사를 추출하고 서비스 단위 연관 규칙으로 불일치를 찾는다.
- **인가 oracle:** 유사 서비스 진입점에서 일관되게 요구되는 검사. 불일치는 취약점 후보이며 추가 해석이 필요하다.
- **원문 범위:** Android 미들웨어 보호 정책의 집행을 평가하는 도구다. 일반 REST API의 원격 블랙박스 인가 스캐너가 아니다.
- **AP-EYE 분석:** 여러 엔드포인트 사이의 정책 불일치 탐지에는 참고할 수 있다. 정상 관행 자체가 일관되게 잘못됐다면, 일관성만으로 의도된 정책을 복구할 수 있다는 보장은 없다.
- **근거:** [연구실 공식 설명·CODASPY 2019 서지·입력](https://wspr.csc.ncsu.edu/acminer/), [저자 확장 원문 arXiv:1901.03603](https://arxiv.org/abs/1901.03603).

### H11. Zanzibar — Pang 등, USENIX ATC 2019

- **분류:** 인가 진단기가 아니라 분산 인가 **집행 시스템** 연구다.
- **입력:** 객체–사용자/객체–객체 관계 튜플, 정책 구성, ACL 변경과 콘텐츠 변경의 순서.
- **방법·정답 기준:** 관계 평가뿐 아니라 변경의 인과 순서를 존중하는 일관성을 제공한다.
- **원문 범위:** Google 서비스에서의 설계·배포·운영 평가다. 모든 다른 시스템의 캐시·복제 오류를 자동 검출하는 연구가 아니다.
- **AP-EYE 분석:** “이 사용자가 원래 권한이 있었는가” 외에 **그 요청 시점에는 권한이 철회됐는가**, 어떤 정책·데이터 버전으로 응답했는가를 시험할 근거다. ACL 변경 전후의 조회 실험은 단발 토큰 교환보다 다른 오류를 측정한다.
- **근거:** [USENIX 원문·학회 서지](https://www.usenix.org/conference/atc19/presentation/pang).

## 5. REST API 자동 테스트: 생성기와 인가 판정기를 분리하기

### H12. RESTler 기본 연구 — Atlidakis·Godefroid·Polishchuk, ICSE 2019

- **입력·접근권한:** OpenAPI/Swagger 명세, 테스트 대상 서비스 접근, 필요한 인증 구성.
- **방법:** 요청 간 producer–consumer 의존성을 추론하고 응답 피드백으로 유효한 호출 순서를 확장한다.
- **oracle:** 기본적인 서버 오류 탐지 및 별도로 정의된 checker. 상태 공간을 더 깊게 탐색하는 능력이 중심이다.
- **원문·구현 경계:** 공식 저장소는 오류 코드(500)와 checker를 구별한다. **일반 fuzzing만으로 임의의 공유·테넌트·필드 권한의 정답을 자동 확보한다고 해석하면 안 된다.**
- **AP-EYE 분석:** 요청 생성·도달 가능 상태 탐색의 강한 기준선으로 삼고, 인가 oracle의 개선과 생성량 증가의 효과를 분리한다.
- **근거:** [ICSE 논문 PDF](https://www.microsoft.com/en-us/research/wp-content/uploads/2021/03/RESTler.pdf), [공식 저장소의 Bugs found by RESTler](https://github.com/microsoft/restler-fuzzer).

### H13. Checking Security Properties of Cloud Services REST APIs — 2019 기술보고서, ICST 2020 학회판

- **입력·접근권한:** RESTler 실행 흐름·동적 객체 ID·서비스 명세; 사용자 네임스페이스 검사에는 서로 다른 인증 문맥이 필요하다.
- **방법:** 삭제 뒤 재접근, 실패한 생성의 잔여 효과, 부모–자식 자원 불일치, 사용자 네임스페이스 격리라는 **네 개 보안 규칙**을 active checker로 검사한다.
- **인가 oracle:** 선언한 자원 계층·사용자 격리 규칙. 사용자 토큰 교환·부모 ID 변경이 이미 포함된다.
- **원문 범위:** Azure·Office 365 서비스에서 발견한 문제를 보고한다. 규칙이 적용되는 자원 모델을 전제한다.
- **AP-EYE 분석:** “RESTler는 인가를 전혀 검사하지 않는다”도 틀리다. 반대로 합법적인 공동 소유·공유 객체에 격리 규칙을 무조건 적용하면 안 된다. 새 가설은 이 전제의 적용 가능성을 검증하거나 규칙 적용 범위를 넓히는 데 두어야 한다.
- **근거:** [Microsoft 공식 설명: 2019 보고서와 ICST 2020 구별](https://www.microsoft.com/en-us/research/publication/checking-security-properties-of-cloud-services-rest-apis/), [원문 §3.1–§3.2](https://www.microsoft.com/en-us/research/uploads/prod/2019/02/paper2.pdf).

### H14. RESTTESTGEN — Viglianisi·Dallago·Ceccato, ICST 2020

- **입력·접근권한:** Swagger 명세와 API 접근. 서버 소스 불필요.
- **방법:** 정상 입력과 오류 입력을 만들고 선행 응답에서 얻은 값을 이용해 API 호출을 구성한다.
- **oracle:** 정상/오류 시나리오의 응답과 명세에 기반한 구현 결함 검사.
- **원문 범위:** 87개 실제 REST API에 대한 일반 API 테스트 연구다.
- **AP-EYE 분석:** 명세 준수·오류 처리 검사와 객체 소유·공유 정책 검사 사이에는 별도 의미 계층이 있다. 논문이 사용자별 모든 인가 정책을 판정했다고 소개하지 않는다.
- **근거:** [ICST 공식 논문 페이지·초록·DOI](https://conf.researchr.org/details/icst-2020/icst-2020-papers/10/RESTTESTGEN-Automated-Black-Box-Testing-of-RESTful-APIs), [저자 전체 PDF](https://profs.scienze.univr.it/~ceccato/papers/2020/icst2020api.pdf).

### H15. RESTest — Martin-Lopez·Segura·Ruiz-Cortés, ICSOC 2020 / ISSTA 2021

- **출판 구분:** 2020 *Black-Box Constraint-Based Testing*과 2021 *Automated Black-Box Testing* 도구 논문을 구분한다.
- **입력·접근권한:** OpenAPI, 테스트 설정, 입력 파라미터 간 의존성 정의 등.
- **방법:** 제약 기반·무작위 등 테스트 생성 전략을 사용하고 유효/무효 입력 및 API 응답을 검사한다.
- **oracle:** 명세·입력 제약·예상 응답과 테스트 구성. 사용자 정의 인가 정책을 자동으로 완성하는 일반 oracle은 아니다.
- **AP-EYE 분석:** “LLM이 많은 요청을 만든다”는 방식만 비교하지 말고 제약 기반 생성기를 포함해야 한다. 동일한 인가 oracle·요청 예산으로 생성기를 비교하고, 동일한 생성 결과로 oracle을 비교해야 원인을 분리할 수 있다.
- **근거:** [저자 연구 목록의 두 논문 구분](https://ssegura.github.io/research/), [저자 기관의 2020 원문](https://idus.us.es/server/api/core/bitstreams/9d39d518-003b-4177-99a3-e9169cb7a45c/content), [공식 구현·2021 인용 정보](https://github.com/isa-group/RESTest).

### H16. Automated Reverse Engineering of Role-based Access Control Policies of Web Applications — Le 등, JSS 2022

- **입력·접근권한:** 웹 애플리케이션 탐색·접근 로그·생성한 접근 요청; 추론 정책을 검토할 보안 엔지니어.
- **방법:** 탐색과 조합 테스트로 접근 관측을 확대하고, 기계학습으로 접근 제어에 영향을 주는 속성과 정책을 복원한다.
- **인가 oracle:** **현재 구현을 설명하는 추론 정책**을 사람이 의도한 접근권한과 비교한다. 구현 복원과 보안상 옳은 정책 발견을 분리한다.
- **원문 범위:** 네 웹 애플리케이션에서 평가. 97.8%는 추론 정책의 **실제 구현 대비 정확성**으로, 범용 취약점 탐지 정확도나 이상적인 업무 정책의 정확도가 아니다.
- **AP-EYE 분석:** 권한표 생성 자동화·사용자 검토 부담 경감은 이미 연구됐다. AP-EYE는 같은 정보로 간단한 규칙/정책 학습 기준선과 비교하고, 누락된 관계를 사람이 얼마나 적은 질문으로 보완하는지 측정할 수 있다.
- **근거:** [저자 소속기관 원문 저장소·초록·학술지 정보](https://orbilu.uni.lu/handle/10993/48104), [DOI 10.1016/j.jss.2021.111109](https://doi.org/10.1016/j.jss.2021.111109).

## 6. 2024–2026년의 연결점

최근 연구는 기존 아이디어가 완전히 사라진 것이 아니라 **객체의 의미를 어디서 얻을지와 결과를 무엇으로 확인할지**를 더 구체화한다.

- **BolaRay, CCS 2024:** *Detecting Broken Object-Level Authorization Vulnerabilities in Database-Backed Applications*. 소스와 DB 관계에서 객체 수준 인가 모델을 추론해 누락된 검사를 찾는다. 따라서 객체 관계 추론 자체를 신규 아이디어로 삼기 어렵다. 소스가 없는 로그 기반 방식과는 관측 조건을 맞추지 않으면 공정 비교가 안 된다. [저자 원문](https://leehaofeng.github.io/papers/2024-BolaRay.pdf), [DOI](https://doi.org/10.1145/3658644.3690227).
- **Links2CPN, International Journal of Information Security 2025-02-21:** OpenAPI를 Colored Petri net으로 변환하고 요청·응답 로그의 적합성을 검사한다. §2.2는 `links`가 필요하며 조사한 1,955개 명세 중 9개만 이를 사용했다고 명시한다. 명세 품질·연결 정보의 누락은 연구자가 인정한 배포 제약이다. “트래픽+명세를 이용한 인가 사고 탐지”도 이미 직접 선행연구가 있다. [출판사 전체 원문](https://link.springer.com/article/10.1007/s10207-024-00970-5).
- **AuthProbe, 2026-07 arXiv 프리프린트:** OpenAPI·통제 가능한 여러 신원·정당한 소유자 응답을 사용해 교차 사용자 읽기 노출을 확인한다. 합성 채용 API의 결과를 보고하며, 이번 확인에서는 학회 심사 완료를 확인하지 못했다. 읽기 경로의 확인을 모든 인가/업무 흐름에 대한 성능으로 확대하면 안 된다. [arXiv 서지·원문](https://arxiv.org/abs/2607.20574).

이 세 사례만으로 2026년 전체 연구 지형을 포괄하지는 않는다. 최신 논문의 세부 한계와 후보 가설은 [최신연구와 연구 가설](RECENT-RESEARCH-GAPS.md)에서, 실제 사건의 증거는 [최근 사고 분석](INCIDENTS.md)에서 비교한다. [통합 보고서](RESEARCH-REPORT.md)는 두 결과를 프로젝트 의사결정으로 연결한다.

## 8. 킥오프의 주장과 연구 주장 사이에서 수정할 부분

| 넓게 말하기 쉬운 주장 | 선행연구를 반영한 정확한 표현 |
|---|---|
| 기존 인가 진단은 사람이 권한표를 먼저 작성해야만 한다 | 명시 권한표를 쓰는 도구가 있으나 RoleCast·SPACE·AuthScope·정책 역공학은 다른 정보와 가정으로 그 부담을 줄였다. **어떤 정보의 수작업 비용을 줄이는지** 특정한다. |
| 트래픽만으로 인가 실패를 확정한다 | 트래픽에서 비정상 후보를 만들 수 있다. 비공개·소유·공유·위임·행위의 의미를 확정할 근거가 부족하면 보류한다. 이 경계는 RoleCast의 조회 제외, AuthScope의 공개 리소스 처리에서 이미 드러난다. |
| 토큰을 바꿔 남의 데이터가 나오면 취약점이다 | 실제 반환 확인은 필요하지만 정상 공개·공유·관리자 접근을 배제해야 한다. AuthScope와 RESTler 사용자 네임스페이스 checker가 직접적인 비교 대상이다. |
| AI로 인가 테스트를 자동화하므로 학술적으로 새롭다 | 기존 요청 생성·차분 검사·정책 복원과 비교해, **동일 입력과 예산에서 어떤 오류 또는 검토 비용이 줄었는지** 검증한다. |
| 로그로 전체 유출 규모를 산정한다 | 관측된 요청·응답과 검토된 정책·대상 대응을 바탕으로 **확인된 노출의 하한/범위와 미확인 부분**을 구분한다. 기록되지 않은 본문·호출·경로까지 확정하지 않는다. |

### 관측만으로 판정할 수 없는 경우의 짧은 설명

다음은 **본 조사자의 식별 가능성 논증**이며 특정 논문의 정리로 인용하지 않는다. A의 토큰으로 B의 문서가 반환된 동일한 HTTP 기록을 생각하자. 상황 1에서는 B가 A에게 문서를 공유했고, 상황 2에서는 공유하지 않았는데 인가 검사가 빠졌다. 기록에 공유 상태가 없다면 관측은 같아도 정답은 다르다. 그 기록만 받는 어떤 모델도 두 상황을 항상 정확히 구별할 수는 없다.

이 논증은 자동화를 포기하자는 뜻이 아니다. **필요한 최소 관계/정책 증거를 추가로 수집할 조건, 부족할 때의 보류, 잘못된 추가 증거를 사용했을 때의 오류**가 연구 대상이라는 뜻이다. H03의 속성 조건, H07의 조회 판정 경계, H09의 공개 자원 제거, H11의 시점 일관성이 각 구성 요소를 뒷받침한다.

## 9. 이 역사에서 직접 도출되는 평가 요구사항

아래는 아직 실험하지 않은 **설계 권고**다. 최신 사고와 결합한 새 가설의 효과가 입증됐다는 뜻은 아니다.

| 평가 축 | 포함해야 할 비교·반례 | 선행 근거 |
|---|---|---|
| 정책 부족과 오판 구별 | 완전/누락/상충 정책; 정상 공유·공개·위임; 무조건 판정 vs 보류 | H03, H07, H08, H09 |
| 입력 정보 효과와 방법 효과 구별 | 같은 정보의 단순 규칙·SQL·권한 행렬과 비교; 추가 정책 정보를 준 기준선도 제공 | H04, H08, H16 |
| 요청 생성과 oracle 분리 | 같은 요청 집합에 서로 다른 판정기; 같은 판정기에 RESTler/제약 생성/제안 생성기 | H12, H13, H14, H15 |
| 단발 결과와 시간 변화 구별 | 공유→철회→재조회, 테넌트 이동, 토큰·캐시 만료 전후 | H11, H13 |
| 읽기와 쓰기 분리 | 읽기: 실제 필드/주체 반환. 쓰기: 별도의 변경 후 상태·감사 이벤트 확인 | H05, H06, H07, H09 |
| 명세·관측 가용성 | OpenAPI 누락/오래된 버전, 링크 누락, 응답 누락, 발견되지 않은 경로 | H12–H16, Links2CPN |
| 외적 타당성 | 합성 개발 사례와 독립 평가 분리; 미관측 앱/스키마/업무 단위 분할 | H08–H10, H16의 평가 범위; AuthProbe의 합성 평가 범위 |

프로젝트의 [현재 구조 문서](../../데모코드/docs/architecture.md)는 로컬 합성 API와 검토된 업무 정책, 요청자–데이터 주체 구별, 실제 응답 증거, `confirmed/allowed/blocked/needs_review` 상태를 설명한다. 이 구조는 위 연구 질문을 실험할 출발점이지만, 운영 서비스 탐지 정확도·사고 예방 효과·학문적 기여가 이미 입증됐다는 증거는 아니다.

## 10. 서지 검증 메모

- **AutoBOLA:** 정확 명칭과 API 인가 관련 조합 검색으로 신뢰할 만한 원문 서지를 확인하지 못했다. 존재하지 않는다고 단정하지 않지만 본 문서의 근거 목록에서 제외했다. 이름이 비슷한 BolaRay와 혼동하지 않는다.
- **RoleCast:** OOPSLA **2011**이다. 초기 검색의 일부 오래된 URL은 실패했지만 McKinley 저자 페이지 PDF와 공식 프로그램을 확인했다.
- **SPACE:** ICSE **2016**의 Security Pattern Checker다.
- **ACMiner:** CODASPY **2019**, Android 미들웨어 대상이다. USENIX/REST API 논문으로 표기하지 않는다.
- **RESTler:** ICSE **2019 기본 상태 기반 fuzzing**과 **ICST 2020 보안 checker**를 나눠 인용한다. 기술보고서 공개 연도 2019와 학회판 2020도 구분한다.
- **RESTest:** ICSOC **2020** 제약 기반 테스트와 ISSTA **2021** 도구 논문이 별도로 존재한다.
- **Links2CPN:** DOI 문자열에 2024가 포함되지만 출판사 공개일은 **2025-02-21**이다.
- **AuthProbe:** **2026-07 프리프린트**로 취급한다. 정식 동료심사 논문으로 승격해 표시하지 않았다.
- 수치의 분모와 목표가 다르므로 연구별 정확도·취약점 수를 하나의 순위표로 합산하지 않았다. 권한표 작성 감소, 요청 도달률, 후보 정밀도, 실제 노출 입증, 영향 범위 오차는 서로 다른 성능 지표다.
