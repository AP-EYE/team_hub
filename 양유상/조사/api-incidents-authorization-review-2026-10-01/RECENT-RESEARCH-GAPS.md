# 최근 API 인가 진단 연구와 AP-EYE의 검증 가능한 연구 후보

조사 기준일: **2026-10-01**. 연구의 방법·한계는 아래에 지정한 원문 버전을 기준으로 읽었다. **문헌 조사와 실험 설계 제안이며, 제안 방법의 구현·성능·신규성을 검증한 실험은 이번에 수행하지 않았다.**

핵심 판단은 다음과 같다. 인가 진단의 어려움은 공격 요청 생성만이 아니라, **그 요청이 원래 허용되어야 하는지에 대한 정답, 실제 데이터·효과가 관측됐는지, 그 정답이 어느 시간과 상태까지 유효한지**에 있다. 그러나 다중 계정 재전송, 응답 비교, 상태 순서, 사람 검토 정책, LLM 후보 생성, 로그 연결은 이미 선행 연구가 있다. AP-EYE는 이 조합을 새롭다고 주장하기보다 **기존 방법이 오판하는 구체적 조건을 독립 정답으로 평가하고, 같은 입력·예산에서 추가 절차가 유용한지** 입증해야 한다.

## 1. 확인 범위와 읽는 법

- 2024~2026년의 BOLA/BFLA/BOPLA, 읽기 노출, 상태 변화, 정책 합성·오라클 연구를 중심으로 조사했다. 직접 관련된 2022~2023년 연구는 비교군에서 빠지지 않도록 추가했다.
- `원문에서 확인`은 저자가 정의·구현·평가·한계로 직접 설명한 내용이다. `AP-EYE 제안`은 그 사실로부터 도출한 검증 전 가설이다.
- 학회·학술지 게재, 프리프린트 공개, 실무 구현을 구분한다. 도구의 존재가 성능 우위를 증명하지 않고, 프리프린트라는 이유만으로 신규성 비교에서 제외하지도 않는다.
- 논문이 주장하는 실서비스 성능·탐지 개수는 저자 보고이며 이 조사에서 재현하지 않았다. 서로 다른 표본의 정확도나 취약점 개수를 순위표로 비교하지 않는다.
- 검색어에는 `BOLA authorization testing`, `API authorization oracle`, `BACFuzz`, `BolaRay`, `BOLAZ`, `AuthProbe`, `EDEFuzz`, `access-control configuration changes`, `revocation effect closure`, `AutoCedar`를 사용했다. 이는 집중 문헌 조사이며 전체 문헌을 빠짐없이 수집한 체계적 문헌고찰은 아니다.

## 3. 최근 사고 원인과 연구 사이의 간격

아래는 사고의 원인을 연구 평가 조건으로 바꾸는 표이다. 사고 공지에서 확인되지 않은 상세 구현을 BOLA로 추정하지 않는다. 공개 취약점은 실제 악용 사고와 구분한다.

| 원인 또는 공개된 문제 | 연결되는 연구 | 기존 연구만으로 충족되지 않는 확인 질문 | 후보 |
| --- | --- | --- | --- |
| 인증은 통과하지만 특정 객체·테넌트·필드의 경계를 누락 | R1·R5·R6·R8, 속성에는 R2·R12 | 목록과 단건 조회가 모두 잘못돼도 정답을 독립적으로 만들 수 있는가? 정상 공유를 위반으로 오판하지 않는가? | H1·H2·H4 |
| 공개·비공개 데이터 범위가 API 구현에서 잘못 적용 | R1·R2·R8 | 객체 ID가 없거나 일부 필드만 반환되는 읽기 노출을 확인할 수 있는가? | H1·H4 |
| 변경 후 오래된 역할·세션·캐시가 남음 | R4·R10·R15·R16 | 정책이 정한 전파 기한 이후의 새로운 호출과, 그 이전에 승인된 작업을 구분하는가? | H3·H8 |
| 인증·인가 의존성 오류가 허용으로 처리됨 | R4·R7·R10 | 보호 서비스 정상/장애 상태의 같은 요청을 비교하고, 오류를 단순 거부 성공으로 착각하지 않는가? | H6 |
| 여러 엔드포인트·표현·배치 사이에서 검사 위치가 다름 | R3·R5·R7·R11 | 동일 자원의 별칭과 정상적인 정책 차이를 구별하며 경로 간 누락을 찾는가? | H7 |

**2026년의 직접 근거:** METR의 2026-08-31 공식 공지는 3월 인증 fail-open 후 API 키 도난 사건과, 5월 공개 transcript viewer의 읽기 전용 SQL 기능에서 비공개 평가 데이터에 접근 가능했던 별개 취약점을 설명한다. 후자는 공격자의 비공개 자료 접근 증거가 없다고 명시한다. 그러므로 `최신 SQL API 데이터 유출 확정 사고`로 적으면 안 된다. 전자는 H6, 후자는 H1·H4의 원인 유형과 맞는다. [공식 공지](https://metr.org/blog/2026-08-31-security-update/)

**시간 문제의 직접 근거:** pyLoad의 2026-04-13 [유지관리자 공지](https://github.com/pyload/pyload/security/advisories/GHSA-66hx-chf7-3332)는 권한 변경 후 기존 세션의 role·permission 캐시 사용을 설명한다. NocoDB의 2026-05-19 [유지관리자 공지](https://github.com/nocodb/nocodb/security/advisories/GHSA-f76x-f9vj-92jv)는 API 토큰 DB 삭제 후 인증 캐시가 남는 문제다. 두 사례는 인가 상태 갱신과 인증 자격 폐기의 차이를 보여주며, 이 공지만으로 실제 공격 피해가 발생했다고 판단하지 않는다.

## 4. 현재 AP-EYE에서 이미 하고 있는 것

현재 [아키텍처](../../데모코드/docs/architecture.md)는 합성 FastAPI 업무 API, HTTPX 기반 로컬 프록시, 검토된 정책과 실제 응답의 대조, 필드 매핑, PostgreSQL 결합, `confirmed/allowed/blocked/needs_review` 분리다. actor·data_subject·resource.owner를 분리하고 같은 실행·요청자·테넌트·회원 체계의 증거만 연결한다. 현재 자동 시험 범위는 GET 16개이며 LLM은 인가 위반을 확정하지 않는다.

로컬에서 읽은 한국어 필드 선택적 분류 가설(`양유상/조사/research-hypothesis-2026-10-01/RESEARCH-HYPOTHESIS.md`)은 정보 부족·오래된 문맥·모델 오판을 나누는 연구이며, 인가 위반 판정과는 구별된다. 로컬 권한 회수 가설(`양유상/조사/authorization-revocation-hypothesis-2026-10-01/RESEARCH-HYPOTHESIS.md`)은 이미 기한·세션·대조군을 제안한다. 두 파일은 이번 조사 때 읽은 로컬 참고자료이며 이 문서와 함께 원격 저장소에 게시됐다고 전제하지 않는다. 이번 H3은 기존 회수 가설의 최신 선행연구 검토를 강화한 것이며 새 발견으로 다시 세지 않는다.

따라서 아래 후보의 가치는 `제품 기능 추가`와 `학술적 기여`를 별도로 평가해야 한다. 예를 들어 역할 변경 API를 추가하면 기능 확장이지만, 학술적 기여는 기존 상태 테스트와 비교했을 때 시간 계약과 증거 연결이 줄인 오류로만 주장할 수 있다.

## 5. 검증 가능한 가설 8개

모든 후보는 **선행 연구 → 구체적 실패 조건 → 제안 → 강한 비교군 → 반증** 순서로 작성했다. 순위는 현재 구현과의 연결·실험 비용에 대한 판단이며 연구 결과가 아니다.

### H1. 목록 조회까지 틀릴 수 있을 때의 독립 정책·응답 오라클

**가설:** 목록과 단건 조회가 함께 권한 범위를 잘못 적용하거나 공유 예외가 있는 API에서, 소수의 검토된 허용·금지 관계와 실제 반환 증거를 분리하는 오라클은 목록 기반 소유권 추론보다 같은 요청 예산에서 잘못된 확정을 줄인다. ID가 생략·변환된 응답에는 검토된 필드 대응이나 합성 canary를 쓰되 근거가 없으면 보류한다.

- **선행 근거·차이:** R8 §III의 목록 기반 정답과 §VIII의 transformed-body 한계가 직접 비교 지점. R6의 SELECT 한계, R2의 불필요 필드와 민감성 분리는 읽기 평가의 필요성을 뒷받침한다. `응답 비교` 자체는 R8와 중복이다. 차별 후보는 **잘못된 목록을 정답으로 쓰는 순환을 제거하고, 그 대가인 준비 비용·보류율까지 측정**하는 데 있다.
- **사고 원인 연결:** 객체·테넌트 검사 누락, 공개 SQL 조회 범위 오류. METR 5월 사례는 이 유형의 동기이지 본 방법의 탐지 성공 증거가 아니다.
- **최강 비교군:** 실제 AuthProbe 원 구현과 문서화된 predicate 설정, 동일 정책·동일 응답을 받는 간단한 Python/SQL 규칙, EDEFuzz가 적용되는 UI 표본. 추가 정책 정보를 제안 방법에만 주지 않는다.
- **정답·실험:** detector가 읽지 않는 별도 정책표와 DB fixture로 `허용/금지/미정` 정답 작성. 목록만 정상/목록만 오류/둘 다 오류, 정상 공유, ID 없음, 부분 필드 노출을 교차한다. 독립 검수자 2명과 불일치 조정, 서비스 단위 분리.
- **제거 비교·지표:** 정책 출처 제거, ID 대응 제거, 보류 제거. 같은 확정 비율뿐 아니라 사전 고정한 **위반 recall 하한**을 만족하는 조건에서, 위반을 정상으로 확정한 오류와 정상을 위반으로 확정한 오류를 함께 비교한다. 클래스별 확정률·읽기 위반 재현율·보류율·준비 시간을 보고한다. 모든 요청을 정상 또는 보류로 보내 오확정률만 낮추는 방법은 개선으로 인정하지 않는다.
- **반증·실현성:** 같은 입력의 단순 규칙과 차이가 없으면 새 오라클 우월성은 기각하고 평가셋·실패 조건의 기여로 줄인다. **현재 GET 프록시에 가장 잘 맞는 후보.**

### H2. 담당자에게 묻는 인가 질문을 줄이는 반례 중심 정책 보완

**가설:** 불완전한 정책에서 가능한 정책 후보들이 서로 다르게 답하는 요청을 우선 질문하면, 무작위 또는 엔드포인트 순서 질문보다 같은 사람 검토 시간에서 잘못된 허용 예측을 줄인다.

- **선행 근거·차이:** R9의 검토된 고정 의도와 검증기 반례, R14의 제한된 질문 예산 오라클 학습을 결합할 수 있다. 사람 개입·반례·LLM 자체의 발명은 아니다. AP-EYE의 추가점 후보는 **인가 축(소유·공유·테넌트·필드·상태)의 모호함을 줄이는 질문 선택 기준**이다.
- **사고 원인 연결:** 업무 예외가 문서화되지 않아 객체·역할·필드에 검사를 일관되게 적용하지 못한 유형. 특정 사고 개발자의 의도 부족으로 단정하지 않는다.
- **최강 비교군:** AutoCedar의 intent-review 절차를 가능한 범위에서 적용, 균등·무작위·불확실성 기반 질문, 같은 후보 정책 공간의 정보이득 선택. LLM 없이 동작하는 방법도 필수.
- **정답·실험:** 독립 담당자가 완전 정책을 먼저 고정하고 일부 규칙을 숨긴다. evaluator만 전체 정책을 보유한다. 실제 사람 검토 시간·오해·정답 불일치를 측정하며 자동 답변 담당자를 사람 연구로 부르지 않는다.
- **제거 비교·지표:** 반례 선택 제거, 비용 가중 제거, 과거 답 재사용 제거. 질문 수·검토 시간당 false-permit/false-deny, 보류, 인가 축별 커버리지.
- **반증·실현성:** 간단한 정보이득이나 규칙 템플릿보다 나아지지 않거나 담당자가 질문을 이해하는 시간이 더 들면 우월성 기각. **정책 담당자 참여가 있어야 실현 가능.**

### H3. 권한 회수 후 새로 시작한 API 호출의 시간 계약 검사

**가설:** 권한 변경의 확인 시각, 허용된 전파 기한, 기존·새 세션·권한 유지 대조군을 함께 기록하면, 단순 변경 전후 응답 비교보다 정상 지연을 오류로 오판하는 비율을 낮추면서 기한을 넘은 잔존 접근을 검출할 수 있다.

- **선행 근거·차이:** R4의 변경 영향 비교, R15·R16의 시퀀스·토큰 변이, R10의 권한 종료 구분을 선행 방법으로 인정한다. 연구할 지점은 **HTTP 관측 제약 아래 기한의 출처와 변경 확인이 불완전할 때의 오판·보류 경계**다.
- **사고 원인 연결:** pyLoad 기존 세션 권한 캐시가 직접 동기. NocoDB 토큰 캐시는 인증 폐기 하위 실험으로 분리.
- **최강 비교군:** 기존 AP-EYE 회수 가설을 구현할 기준 방식, MST-wi 관계 기반 검사, ACtests형 전후 비교, TTL 대기 뒤 재전송이라는 단순한 강한 방법. 현재 회수 가설의 전체 구현·검증 완료를 뜻하지 않는다. 원 도구를 실행하지 못하면 재구현으로 명시한다.
- **정답·실험:** 중앙 단조시계, 정책 변경 commit 시각, 각 검사점의 정책 버전, 실제 반환 결과를 별도 기록. 즉시 회수·정상 bounded-delay·영구 stale-session·clock-skew·timeout을 포함한다.
- **제거 비교·지표:** 새 세션·유지 대조군·기한·버전 각각 제거. 오탐, 기한 초과 검출 지연, 미확정 비율, 시간 구간 폭을 측정. `관측 마지막 허용~첫 차단` 구간을 정확한 전역 회수 시점으로 보고하지 않는다.
- **반증·실현성:** 단순 TTL 대기 방식이 같은 지연·오탐에서 동등하면 복잡한 계약의 필요성은 약화. **기존 연구계획의 연속이며 별도 신규 가설 수로 중복 계산하지 않는다.**

### H4. 객체는 허용돼도 금지 필드가 읽히거나 수정되는 경우

**가설:** 객체 접근 허용, 필드 읽기 허용, 필드 쓰기 허용을 분리하고 조회·수정·재조회 결과를 대조하면, 객체 단위 BOLA 검사와 단순 민감정보 탐지보다 BOPLA의 오탐·누락을 줄인다.

- **선행 근거·차이:** R12는 mass assignment 시험을 이미 구현했고, R2는 응답의 과다 필드 후보를 찾는다. R1의 열별 예외 오탐은 객체 모델만으로 충분하지 않은 사례다. 차별 후보는 **읽기와 쓰기를 같은 필드 정책 아래 교차 평가하되 공개·공유·계산필드 예외를 보존**하는 것.
- **사고 원인 연결:** 객체 전체 직렬화, 클라이언트 화면에서만 필터링, 수정 payload의 금지 속성 수용 유형.
- **최강 비교군:** RestTestGen mass-assignment strategy, EDEFuzz, 완전한 필드 allowlist와 round-trip assertion. 동일 정책을 가진 수동 계약 테스트보다 나아지는지 확인해야 한다.
- **정답·실험:** 고정 필드 정책과 독립 DB observer. 허용 필드, 읽기만 허용, 쓰기만 허용, public metadata, 지연 계산필드, nested array, 부분 업데이트를 준비한다. 성공 HTTP 코드만으로 수정 성공을 라벨링하지 않는다.
- **제거 비교·지표:** 재조회·독립 observer·경로 문맥 제거. 필드 수준 precision/recall, 상태 복구 성공률, 호출 수, 정상 필드 변경 손실률.
- **반증·실현성:** allowlist 계약 테스트로 충분하면 도구 통합·벤치마크 기여로 제한. 현재 GET 전용 시험을 넘어가므로 **별도 합성 write/reset 환경이 필요**하다.

### H5. 사고 질문별로 저장할 최소 증거와 판정 불가능 영역

**가설:** `누가 누구의 어떤 필드를 받았는가` 등 질문을 먼저 고정하고 응답·연결 키·정책 버전을 선택 보존하면, 고정 마스킹보다 같은 저장량에서 피해 범위의 과장·축소를 줄일 수 있다. 관측이 빠진 경우 알려진 하한과 미확인 범위를 분리한다.

- **선행 근거·차이:** R17은 응용의 질문에 맞춘 provenance 선택 수집을 직접 다루므로 `질문에 맞는 증거만 남긴다`도 이미 선행 개념이다. R13은 관련 인가 로그·민감정보 경계를, R18은 사용자·정책·반환 데이터 대응을 다룬다. AP-EYE 후보는 **부분 HTTP 응답·tenant 충돌·정책 버전 누락 조건에서의 사람/필드 노출범위와 보류를 함께 평가**하는 좁은 실증이다.
- **사고 원인 연결:** 호출 로그만 있어 실제 반환 필드·정보주체를 확정하지 못하는 사후 분석 문제. 이는 초기 BOLA를 막는 방법과 별도 목표다.
- **최강 비교군:** 전체 응답+독립 정답, 메타데이터 전용, 고정 필드, 기존 마스킹, 동일 입력을 쓰는 SQL 최소 집계, CamFlow의 응용별 선택 원칙을 HTTP에 적용한 방식. 후자는 CamFlow 원 도구 실행과 구분한다. 전체 응답 방식의 결과를 자동으로 정답이라 놓지 않는다.
- **정답·실험:** 허용된 합성 피해 ledger로 실제 전달된 사람·필드를 미리 기록. 로그 샘플링·배치·중복 ID·다른 tenant·누락 응답을 독립 변이하고 retention 정책을 고정한다.
- **제거 비교·지표:** 연결 키·반환 필드·정책 버전·수집완전성 표시를 각각 제거. 사람/필드별 범위 오차, 잘못된 동일인 연결, 보류율, 저장 바이트, 보존된 민감 값 수.
- **반증·실현성:** 단순 고정 필드가 모든 질문에서 동등하면 선택 방법의 새 기여 없음. **현 아키텍처에 맞지만 이미 팀원의 최소 로그 주제와 중복 가능성이 커 공동 확장으로 다뤄야 함.**

### H6. 인증·인가 의존성 장애를 주입한 fail-open 진단

**가설:** 같은 보호 요청을 정책 서비스·키 조회·세션 저장소의 정상/오류/지연/잘못된 응답 상태에서 대조하고 실제 반환 또는 효과를 확인하면, 정상 상태만 검사한 회귀 시험보다 fail-open을 더 찾아내면서 단순 가용성 장애를 인가 위반으로 오판하지 않는다.

- **선행 근거·차이:** R4는 환경을 포함한 설정 변화 시험, R7은 인증·인가 결과를 이용한 오라클을 다룬다. R18이 전제한 정확한 인증 로직도 장애 평가에서 별도로 확인해야 한다. 여기서 도출한 것은 **의존성 장애 × 인가 축 × 관측 근거의 통제 실험**이다. fail-closed 원칙이나 fault injection 자체의 신규성을 주장하지 않는다.
- **사고 원인 연결:** METR 3월 인증 fail-open은 직접적인 공개 동기. 공지는 구체적 오류 트리거를 모두 밝히지 않으므로 아래 장애 시나리오는 그 사건의 정확한 재현이 아니라 일반화한 합성 조건이다.
- **최강 비교군:** 통상적인 의존성 fault-injection 테스트+명시적 deny assertion, EvoMaster 인증 오라클, 같은 장애를 주되 status만 검사하는 방식. 반드시 `단순 장애주입+정책 assertion`을 이겨야 한다.
- **정답·실험:** 독립 정책표와 canary sink. 모든 보호 요청의 허용·거부·오류 기대값을 사전 작성한다. timeout/500/빈 정책/서명키 조회 실패/캐시 불일치를 국소적으로 주입하고 정상 허용 대조군도 유지한다.
- **제거 비교·지표:** 장애 주입, 실제 효과 observer, 정상 대조군 각각 제거. 장애군별 검출, 정상 업무 보존, 오류와 거부의 혼동률, 복구 후 상태 일치.
- **반증·실현성:** 기존 장애주입 계약 테스트로 동일한 결과면 독립 알고리즘 기여는 약하다. **FastAPI에 작은 의존성 stub을 추가해 실험 가능하므로 H1과 함께 실용적인 후보.**

### H7. 자원의 별칭·경로가 달라질 때의 인가 일관성

**가설:** 명시적으로 동등하다고 검토된 자원·행위에만 경로 간 관계를 적용하고, ID의 생산·소비와 tenant namespace를 보존하면, ID 문자열이나 URL 유사도만으로 연결한 검사보다 별칭 경로의 검사 누락을 더 찾고 정상적인 정책 차이의 오탐을 줄인다.

- **선행 근거·차이:** R5의 producer/consumer와 인가 구간, R3의 links 기반 관계, R11의 chained disclosure·tenant 유형을 출발점으로 한다. 추가 가치는 **정확한 links/소스가 없을 때 부분 관계만으로 가능한 진단과 준비 비용**을 보이는 데 있다.
- **사고 원인 연결:** 기본 조회는 막지만 검색·export·bulk·이전 버전에서 같은 객체가 노출되는 유형. 모든 별칭이 반드시 같은 정책이어야 한다고 가정하지 않는다.
- **최강 비교군:** Links2CPN에 정확한 links를 제공한 상한, 소스가 있는 표본의 BolaZ, 검토된 route-equivalence 표+단순 정책 비교. 제안에만 관계 정보를 주면 안 된다.
- **정답·실험:** 테스트 작성자와 분리된 자원 대응표, tenant별 같은 번호, UUID·인코딩 ID·배치 배열, 정상 요약/public 경로, 관계 누락·잘못된 관계를 포함. 원문 ID 값의 외형만으로 동일 객체를 정답 처리하지 않는다.
- **제거 비교·지표:** namespace·ID 출처·관계 신뢰등급 제거. 경로군별 위반 재현율, 잘못된 자원 연결, 검토해야 할 관계 수, 관계 수집 비용.
- **반증·실현성:** 사람이 작성한 단순 동등성 표 이상의 효과가 없으면 시스템 기능으로 한정. **중간 난도이며 소수 로컬 별칭 API부터 가능.**

### H8. 요청 허용과 최종 효과를 분리한 비동기 인가 진단

**가설:** 큐 작업을 제출한 사용자·검사 당시 정책 버전·실행자·최종 효과를 연결한 이중 관측은, 접수 응답이나 현재 ACL만 보는 검사보다 권한 변경 이후 금지된 실행을 더 정확히 구분한다.

- **선행 근거·차이:** R10은 이미 승인된 작업의 효과 종료를 직접 다루므로 가장 강한 선행연구다. R4의 환경 기반 시험과 R11의 workflow 분류도 관련된다. AP-EYE의 가능 기여는 **특정 HTTP→worker 업무 흐름에서 필요한 최소 관측과 black-box 진단의 불가능 조건을 실증**하는 정도로 좁힌다.
- **사고 원인 연결:** 최초 접수에서만 검사하고 지연 실행·export 다운로드 때는 권한을 재확인하지 않는 일반 유형. 이번에 읽은 특정 최근 사고가 반드시 이 순서로 발생했다고 주장하지 않는다.
- **최강 비교군:** EffectBound 계약을 동일 합성 흐름에 적용, worker에서 직접 정책을 재검사하는 단순 기준 구현, 시간 기반 상태 테스트. 효과 observer가 없는 baseline과만 비교하지 않는다.
- **정답·실험:** enqueue·authorize·revoke·dequeue·effect의 실제 시각과 권한 버전을 별도 observer로 기록. 업무 계약에 따라 기존 접수는 완료 허용/즉시 중단을 각각 정상 케이스로 둔다.
- **제거 비교·지표:** 실행자·정책 버전·최종 효과·상관 ID 제거. 잘못된 종료 확정, 미탐, 정상 작업의 불필요 중단, 모니터링 비용.
- **반증·실현성:** 계약·효과 관측을 준비할 수 없거나 단순 worker 재검사와 차이가 없으면 새 기여를 축소한다. **현재 GET 데모에는 큰 확장이고 R10과 중복이 커 후순위**다.

## 6. 우선순위와 최소 실험안

| 후보 | 현재 구현 활용 | 추가 환경·사람 | 선행연구 중복 위험 | 우선순위 판단 |
| --- | --- | --- | --- | --- |
| H1 독립 정책·읽기 응답 | 높음 | 독립 정책 정답, 변환 응답 사례 | 높음: AuthProbe·규칙 오라클 | **1순위**: 왜 기존 소유권 정답이 틀리는지 명확하게 검증 가능 |
| H6 장애 시 fail-open | 중간 | 의존성 stub, 장애주입 | 중간~높음: 기존 fault-injection | **2순위**: 최신 공개 원인과 직접 연결, 합성 재현 용이 |
| H3 회수 시간 | 높음 | 세션·변경·단조시계 | 높음: 기존 팀 가설·EffectBound | **진행 중 가설 강화**: 추가 신규 주제로 부풀리지 않음 |
| H4 읽기·쓰기 필드 | 중간 | write/reset, 독립 DB observer | 높음: RestTestGen·EDEFuzz | **중기**: 읽기 전용 범위를 넓힐 때 유용 |
| H7 별칭·경로 | 중간 | 자원·경로 대응 정답 | 높음: BolaZ·Links2CPN | **중기**: 정답 준비 비용을 포함하면 연구 가능 |
| H5 최소 증거 | 높음 | 독립 피해 ledger | 높음: 기존 팀 주제·SECLOG | **팀 공동 연구로 통합** |
| H2 정책 질문 | 중간 | 실제 정책 담당자·검수 연구 | 높음: AutoCedar·active learning | **참여자 확보 후** |
| H8 비동기 최종 효과 | 낮음 | 큐·worker·효과 observer | 매우 높음: EffectBound | **후속 연구** |

첫 독립 실험은 **H1 하나를 중심으로** 삼고 H6를 별도 실험으로 유지하는 편이 해석하기 쉽다. H1의 개발용 시험은 정책 6종(개인 소유·정상 공유·tenant 분리·필드 제한·공개 예외·목록 오류) × 응답 3종(원형·ID 없는 변환·부분 필드)의 **18개 조건군**으로 시작할 수 있다. 각 조건군에는 실제 위반과 정상 반례를 함께 둔다. 이는 시험 설계 제안이며 충분한 표본 수를 이미 확보했다는 뜻이 아니다.

실제 본 실험에서는 다른 작성자가 만든 독립 서비스/결함을 추가하고 서비스 단위 train/development/test 분리를 유지한다. seed·요청 순서·API 버전·정책 버전·모델·budget을 고정한다. 반복 실행은 독립 서비스 수를 늘린 것처럼 세지 않는다. 표본 수와 반복 수는 파일럿 분산을 보고 정하며, 효과크기와 신뢰구간을 공개한다.

공통 판정은 `위반 확인`, `정상 확인`, `차단 확인`, `근거 부족`, `시험 무효`로 구분한다. 마지막 두 상태를 정상에 합쳐 정확도를 높이지 않는다. 위반 recall의 사전 하한과 양방향 확정 오류를 함께 보고하며, 높은 정상 비중에 기대는 `전부 정상` 또는 `전부 보류` 결과를 성공으로 세지 않는다. **개인정보 유형의 정답·업무 정책의 정답·실제 반환/효과의 정답을 서로 독립적으로 준비**해야 한다.

학술적 가치로 주장할 수 있는 결과는 세 가지다. ① 기존 도구의 특정 오라클 가정이 깨지는 재현 가능한 조건, ② 동일 정보·예산에서 그 실패를 줄이는 방법과 비용, ③ 관측이 부족하면 어느 결론까지 불가능한지 보여주는 평가·반례. `AI를 붙였다`, `gateway를 썼다`, `HTTP 200을 검사했다`, `두 계정으로 조회했다`, `로그를 연결했다`는 그 자체로 기여가 아니다.

## 7. 조사상 남은 제한

- 모든 도구의 원 구현을 실행하지 않았으며 실행 가능성·라이선스·정확한 버전 고정은 실험 준비 단계에서 확인해야 한다.
- R8·R9·R10처럼 최근 프리프린트는 후속 버전과 독립 재현 결과가 달라질 수 있다. 읽은 버전을 인용하고 결과를 저자 주장과 구분했다.
- `AutoBOLA`라는 이름은 이번 정확명 검색에서 관련 학술 원문을 확인하지 못해 인용하지 않았다. 이름이 비슷한 도구를 합쳐 가상의 논문을 만들지 않는다.
- Karate-BOLA-Guard의 IEEE Access 서지·초록 존재는 확인했지만, 출판사 본문 접근으로 상세 오라클을 독립 검증하지 못했다. 따라서 이번 후보의 강한 방법 근거로 사용하지 않았다. [출판사 레코드](https://ieeexplore.ieee.org/document/10942340/)
- 최근 공개 사고가 많아 보인다는 사실과 전체 발생률이 증가했다는 통계적 결론은 다르다. R11의 공개 버그바운티 표본도 전체 산업의 연간 사고 증가율을 추정하는 자료가 아니다.
