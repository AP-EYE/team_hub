# 최근 API 사고의 원인과 인가 진단이 관찰해야 할 것

조사 기준일: **2026-10-01, 한국 시간**. 2023~2026년 공개 사례를 중심으로 선정했고, 원인 비교를 위해 2022년 Optus를 포함했다. 기업 공지·규제기관 문서·최초 발견 연구자의 기술 공개를 우선했다. 공개된 문헌을 읽은 조사이며 대상 서비스에 취약점 점검이나 재현 요청을 보내지 않았다.

이 문서는 사고 원인 근거를 정리한다. 학술 선행연구 및 새 가설의 신규성 판단은 같은 폴더의 종합 보고서에서 별도로 수행한다. **사례가 여러 건 있다는 사실만으로 API 사고의 발생률이 증가했다고 결론 내릴 수 없다.** 분모인 운영 API 수, 신고 기준, 조사 범위, 관측 기간과 공개 지연을 통제한 시계열이 필요하다.

## 1. 가장 먼저 구분할 것

| 구분 | 이 문서의 의미 | 피해야 할 해석 |
|---|---|---|
| 실제 침해 확인 | 당사자·규제기관이 무단 접근 또는 자료 반출을 확인 | 모든 데이터 필드가 모든 이용자에게서 빠져나갔다고 확대 |
| 취약점 공개 | 연구자·공급사가 접근 가능성을 확인 | 접근 가능한 전체 규모를 실제 탈취 규모로 전환 |
| 원인 제한 공개 | API를 통한 접근은 확인했으나 구현 결함은 미공개 | 자동으로 BOLA/IDOR 또는 인증 부재라고 분류 |
| 2차 보도만 확보 | 언론이 회사 공지·취재 내용을 전달했으나 원문 미확보 | 직접 기술 검증한 확정 원인처럼 사용 |
| 비교용 반례 | API 결함으로 확인되지 않은 내부자·위임권한 악용 | 개인정보 유출을 전부 API 인가 결함으로 묶음 |

규모의 단위도 보존한다. **사람, 계정, 신청서, 채팅 레코드, 데이터 행, API 토큰은 서로 다른 단위**다. 접근 가능, 실제 반환, 실제 반출, 이후 악용 여부는 별도 상태로 관리한다.

### I01. Optus: 접근통제가 존재해도 모든 진입점에 동일하게 적용되지 않았다

2022년 9월 공개된 침해다. OAIC는 2025-08-08 약 **950만 명**의 개인정보 보호 실패를 주장하며 민사제재 소송을 제기했다. 이 수치는 규제기관의 주장 범위이며 법원 최종 판단과 동일하지 않다. [OAIC 공식 발표](https://www.oaic.gov.au/news/media-centre/australian-information-commissioner-takes-civil-penalty-action-against-optus)

2024-06-19 법원 명령에 첨부된 ACMA의 공개용 진술서는 2018년 접근통제 코드 오류, 2021년 주 도메인에서의 수정, 같은 문제를 가진 별도 API 도메인에서의 미수정을 설명한다. 사용하지 않던 도메인이 인터넷에 연결된 상태로 남았다는 주장도 담겼다. **문서는 소송상 주장이지 확정 판결문상의 사실 인정이 아니다.** [ACMA 진술서가 첨부된 연방법원 문서, 제3자 보관 사본](https://ismg-cdn.nyc3.cdn.digitaloceanspaces.com/asset_files/external/pvid42920242300547.pdf)

연구에 주는 질문은 “권한 검사 함수가 있는가”에서 끝나지 않는다. **같은 업무 데이터에 이르는 도메인·버전·경로 모두에서 같은 권한 규칙이 집행되는가**를 시험해야 한다. 이는 본 조사의 원인 해석이다.

### I02. T-Mobile: API 침해 사실과 BOLA 판정은 별개다

T-Mobile은 2023-01-05 무단 API 조회를 발견했고, 2023-01-19 SEC 공시에서 약 **3,700만 선불·후불 고객 계정**의 정보가 조회됐다고 밝혔다. 시작일은 2022-11-25 무렵으로 추정했다. 이름·연락처·청구주소·생년월일·계정번호·일부 요금제 정보 등이 대상이었지만 계정마다 모든 필드가 포함된 것은 아니다. 당시 공시는 비밀번호·지불카드·정부 발급 식별번호 등의 노출은 부인했다. [T-Mobile SEC 8-K](https://www.sec.gov/Archives/edgar/data/1283699/000119312523010949/d641142d8k.htm)

공식 문서로 확인되는 것은 **하나의 API를 통한 허가되지 않은 조회**다. 그 문서만으로 순차 ID, 인증 부재, 속도 제한 부재, 특정 BOLA 구현 결함을 확정할 수 없다. 따라서 이 사례는 대규모 응답 범위 분석의 동기는 되지만 특정 인가 탐지 알고리즘의 탐지 성공 사례로 사용할 수 없다.

### I03. Kia: 한 요청의 성공보다 연속 호출의 권한 변화가 중요했다

발견 연구자는 2024-06-11 문제를 제보했고, 공개 타임라인상 2024-09-26 수정 확인 후 공개했다. 페이지 상단 표기일은 9월 20일이어서 두 날짜를 구분한다. 공개 내용은 딜러 계열 API에서 개인정보를 조회하고 차량 소유자 관계를 바꾼 뒤 연구자 계정을 차량에 연결해 원격 기능을 사용하는 흐름이다. 연구자는 Kia가 악의적 악용이 없었음을 확인했다고 기술한다. **잠재적으로 영향받는 차량과 실제 탈취된 차량을 동일시하면 안 된다.** [Sam Curry 등의 최초 기술 공개](https://samcurry.net/hacking-kia)

분석상 핵심은 주체의 기능 권한, 주체와 차량의 관계, 관계를 변경하는 동작, 변경 뒤 실행 권한이 연결된다는 점이다. API 호출 하나의 응답코드만 비교하는 평가로는 “첫 호출이 두 번째 호출의 인가 상태를 바꾸는 경로”를 놓칠 수 있다. AP-EYE의 실험은 무해한 모의 차량 객체에서 이 구조를 재현하는 방식이 적절하다.

### I04. McHire/Paradox: 방치 계정 + 객체 인가, 그리고 규모 과장의 위험

연구자는 2025-06-30 기본 자격증명이 남아 있는 테스트 식당 계정과 내부 API의 IDOR를 제보했다. 다른 지원자 관련 정보를 가져오고 추가 사용자 접근 토큰도 반환되는 것을 확인했다. 연구자 글의 6,400만 규모는 시스템 식별자 및 접근 가능한 채팅 자료 범위에 대한 해석이다. [Ian Carroll·Sam Curry 공개](https://ian.sh/mcdonalds)

Paradox의 2025-07-09 공지는 실제 연구자가 내려받은 **채팅 레코드 7개 중 개인정보 포함은 5개**였고, 한 고객사 인스턴스가 영향받았다고 설명한다. 대다수 채팅 레코드는 지원자 개인정보가 없는 자료였으며, 해당 테스트 계정은 연구자 외 제3자가 사용하지 않았다는 회사 설명이다. 기존 침투테스트도 이 문제를 발견하지 못했다고 밝혔다. [Paradox 공식 보안 공지](https://www.paradox.ai/blog/responsible-security-update)

따라서 **“2026년에 지원자 6,400만 명 정보가 공격자에게 유출됐다”는 요약은 연도·단위·증거 상태 모두 부정확**하다. 이 사례에서 검증할 것은 테스트 계정 수명주기, 업무 객체의 관계 인가, 응답에 포함된 추가 권한정보다. API에 AI 채팅 기능이 있다고 해서 근본원인이 프롬프트 인젝션인 것도 아니다.

### I05. Salesloft Drift: 유효한 위임 토큰으로 정상 API 기능을 악용했다

Google Threat Intelligence Group은 2025-08-08~18에 Drift 관련 OAuth 토큰을 이용해 다수 Salesforce 고객 인스턴스에서 데이터를 반출한 활동을 관찰했다. 8월 26일 공개 후 28일 업데이트에서는 일부 Drift Email 연결 계정도 영향받았다고 밝혔다. 연결되지 않은 Google Workspace 계정 전체로 확대되는 사건은 아니며, Salesforce 핵심 플랫폼의 취약점에서 비롯된 사건도 아니라고 명시했다. [GTIG·Mandiant 분석](https://cloud.google.com/blog/topics/threat-intelligence/data-theft-salesforce-instances-via-salesloft-drift)

Cloudflare는 자사 Salesforce 인스턴스에서 8월 12~17일 지원 사례의 텍스트 필드가 반출됐고, 첨부파일은 범위에 포함되지 않았다고 설명했다. 반출 자료에서 발견한 **Cloudflare API 토큰 104개**는 회전했지만 관련 의심 활동은 찾지 못했다. 이 104개를 실제 추가 침해 104건으로 표현하면 안 된다. [Cloudflare 당사자 사후분석](https://blog.cloudflare.com/response-to-salesloft-drift-incident/)

연구적 함의는 “유효한 토큰”과 “정당한 실제 행위자·업무 목적”을 분리해야 한다는 것이다. BOLA 검사를 모두 통과하더라도 위임 토큰 탈취와 이미 허용된 범위의 반출은 남을 수 있다. 이 사건이 특정 고객사의 권한 과다 부여를 모두 입증하지는 않으며, **연결 주체·scope·접속 맥락·실제 반환 필드**를 함께 평가해야 한다는 분석으로 제한한다.

### I06. Coinbase: API 인가 결함으로 끼워 맞추면 안 되는 반례

2025-05-15 Coinbase는 해외 고객지원 담당자 일부가 매수돼 고객지원 도구의 접근권한으로 데이터를 복사했다고 밝혔다. 회사 표현상 월간 거래 이용자 **1% 미만**이 대상이며 전체 가입자의 1%라고 바꾸면 안 된다. 신분증 이미지와 계정 관련 정보 등이 포함됐지만 로그인 자격증명·개인키·고객 자산을 직접 이동하는 권한이 유출된 것은 아니라고 설명했다. [Coinbase 공식 공지](https://www.coinbase.com/blog/protecting-our-customers-standing-up-to-extortionists)

공식 공지만으로 API 결함이나 BOLA라고 분류할 근거는 없다. 이 사건은 **기술적으로 허용된 기존 접근권한의 부적절한 사용**을 보여주는 비교 사례다. AP-EYE가 정책 자체에 허용된 직원 조회를 “인가 버그”로 판정한다면 오탐일 수 있다. 정책 위반, 업무 목적 위반, 행위 이상, 데이터 노출을 별도 라벨로 다루어야 한다.

### I07. Navia: 2026년 실제 무단 접근, BOLA 세부 근거는 제한

Navia의 공식 PEBB 안내는 무단 접근·잠재적 정보 취득 기간을 **2025-12-22~2026-01-15**, 발견일을 2026-01-23으로 밝혔다. 이 안내가 제시한 인원은 해당 프로그램별 약 2.7만 PEBB, 5,600 SEBB, 약 3,000 COFA 참여자 범위이며 **Navia 전체 피해 규모가 아니다**. 이름·생년월일·주소, 일부 프로그램의 사회보장번호 등이 대상이었다. [Navia 공식 안내](https://pebb.naviabenefits.com/notice-of-data-security-event/)

2026-03-24 보도는 HackerOne의 직원 통지문을 인용해 원인을 BOLA라고 전했지만, 연결된 Maine 규제기관 통지 원문은 이번 조사에서 403으로 읽지 못했다. 따라서 **BOLA라는 구체 기술분류는 원문 미확보 상태**로 남긴다. 보도된 HackerOne 직원 287명이나 전체 Navia 270만 명을 공식 PEBB 안내의 프로그램 수치와 섞거나 합산하지 않는다. [원문 링크를 제공하는 보도 — 기술 확정 근거로 사용하지 않음](https://www.bleepingcomputer.com/news/security/hackerone-discloses-employee-data-breach-after-navia-hack/)

### I08. Cisco Secure Workload: 내부 API는 웹 화면과 다른 보안 경계다

Cisco는 2026-05-20 **CVE-2026-20223**을 공개했다. 내부 REST API의 검증·인증 부족으로 인증되지 않은 원격 주체가 Site Admin 권한으로 민감정보를 읽고 테넌트 간 설정을 바꿀 수 있는 문제였다. SaaS와 온프레미스가 해당하며, 웹 관리 화면 자체의 문제는 아니라고 구분했다. 내부 보안시험에서 발견했고 당시 악의적 악용 사실은 인지하지 못했다고 밝혔다. [Cisco 공식 보안 권고](https://www.cisco.com/c/en/us/support/docs/csa/cisco-sa-csw-pnbsa-g8WEnuy.html)

**심각도 10.0은 실제 피해 계정 수가 아니다.** 프로젝트 평가에서는 사용자용 화면이나 외부 API만 검사한 결과를 내부 관리 API·테넌트 경계까지 일반화하지 않아야 한다. “internal”이라는 이름을 붙였다는 사실이 호출자 검증을 대체하지 못한다는 근거로 활용할 수 있다.

### I09. METR: 실제 키 탈취와 비공개 자료 접근 가능성을 분리한 좋은 사후분석

[METR 공식 보안 업데이트](https://metr.org/blog/2026-08-31-security-update/)

두 사건은 API 키 유효성만 검사하는 방식, 응답의 정보 유형만 분류하는 방식, 실제 노출 범위를 추정하는 방식이 서로 다른 질문에 답한다는 예다. “인증 실패 시 허용되는가”, “반환 가능한 자료에 비공개 데이터가 혼재하는가”, “실제로 누가 어떤 값을 읽었는가”를 개별 검증해야 한다.

## 6. AP-EYE 평가에 바로 적용할 증거 규칙

1. **결함 존재와 실제 피해를 분리한다.** 연구자의 한 건 재현으로 전체 DB가 탈취됐다고 판정하지 않는다.
2. **정책이 없으면 인가 정답을 만들지 않는다.** 타인의 정보처럼 보이는 응답도 위임·공유·지원 업무상 허용일 수 있다. 반대로 본인 객체에도 허용되지 않은 필드가 있을 수 있다.
3. **엔드포인트, 호출자, 객체, 필드, 관계, 상태, 정책 버전을 함께 보존한다.** 단, 실험 데이터는 합성 데이터로 구성하고 불필요한 개인정보 원문을 수집하지 않는다.
4. **URL 발급, API 반환, 파일 다운로드, 제3자 반출, 후속 악용을 각각 기록한다.** 이들 사이의 증거가 없으면 `UNRESOLVED`로 남긴다.
5. **정확한 단위로 영향 범위를 계산한다.** 요청 수 → 행 수 → 고유 객체 수 → 고유 정보주체 수의 변환 근거를 보존한다. 신뢰할 수 있는 연결키가 없으면 명 단위 수치를 만들지 않는다.
6. **부족한 근거를 인가 위반으로 채우지 않는다.** T-Mobile의 공식 API 무단조회는 확인되지만 세부 BOLA 원인은 미확인인 것처럼, 모델 결과도 원인 분류를 보류할 수 있어야 한다.
7. **기존 방어의 효과를 무시하지 않는다.** 응답 최소화, 데이터 격리, 키 회수로 제한된 범위가 있다면 함께 측정한다. 사고 사례는 “아무 통제도 효과 없다”는 근거가 아니다.

## 7. 조사 범위와 제외·보류 이유

- 2026년 검색을 수행했고 METR·Cisco·Navia·Klue 및 국내 8~9월 사례를 확인했다. 그러나 공개자료 선별 조사이므로 2026년 전체 사고 목록이나 최신 모든 후속 조치의 완전성은 보장하지 않는다.
- Dell 2024와 Trello 2024도 후보로 검색했지만, 이번 작업에서는 상세 원인에 대해 회사 원문과 공격자·언론 주장을 충분히 분리할 자료를 확보하지 못해 핵심 확정 원인 비교에서 제외했다.
- 국내 4개 사건의 회사 원문, Navia BOLA 통지 원문, Instagram의 원 수집 시점·방법은 남은 확인 과제다. 언론 간 일치만으로 구현 결함을 확정하지 않았다.
- 이 조사만으로 “선행연구가 최근 사고를 탐지하지 못했다”는 인과관계를 만들 수 없다. 기업이 해당 연구의 기법을 사용했는지, 필요한 입력·정책을 갖췄는지, 운영 조건이 같았는지 공개되지 않았기 때문이다.
- 학문적 가치를 주장하려면 사고에서 추린 조건을 합성 또는 허가된 벤치마크에 명시하고, 강한 기존 방법과 같은 입력·정책·예산으로 비교해야 한다. 표의 조건을 추가했다는 사실만으로 신규성이나 성능 향상을 주장하지 않는다.
