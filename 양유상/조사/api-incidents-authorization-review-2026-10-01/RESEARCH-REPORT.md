# 최근 API 사고와 인가 진단 연구: AP-EYE에서 검증할 연구 가설

조사 기준일: **2026-10-01, Asia/Seoul**. 최근 사고는 2023–2026년을 중심으로 조사하고 과거 비교 사례를 별도로 다룬다. 학술 흐름은 초기 접근통제 모델부터 2026년 공개 연구까지 포함한다. **이번 산출물은 문헌·공개 사건 분석과 연구계획이며, 제안 방법의 성능·신규성을 입증하는 실험 결과가 아니다.**

## 1. 결론부터

AP-EYE의 문제 설정은 타당하지만, **“권한표 없이 토큰을 바꿔 응답을 비교한다”는 방법만으로 학문적 차별성을 주장하기는 어렵다.** 계정별 차이를 활용하는 AuthScope(2017), 응답의 데이터 노출을 검사하는 FlowWatcher(2015)·EDEFuzz(2024), 최신 다중 신원 검사 AuthProbe(2026), 접근정책 위반 오라클을 확장한 EvoMaster 연구(2026)가 이미 있다. 각각의 접근권한·가정·지원 범위는 다르다. [AuthScope 원문](https://acmccs.github.io/papers/p799-zuoA.pdf), [FlowWatcher 원문](https://lsds.doc.ic.ac.uk/sites/default/files/ccsfp224-muthukumaran_0.pdf), [EDEFuzz 학회 발표](https://conf.researchr.org/details/icse-2024/icse-2024-research-track/12/EDEFuzz-A-Web-API-Fuzzer-for-Excessive-Data-Exposures), [AuthProbe 원문](https://arxiv.org/html/2607.20574v1), [EvoMaster 확장 원문](https://arxiv.org/html/2604.00702v1).

권하는 중심 질문은 다음과 같다.

> **공개·공유·권한 변경·응답 누락이 섞인 API에서, 적은 정책 확인과 실제 응답 증거로 인가 위반을 어디까지 신뢰성 있게 판정할 수 있는가?**

팀 전체의 중심 연구에는 **H1 최소 정책 근거와 선택적 판정**을 우선 추천한다. 기존 팀원 주제와 구분되는 추가 연구로는 **H2 권한 회수의 시간 계약**, 개인정보 노출과의 연결에는 **H3 정책 변경 뒤 남는 응답 필드**, 사후 분석에는 **H4 질문별 최소 증거**가 적합하다. 이는 현재 구현과의 연결성·실험 통제 가능성을 기준으로 한 추천이며, 선행연구 대비 우월성은 아직 검증 전이다.

“사고가 늘어난 것 같다”는 관찰을 연구 동기로 쓸 수는 있지만, 이번 공개 사례 표본으로 산업 전체 발생률 증가를 증명할 수는 없다. 공격 규모·공개 시점·검색 노출·API 보급·버그바운티 공개 정책이 모두 달라진다. 2026 BOLA 실증 프리프린트도 시점 미확인 보고와 표집 편향을 한계로 명시한다. [Kaur 2026, §8](https://arxiv.org/html/2605.25865v1#S8).

## 2. 사고 원인은 한 가지가 아니다

사건별 날짜·숫자·출처 강도는 [사고 분석](INCIDENTS.md)에 있다. 아래는 그 사건을 연구 문제로 연결하는 인과 구분이다. 공식 공지에서 확인하지 못한 코드를 추정해 채우지 않는다.

| 원인 유형 | 무너진 조건 | 근거와 해석 | 필요한 진단 |
|---|---|---|---|
| 인증만 하고 객체·기능 권한은 검사하지 않음 | “로그인함”과 “이 데이터/기능 접근 가능”을 혼동 | 개인정보위는 로그인 검사와 개인정보 조회 권한 검사를 구분해 권고. McHire 연구자 공개도 객체 식별자 접근 경계를 보여줌 | 계정×객체×행위·공유 관계의 교차 검사. 익명 접근 검사만으로는 부족 |

| 합법 권한의 악용·자격증명 탈취 | 기술적 허용과 업무 목적의 정당성이 다름 | Coinbase 2025 내부자 사건은 단순한 객체 권한 검사 누락의 대조 사례 | 행위·내보내기 통제·감사·목적 제한. 정상 권한표와 응답 비교만으로 해결한다고 주장하지 않음 |
| 반복·대량 호출로 피해 확대 | 하나의 허용 또는 취약 동작이 대규모로 반복됨 | 접근통제 결함과 대량조회 방어 부재는 서로 다른 원인 층위 | 먼저 위반 여부, 다음으로 호출량·응답량·실제 노출 범위를 측정 |

Coinbase 및 첨부의 국내 네 사건에 대한 직접·보조 근거는 [사건별 원장](INCIDENTS.md)을 참조한다.

특히 **공개 취약점, 잠재적 접근 규모, 실제 다운로드, 고유한 사람 수**를 서로 바꾸어 쓰면 안 된다. McHire의 거대한 record 공간은 그만큼의 사람 정보가 실제 탈취됐다는 뜻이 아니다. 29CM 등 최근 기사에서 API 공격이 언급되어도 상세 인가 코드가 공개되지 않으면 BOLA/BOPLA를 확정하지 않는다.

## 3. 인가 진단 연구가 발전한 방식

발전은 이전 방법이 모두 폐기되는 일직선의 과정이 아니다. 정책 명세, 코드 분석, 동적 실행, API 명세 기반 생성, 응답 관측이 서로 다른 조건에서 병행된다. 전체 서지·원문 위치·한계는 [선행연구 연대기](LITERATURE-HISTORY.md)에 정리했다.

| 시기 | 중심 질문 | 대표 계열 | 해결한 점과 남는 문제 |
|---|---|---|---|
| 1990년대–2000년대 | 누가 무엇을 할 수 있는가를 어떻게 표현할까? | RBAC, 이후 ABAC·ReBAC | 역할·속성·관계로 정책 표현. 모델의 표현력과 실제 프로그램이 정책을 지키는지는 다른 문제 |
| 2010–2016 | 클라이언트 제약·서버 검사·코드 경로가 일치하는가? | NoTamper, WAPTEC, RoleCast, SPACE | 코드·제약·실행 경로를 이용해 누락 탐색. 언어·프레임워크·분석 범위의 조건이 붙음 |
| 2015–2017 | HTTP에서 데이터와 계정을 추적하면 인가 결함을 볼 수 있는가? | FlowWatcher, AuthScope | 프록시의 정책 상태 추적, 계정별 차이·교차 실행. 공유·공개·의도 정책을 어떤 근거로 아는지가 중요 |
| 2019–2021 | API 호출 순서와 데이터 의존성을 자동 생성할 수 있는가? | RESTler, RESTTESTGEN, RESTest | 유효한 상태와 요청을 더 많이 탐색. RESTler의 ICST 2020 checker는 사용자 네임스페이스·자원 계층도 검사. 일반 요청 생성 성공이나 500 오류 탐지는 인가 위반 정답과 같지 않음 |
| 2019–현재 | 관계·권한 변경을 분산 환경에서 일관되게 적용할 수 있는가? | Zanzibar 및 후속 정책 시스템 | 정책 집행·인과적 일관성의 발전. 외부 진단기가 변경 완료·반영 기한을 관측하는 문제와 구분 |
| 2024–2026 | 데이터 노출·BOLA·업무 권한에 맞춘 오라클을 어떻게 만들까? | EDEFuzz, BolaRay, BACFuzz, EvoMaster 보안 확장, AuthProbe | 도메인에 맞는 코드/SQL/응답/상태 오라클과 LLM 보조. 정답 가정, 복잡한 공유, 변경 시점, 적용 가능성은 개별 연구별 검토 필요 |
| 2026 공개 연구 | 의도 정책의 생성·검증과 최종 효과까지 어떻게 연결할까? | AutoCedar, EffectBound | 사람이 검토한 의미 경계, 검증기, 실행 효과를 다루는 최근 프리프린트. 도구·언어·provider 관측 전제를 AP-EYE와 맞춰야 비교 가능 |

정책 모델을 API 스캐너로, Android 분석기 ACMiner를 REST API 도구로, 일반 fuzzing을 BOLA 전용 정답기로 소개하지 않도록 구분했다. 프리프린트의 주장과 동료심사 논문, 실무 도구, 회사 공지도 서로 다른 종류의 근거다.

## 4. 최근 연구와 사건 사이의 구체적 간격

| 비교 축 | 선행연구에서 이미 하는 일 | 사건이 요구하는 조건 / AP-EYE에서 검증할 부분 |
|---|---|---|
| 정상 공유와 잘못된 교차 접근 | AuthScope의 교차 실행, AuthProbe의 소유자 응답 비교, EvoMaster의 실행 기반 접근 추론 | 공유·관리자 예외·정책 미관측 상태를 위반으로 단정하지 않는 조건. 자동 판정률과 오탐을 함께 측정 |
| read·field 노출 | FlowWatcher의 정책 기반 데이터 흐름, EDEFuzz의 응답 변이 | 정상 호출 안에 남는 금지 필드, 버전 변경·매핑 변경·관측 누락. UI 미사용과 인가 금지는 같은 정답이 아님 |
| 역할/권한의 시간 변화 | Zanzibar의 일관성, EffectBound의 효과 경계 | 회수 완료·허용 반영 지연·기존 세션·새 세션·독립 확인. 회수 직후 한 번의 HTTP 200은 충분한 판정이 아님 |
| 쓰기·비동기 작업 | RESTler 보안 속성, BACFuzz의 SQL 피드백, EvoMaster의 변경 행위 오라클 | 응답 성공과 실제 변경의 분리. 검사 대상 DB를 사용할 수 없는 경우의 독립 효과 근거 |
| 관측 범위 | 명세·코드·계정·로그·SQL마다 접근 가능한 증거가 다름 | 게이트웨이로 안 지나간 API, 응답이 유실된 호출, 다른 테넌트의 같은 ID는 별도 불확실성 |
| 평가 현실성 | AuthProbe의 합성 read 실험, BOLA 공개 보고 분류 연구 등 | 취약한 예제뿐 아니라 정상 공유·공개·캐시·부분응답·권한 재부여 반례가 포함된 평가 필요 |

위의 “간격”은 전 분야에 해결책이 없다는 선언이 아니다. **확인한 연구의 입력·가정·평가 조건과 AP-EYE의 목표 조건이 다르다는 분석**이다. 가장 가까운 선행 방법을 실제로 재현한 뒤에야 방법상의 기여를 판단할 수 있다. 최근 논문별 명시적 한계와 보고서의 추론은 [최근 연구 검토](RECENT-RESEARCH-GAPS.md)에서 분리했다.

## 5. 추천 가설 여덟 가지

아래 H1–H8은 이 통합 보고서의 번호다. 개별 문헌 검토 문서의 후보 번호와 반드시 같지는 않다. 모두 **제안·NOT_RUN**이며, 선행연구는 필요성과 비교 기준의 근거이지 우리 성능의 증거가 아니다.

### H1. 최소 정책 근거를 요청하는 선택적 인가 판정 — 중심 연구 추천

**가설:** 동일한 요청·응답·계정 정보와 같은 사람 검토 예산에서, 후보별로 소유·공유·공개·행위 권한의 누락 근거를 확인하고 불충분 사례를 보류하면, 응답 유사도 또는 단일 확신도만 쓰는 방법보다 **사전에 정한 위반 재현율 하한을 유지하면서 같은 자동 판정 비율에서 정상·위반의 양방향 오류와 잘못된 위반 확정률**이 낮아진다. 모두 정상으로 판정하거나 모두 보류하는 방법이 지표상 유리해지지 않도록 한다.

- 선행 근거: [AuthScope](https://acmccs.github.io/papers/p799-zuoA.pdf)의 공개 응답 오탐 조정, [AuthProbe §VIII](https://arxiv.org/html/2607.20574v1#S8)의 객체 발견·응답 형태 한계, [EvoMaster §3.3](https://arxiv.org/html/2604.00702v1#S3.SS3)의 권한 패턴 가정과 오탐 가능성.
- 사고 연결: 정상 인증 이후 객체 조회 권한이 빠지는 유형. 정책이 안 보인다는 이유로 모든 타인 데이터를 위반으로 분류하는 반대 방향의 오류도 함께 시험한다.
- 추가할 것: `actor, tenant, object, action, share/public state, policy version, evidence source`로 최소 판정 계약을 만들고 어떤 추가 질문이 필요한지 기록. LLM은 후보와 질문을 제안할 수 있지만 확인 사실을 대신하지 않는다.
- 가장 강한 비교군: AuthProbe/Autorize식 교차 응답 검사, EvoMaster 해당 오라클, **똑같은 정책 입력을 받은 결정 규칙**, 사용자·URL별 Allowed/Denied/Unknown 규칙을 설정한 [ZAP Access Control Testing](https://www.zaproxy.org/docs/desktop/addons/access-control-testing/). 전체 정책 기준선은 정보 상한선이고 정책 없는 방법과 공정한 성능 단일 순위로 섞지 않는다. 도구의 버전·인증 설정·거부 응답 판별식을 고정한다.
- 평가·제거 실험: 정책 정보량과 검토 시간, risk–coverage, 정상 공유 오탐, 누락 사유별 보류. 관계 근거·공개 확인·정책 버전 검사를 각각 제거한다.
- 기각 조건: 같은 입력의 간단한 규칙이 동일하거나 더 좋으면 “새 지능형 판정 방법” 주장을 버린다. 자동 판정량만 크게 줄여 얻은 낮은 오류도 우월성으로 세지 않는다.
- 가능한 기여: 정책 정보 비용과 판정 가능성의 경계를 측정한 평가 방법, 필요한 근거를 고르는 절차. 단순 `unknown` 라벨 추가는 기여가 아니다.

### H2. 권한 회수 뒤 잔존 접근의 시간 계약 — 추가 독립 주제로 추천

**가설:** 권한 회수의 확인된 완료 사건과 최대 반영 기한, 계정 인증 유효성, 보호 데이터의 실제 반환을 함께 검사하면, 정적 계정 비교나 회수 직후 재요청보다 **정상 전파 지연을 오탐하는 비율과 잔존 권한 누락**을 줄일 수 있다.

- 선행 근거: [Zanzibar, USENIX ATC 2019](https://www.usenix.org/conference/atc19/presentation/pang)의 권한 변경과 데이터 변경 사이 인과적 순서. [EffectBound, 2026 프리프린트](https://arxiv.org/html/2609.02866v1)는 최종 효과까지 인가 경계를 확장하므로 “시간적 인가를 처음 다룬다”는 주장은 불가.
- 현실 근거: [pyLoad 유지관리자 공개 GHSA](https://github.com/pyload/pyload/security/advisories/GHSA-66hx-chf7-3332)는 기존 세션의 회수된 권한 잔존을 설명한다. **제품 취약점 공지이며 실제 침해 사고의 증거는 아니다.** 개인정보위의 자격증명 회수 권고는 운영 동기를 제공하지만 같은 세션 결함을 입증하지는 않는다.
- 추가할 것: 기존 admin 세션을 유지한 채 역할 회수 → 독립 관리 경로로 적용 확인 → 계약 기한 뒤 새 보호 표식 조회. 새 세션·권한 유지 계정을 대조한다.
- 비교군: 정적 역할 행렬, 회수 직후 한 번 검사, 일정 간격 재시도, **같은 시간 계약을 받은 단순 폴링 상태기계**. 시스템 자체의 Zanzibar 일관성은 외부 스캐너 성능 기준선으로 직접 치환하지 않는다.
- 평가·제거 실험: 탐지 지연, 정상 지연 오탐, 기한 미제공 사례 단정률. 독립 변경 확인·기한·기존/새 세션 대조를 제거한다.
- 기각 조건: 시간 계약이 현실 대상에서 얻기 어렵거나 단순 폴링이 동일 성능이면 범용 자동진단 주장을 축소한다. 유한한 시점 검사로 모든 노드·연속 시간의 안전을 증명하지 않는다.
- 기존 작업과 관계: 로컬의 기존 권한 회수 가설을 이번 사고·문헌 조사와 연결한 후보다. 이번에 처음 발견한 아이디어로 세지 않는다.

### H3. 정책 변경 이후 응답 필드가 따라 바뀌는지 진단 — 사건과 가장 직접 연결

**가설:** 검토된 정책 변경 이력과 스키마·매핑 버전을 응답 관측에 결합하면, 정적 개인정보 패턴 탐지나 UI 미사용 필드 검사보다 **정책 변경 뒤 남은 금지 필드의 재현율을 높이되 합법 필드를 덜 오탐**한다.

- 선행 근거: [EDEFuzz, ICSE 2024](https://arxiv.org/abs/2301.09258)의 응답 변이와 UI 동작 기반 과다노출 후보 탐지. [FlowWatcher §3.5](https://lsds.doc.ic.ac.uk/sites/default/files/ccsfp224-muthukumaran_0.pdf)는 URL·필드 변경 뒤 정책 규칙이 맞지 않으면 누락될 수 있다고 설명한다.
- 사고 연결: 개인정보위가 공개한 안심번호 전환 후 실제 전화번호가 계속 전송된 사례. 정상 로그인·정상 주문 조회여도 필요 없는 필드가 계속 나갈 수 있다.
- 추가할 것: 정책 버전별 허용 JSON 경로·목적·대상 역할, 필드 별칭 후보, 매핑 검토, 불일치·미관측 보류. 필드명이 같아도 값의 의미가 달라지는 반례를 넣는다.
- 비교군: 정적 allowlist/schema diff, 개인정보 패턴 탐지, EDEFuzz 적용 가능한 UI 사례, 같은 정책 버전을 받은 수동 회귀/규칙 검사.
- 평가·제거 실험: 변경별 탐지율, 합법 필드 오탐, 매핑 유지 비용, 버전 누락 상태의 단정률. 의미 매핑·버전 결합을 독립 제거한다.
- 기각 조건: 단순 allowlist diff가 동일하게 해결하면 독립적인 새 탐지 알고리즘의 우월성을 주장하지 않는다. 기여는 변경 유형별 실패 조건·검증 데이터셋으로 축소할 수 있다.

### H4. 질문별 최소 증거로 노출 범위를 보존 — 사후 분석 확장

**가설:** 사고 조사 질문별로 필요한 정책·응답·연결 근거만 보존하면, 동일 저장량의 고정 마스킹·고정 필드 로그보다 **허위 인물 결합과 노출 범위 오차를 줄이면서 원문 보존량을 낮출 수 있다.**

- 선행 근거: [CamFlow, SoCC 2017](https://camflow.org/publications/socc-2017.pdf)은 응용의 질의에 필요한 provenance를 선택적으로 수집하는 선행 사례다. [FlowWatcher](https://lsds.doc.ic.ac.uk/sites/default/files/ccsfp224-muthukumaran_0.pdf)는 사용자·데이터·정책 대응을 이미 사용한다. “로그를 연결한다/덜 저장한다” 자체는 신규성이 아니다.
- 사고 연결: 공개 사고마다 호출 수, 데이터 행 수, 실제 수신 필드, 고유인 수가 다름. 요청 메타데이터만 있으면 실제 응답의 노출을 복원할 수 없는 경우가 생긴다.
- 추가할 것: 요청자·테넌트·회원 체계 안에서의 연결, 관측 필드 집합·정책/매핑 버전·수집 누락 표시. 사람 수를 모르면 모른다고 출력한다. 식별자를 해시한 것만으로 익명성을 보장했다고 하지 않는다.
- 비교군: 원문 전체, 메타데이터만, 현재 마스킹, 고정 필드, 질의별 선택. **같은 보존 데이터에 SQL/규칙과 제안 분석기를 모두 적용**해 입력량 효과와 방법 효과를 분리한다. CamFlow와는 계층이 달라 전체 시스템 벤치마크 수치를 직접 비교하지 않는다.
- 평가·제거 실험: 바이트 수·원값 보존 필드 수, 질문별 정답률, 잘못된 확정률, 중복/다른 테넌트 결합 오류. 반환 필드·연결 키·정책 버전을 각각 삭제하고 누락률을 바꾼다.
- 기각 조건: 단순 고정 필드 기록이 동일 비용·오류를 달성하면 적응적 선택의 장점은 없다. 원문 분석기와 결과가 같아도 독립 정답에 둘 다 틀리면 성공이 아니다.
- 기존 작업과 관계: 기존 AP-EYE 사후 증거 분석 가설의 연장이다. 전체 미관측 피해 규모 추정과는 구분한다.

### H5. 응답 성공이 아닌 실제 변경을 확인하는 쓰기·비동기 인가 진단

**가설:** 동일 요청 예산에서 정책상 금지된 실행의 독립적인 사후 효과를 확인하면, HTTP 상태/응답만 보는 검사보다 잘못된 성공·실패 판정을 줄인다.

- 선행 근거: [RESTler 보안 속성 연구](https://www.microsoft.com/en-us/research/publication/checking-security-properties-of-cloud-services-rest-apis/), [BACFuzz](https://arxiv.org/html/2507.15984v1)의 런타임·SQL 근거, [EffectBound](https://arxiv.org/html/2609.02866v1)의 최종 효과 경계. 이들은 이미 상태·효과를 다루므로 단순 기능 합침은 차별성이 약하다.
- 사고/표본 연결: [2026 BOLA taxonomy](https://arxiv.org/html/2605.25865v1)에서 분류된 BOLA 84건 중 41.7%는 상태 변경 유형. 공개 표본의 분포이며 전체 산업 비율은 아니다. 첨부의 개별 유출 사고가 쓰기 공격이었다고 추정하지 않는다.
- 추가할 것: 격리 시험 서버의 수정·삭제·내보내기 큐와 독립 읽기 검증 경로. 요청 거부처럼 보이지만 효과가 생김, 202 수락 뒤 실패, 재시도 중복, 권한 회수 뒤 완료를 구분.
- 비교군: 상태코드, 응답 본문, 같은 사후 상태를 받은 결정 규칙, 적용 가능한 EvoMaster/BACFuzz 오라클. SQL 접근 가능 여부를 별도 실험 조건으로 둔다.
- 평가·제거 실험: 효과 판정 precision/recall, 잘못된 확정, 검증/초기화 비용. 독립 effect 조회와 전후 상태 비교를 제거한다.
- 기각 조건: 효과를 볼 수 없는 대상이 대부분이거나 기존 effect 방법과 같으면 범용성·신규성은 제한적. 현재 GET 데모에서 확장 비용이 커 후순위.

### H6. 적게 관측한 트래픽에서 검사 대상을 고르는 방법

**가설:** 트래픽 빈도 대신 정책·객체 의존성과 명세/배포 목록의 차이를 이용해 검사 순서를 정하면, 같은 요청 수에서 임의·빈도·스키마 순회보다 더 다양한 원인의 결함을 찾는다.

- 선행 근거: RESTler의 상태·생산자/소비자 의존성, RESTTESTGEN·RESTest의 명세 기반 생성, [EvoMaster §3.7](https://arxiv.org/html/2604.00702v1#S3.SS7)의 숨겨진 접근 가능 경로 검사는 이미 존재. 정확한 서지는 [연대기](LITERATURE-HISTORY.md) 참조.
- 사고 연결: 구버전 API 잔존과 METR의 공개 경로 관리 문제. 트래픽에서 한 번도 보지 못한 엔드포인트는 수동 관찰만으로 발견할 수 없다.
- 추가할 것: 시험 배포의 알려진 endpoint 집합을 평가 정답으로 두고, 진단기에 보이는 트래픽 비율·오래된 OpenAPI·미등록 경로를 통제. 운영 자산 전체 자동 발견을 가정하지 않는다.
- 비교군: 랜덤, 빈도순, 명세 coverage 순, 기존 의존성 기반 방법. 새 방법만 완전한 배포 목록을 받지 않게 입력을 맞춘다.
- 평가·제거 실험: 요청 수 대비 원인별 recall, 최초 발견 비용, 미관측 endpoint 비율. 정책 신호와 의존성 신호를 각각 제거.
- 기각 조건: 기존 coverage 최적화로 충분하면 독립 연구성이 약하다. 보안 결함보다 단순 endpoint 수만 늘면 가설을 지지하지 않는다.

### H7. 한국어 API 필드에서 정보 부족과 모델 오류를 분리

**가설:** 문맥의 출처·버전·충돌 여부와 분류 확신도를 분리하면, 동일 모델·입력·검토량에서 확신도만 사용하는 보류보다 잘못된 개인정보 유형 채택이 감소한다.

- 선행 근거: [Towards Contextual Sensitive Data Detection, 2025/2026](https://arxiv.org/html/2512.04120v2), [Detection of Personal Data in Structured Datasets Using a Large Language Model, 2025 워크숍](https://dbpmworkshop.github.io/files/personaldata.pdf), [Two Axes of LLM Abstention, 2026 프리프린트](https://arxiv.org/html/2607.08456v1). 문맥 활용·두 축 구분은 선행연구에 있다.
- 사고 연결: 과다 반환 필드의 유형과 우선순위 입력을 개선하는 보조 연구. 이를 잘한다고 객체 인가나 법적 개인정보 여부가 자동 확정되는 것은 아니다.
- 비교군: 정규식/규칙, 동일 모델의 문맥 분류, 확신도 보류, 두 축 보류, 단순 스키마 버전 검사.
- 평가·제거 실험: 출처·템플릿 분리 평가셋에서 같은 자동 처리율 오류, 정보 부족 단정률, 검토량·지연. 근거검사 없이도 동일 정보가 제공되는 조건과 비교한다.
- 기각 조건: 단순 문맥/버전 규칙과 차이가 없거나 기존 개발용 KO96에서만 이점이 있으면 일반화 주장을 철회한다.
- 기존 작업과 관계: 기존 로컬 한국어 필드 연구계획의 연장. 새로운 인가 진단 알고리즘과는 별도 기여로 다룬다.

### H8. 실제 원인과 정상 반례를 반영한 인가 진단 벤치마크

**가설:** 취약한 GET 예제 중심 평가에서 좋은 도구의 순위는 정상 공유·회수 지연·상태 변경·정책 변경·관측 누락을 포함하면 유의하게 달라진다.

- 선행 근거: [BOLA taxonomy §8](https://arxiv.org/html/2605.25865v1#S8)의 표집·라벨 불확실성, [AuthProbe §VIII-A](https://arxiv.org/html/2607.20574v1#S8.SS1)의 합성 대상 외적 타당성 한계, [EvoMaster 연구](https://arxiv.org/html/2604.00702v1)의 여러 API 평가.
- 추가할 것: 실제 공개 원인에서 추출한 **원인 단위의 합성 재구성**과 정상·수정 counterpart, 독립 라벨 검토, 도구의 적용 가능/불가능/오류/미탐을 분리한 실행 계약.
- 비교군: 기존 crAPI/VAmPI 중심 평가와 확장 평가를 동일 도구·버전·예산으로 수행. 원래 도구가 지원하지 않는 언어를 미탐으로 점수화하지 않는다.
- 평가·제거 실험: 원인별 recall·정상 반례 false-positive·순위의 신뢰구간. 정상 반례와 시간/상태 조건을 하나씩 제거해 순위 변화의 이유를 확인한다.
- 기각 조건: 결과가 동일하거나 독립 라벨 합의가 낮으면 순위 왜곡 주장은 성립하지 않는다. 그래도 재현 가능한 데이터·실행 계약은 제한된 산출물이 될 수 있다.
- 주의: 기업 운영환경을 그대로 재현했다고 부르지 않는다. 공격자가 실제 이용한 상세가 공개되지 않은 사건은 특정 결함의 정답으로 만들지 않는다.

## 6. 선정 우선순위와 연구를 줄이는 기준

| 후보 | 현재 프로젝트 연결성 | 직접적인 사고 연결 | 신규성 위험 | 추천 |
|---|---|---|---|---|
| H1 최소 정책·선택적 판정 | 높음: 교차 계정 검사·공유 반례 | 높음 | 높음: AuthScope/AuthProbe/EvoMaster와 정면 비교 필요 | 팀 중심 연구. 정책 비용-오류 관계로 좁히기 |
| H2 권한 회수 시간 | 중간: 전이·독립 확인 추가 | 공식 취약점 + 운영 권고 | 중간~높음: Zanzibar/EffectBound와 차이 명시 | 팀원 BOLA와 분리되는 추가 주제 |
| H3 정책-응답 필드 변경 | 높음: 필드 매핑·관측 | 매우 직접적: 안심번호 전환 사례 | 중간~높음: EDEFuzz/FlowWatcher 및 단순 diff | 개인정보 노출 중심 대안 |
| H4 최소 증거 | 높음: 기존 DB 사후 분석 | 범위 산정의 실무 필요 | 높음: 기존 provenance·선택 보존과 비교 | H1 또는 H3의 보조 연구 |
| H5 쓰기·비동기 효과 | 낮음~중간 | 공개 BOLA 표본의 상태 변경 | 높음: 효과 검증 선행 존재 | 장기 확장 |
| H6 검사 대상 선택 | 중간 | 구버전·미관리 API | 높음: fuzzing 연구 밀집 | 파일럿에서 이점 확인 때만 확대 |
| H7 한국어 문맥 충분성 | 높음: 현재 분류 모듈 | 간접적 | 높음: 문맥/보류 선행 존재 | 개인 분류 연구로 분리 |
| H8 원인 기반 벤치마크 | 중간 | 높음, 상세 원인 공개 사례 한정 | 중간: 기존 dataset과 차이 입증 | 모든 후보의 공통 평가 토대 |

여덟 가지를 동시에 구현하면 각 기여의 검증이 약해진다. **H1 또는 H3 하나를 주 방법으로, H8을 평가 토대로** 시작하는 구성이 현실적이다. 팀원과 주제가 겹치면 H2를 별도 축으로 삼되 데이터·수집기를 공유한다. H4·H7은 이미 로컬 연구계획이 있으므로 신규 후보 수를 부풀리는 데 사용하지 않는다.

## 7. 최소 실험 설계: 무엇을 해야 논문 주장이 되는가

### 공통 정답 계약

시험 사례는 `주체, 테넌트, 객체, 행위, 관계, 정책 버전, 시점, 관측 범위`로 정의한다. 정답은 구현자가 심어 놓은 버그 이름이나 탐지기의 출력만으로 만들지 않는다. 독립 검수자가 정책과 보호 자산·변경 효과를 확인하고 불일치를 조정한다.

정상/위반의 실제 정답과 **진단기에게 주어진 증거로 판정 가능한가**를 별도 라벨로 둔다. 실제로 위반인 사례라도 응답이 유실되어 진단기가 확정할 근거가 없을 수 있다. 이때 “근거 없는 확정”과 “보수적 보류”를 같은 오답으로 뭉개면 H1/H4를 평가할 수 없다.

### 파일럿 구성

1. 비공개 타인 객체, 공개 객체, 명시적 공유, 정상 관리자 접근, 다른 테넌트의 동일 ID, 필드별 권한, 회수 뒤 지연, 토큰 만료, 응답 누락, 구버전 경로 등 원인·반례를 선정한다.
2. 각 원인에 취약/수정/정상 예외 사례를 만들고, 서로 다른 API 구조에서도 반복한다. 초기 목표는 라벨·실행 계약이 작동하는지 확인하는 것이며 임의의 작은 표본으로 통계적 검정력을 주장하지 않는다.
3. 공개 예제는 개발용으로 사용한다. 최종 평가는 코드베이스·작성자·템플릿을 분리하고 버전·설정·정책을 동결한다. 동일 사례의 이름만 바꾼 변형을 독립 표본으로 세지 않는다.
4. 같은 입력의 규칙 기준선을 먼저 실행한다. 실패 원인이 데이터 부족인지 생성 실패인지 오라클 오류인지 나누어 기록한다.
5. 파일럿의 분산·실패율로 본 평가 크기를 결정하고, 측정 지표·종료 기준·제외 조건을 먼저 고정한다.

### 필수 지표

- 취약점 후보 단위 및 원인 단위 precision/recall, 정상 공유·권한 지연 등 조건별 false-positive.
- 자동 판정 비율과 그 구간의 오류율, 보류율·사유, 근거 없는 단정률.
- 설정 시간·정책 입력 수·계정/객체 준비 비용·요청 수·p50/p95 지연.
- H4는 실제 관측 노출 범위 오차·허위 연결·보존량, H2는 탐지 지연과 기한 이후 잔존 접근을 추가.
- 도구 실행 실패·미지원·미관측·초기화 실패는 결과표에 남긴다. 401·403·404·429·5xx를 서로 같은 “안전”으로 묶지 않는다.

신뢰구간과 반복 실행을 제시하되, 통계 단위는 요청 수가 아닌 독립 서비스/정책·원인 사례를 중심으로 잡는다. 여러 후보 중 유리한 결과만 보고하지 않도록 후보·지표·제외 규칙을 사전 등록한다. **간단한 비교 방법과 차이가 없다는 결론도 보존한다.**

## 8. 발표와 논문에서 사용할 수 있는 표현

> 최근 API 관련 공개 사례는 인증 여부만으로 충분하지 않으며, 객체·필드·정책 변경·운영 경로를 함께 검증해야 함을 보여준다. 기존 연구는 코드 분석, 다중 신원 실행, 상태 기반 fuzzing, 응답 관측으로 이 문제를 다루어 왔다. AP-EYE는 이 방법들을 처음 제안한다고 주장하지 않는다. 본 연구에서는 제한된 정책·관측 조건에서 판정 가능한 사례와 추가 확인이 필요한 사례를 구분하고, 같은 검토 비용에서 오판과 노출 범위 오류가 줄어드는지 검증한다.

피해야 할 표현: “세계 최초”, “권한 정보가 전혀 필요 없다”, “타인 데이터가 보이면 무조건 취약점”, “개인정보 패턴이면 법적 위반”, “HTTP 200이면 유출”, “잠재적 record 수=실제 피해자 수”, “관측되지 않음=발생하지 않음”.

## 9. 자료 접근과 검증 상태

자료별 확인 범위는 [검증 기록](VERIFICATION.md)에 있다. [킥오프 검토](KICKOFF-REVIEW.md)는 원본을 보존하면서 발표 표현을 수정할 근거를 제공한다. 최신 연구는 [최근 연구·공백](RECENT-RESEARCH-GAPS.md), 과거 흐름은 [연대기](LITERATURE-HISTORY.md), 공개 사건은 [사고 원장](INCIDENTS.md)에서 각각 확인할 수 있다.

현재 저장소의 구현 경계는 [아키텍처 문서](../../데모코드/docs/architecture.md)를 기준으로 확인했다. 운영 배포나 외부 대상 공격은 하지 않았다. 기존 로컬 실험 수치를 새로운 독립 평가로 바꾸어 보고하지 않았으며, 제안 가설의 성능은 모두 후속 실험이 필요하다.
