# 구현 순서와 검증 계획

2026-09-21 제안. 개발 인원·기간 답변이 없어 4인·8주를 가정했다. 아래 숫자는 평가 목표와 실험 설계이며 측정 결과가 아니다. 전일제 개발을 보장받은 일정도 아니다.

## 1. 개발 순서의 원칙

**정답이 있는 작은 인가 검증을 먼저 완성하고, 그 다음 개인정보·LLM·대시보드를 연결한다.** 게이트웨이와 UI부터 크게 만들면 잘못된 판정이 보기 좋게 표시되는 상태가 될 수 있다.

첫 수직 기능은 아래 한 흐름이다.

```text
합성 상담 API
 -> APISIX 통과
 -> 이벤트 1건 수집
 -> 소유자 A와 타인 B 비교
 -> 승인된 규칙 위반 확인
 -> /reason의 개인정보 후보 표시
 -> 근거를 담은 Markdown finding 생성
```

UI가 완성되기 전 CLI/JSON/Markdown으로 end-to-end 결과를 확인한다. LLM 없이 동작하는 기준선을 먼저 확보해야 LLM이 더한 효과를 측정할 수 있다.

## 2. 8주 개발안

| 주차 | 구현 | 완료 증거 |
|---|---|---|
| 1주 | 서비스 범위·권한표, Compose, APISIX, 합성 API, 수집 연결 | 정상 요청 통과와 이벤트 연결, 정책 초안, golden fixture |
| 2주 | 인벤토리·경로 정규화, 테스트 계정 로그인, 데이터 계약 | 약 12 operation 목록, 계정별 신원 검증, 본문 누락 표시 |
| 3주 | BOLA/BFLA 비교기, 승인 정책 평가, 결과 상태 | 공개·공유·타인·조직 경계 사례 판정과 증거 |
| 4주 | 읽기 BOPLA, 안전한 수집 플러그인, 회귀 테스트 | 공개 프로필의 비공개 필드만 탐지, 로그 비밀 제거 |
| 5주 | Presidio 적용·한국 유형 검증·법령 매핑 | 정형 탐지 기준선, 오탐·미탐 사례, 매핑 근거 |
| 6주 | 로컬 LLM 문맥 분류·출력 검증·검토함 | LLM 없는 방식과 비교, 보류·주입문·장애 처리 |
| 7주 | 결과 대시보드·점수 범위·집계·Markdown 리포트 | 증거부터 점수까지 추적 가능한 데모 |
| 8주 | 독립 평가·성능·장애·문서·패키징 | 재현 가능한 평가 결과, 한계, 버전·라이선스 기록 |

3주차 종료 시 인가 판정이 안정되지 않으면 실시간 차단·사진 분석을 추가하지 않는다. 6주차 종료 시 LLM의 추가 효과가 없으면 그 결과를 그대로 보고하고, 검토 보조 기능으로 제한한다.

## 3. 역할 배치 예시

| 역할 | 담당 기능 | 주요 연결점 |
|---|---|---|
| A: 게이트웨이·수집 | APISIX, 본문 처리, 이벤트·메트릭 | 이벤트 계약을 B/C/D와 먼저 고정 |
| B: 인가 엔진 | 정책, 계정·객체 fixture, 비교·판정 | C의 분류를 기다리지 않고 독립 진단 가능 |
| C: 개인정보·LLM | 정형 인식, 법령 팩, 문맥 분류, 평가셋 | 증거 ID와 JSON path로 B 결과에 연결 |
| D: 서비스·UI·통합 | 제어 API, DB, 권한표·결과 화면, 리포트 | 초반에는 합성 서비스와 API 계약을 우선 |

테스트 정답 작성·라벨 검토는 교차 수행한다. 한 사람이 생성한 데이터와 본인이 튜닝한 프롬프트만으로 성능을 검증하지 않는다. 실제 팀원의 이름이나 확정 담당으로 해석하지 않는다.

## 4. 가장 먼저 구현할 백로그

1. **권한표**: 공개 프로필, 비공개 상담, 공유 문서, 관리자 내보내기의 정답을 확정한다.
2. **합성 데이터**: T1/T2 조직, 소유자·일반 사용자·상담사·관리자, 공유/비공유 객체를 만든다.
3. **취약/수정 버전**: 동일 API에서 객체 검사 누락·필드 필터 누락·관리자 검사 누락을 독립 토글한다.
4. **실행 환경 고정**: API·gateway·DB 이미지와 소스 commit을 기록한다.
5. **실제 신원 검사**: 테스트 요청 전후 계정 신원을 확인하고 세션 혼합을 막는다.
6. **비교기**: 200·403·404보다 본문·객체 관계·허용 필드를 먼저 근거로 삼는다.
7. **판정 상태**: UNKNOWN 정책과 timeout이 취약/안전 양쪽으로 잘못 들어가지 않도록 한다.
8. **수집기**: 테스트 요청과 수집 증거의 trace ID를 연결한다.
9. **정형 분류**: 기존 Presidio 한국 인식기의 실제 지원·정확도를 확인한다.
10. **최초 Markdown 리포트**: 원문 비밀 없이 재현 증거·정책·노출 항목을 설명한다.

이 10개가 끝나면 교수님에게 5분짜리 수직 데모를 보여줄 수 있다. 전체 대시보드 디자인이 끝날 때까지 시연을 미루지 않는다.

## 6. 평가용 서비스 선택

### 주 평가: 직접 만든 합성 서비스

공개/비공개/공유/담당자/조직/관리자/필드 제한을 정확히 정의할 수 있는 상담·프로필·문서 서비스 하나를 만든다. 관계와 문구를 합성하고 실제 사건 피해자 데이터를 사용하지 않는다.

추천 operation 예시:

```text
GET /me
GET /profiles/{userId}
GET /consultations
GET /consultations/{consultationId}
GET /consultations/{consultationId}/summary
GET /documents/{documentId}
GET /documents
GET /admin/consultations/export
GET /admin/users
GET /health
POST /test/session
POST /test/reset
```

로그인·초기화용 마지막 두 operation은 스캐너의 일반 진단 대상에서 제외하고 격리 lab 제어 경로로만 사용한다. 공개 프로필와 비공개 상담은 같은 서비스에 있어야 맥락 차이를 실제로 평가할 수 있다.

### 보조 평가: OWASP crAPI

crAPI는 의도적으로 취약하게 만든 교육·실습용 API이므로 외부 재현 사례를 추가하는 데 적합하다. 하지만 공개/공유 정상 예외와 한국어 개인정보의 정답셋을 모두 대신하지 못한다. [공식 저장소](https://github.com/OWASP/crAPI)

첨부 자료에 crAPI 성공 기록이 있다. 개발 시작 시 남아 있는 원본 요청·응답, 계정·객체 관계, 서비스 버전, solver를 먼저 확인해 재사용한다. 이 조사에서는 서버를 실행하거나 취약점 재현을 다시 하지 않았다.

## 7. 인가 진단 평가

### 실험군

| 군 | 구성 | 목적 |
|---|---|---|
| A | 신원/소유자 불일치 단순 규칙 | 기존 기획의 실패 조건 확인 |
| B | status·응답 유사도·필드 차이 비교 | 정책 없는 비교의 한계 측정 |
| C | 승인 정책 + 신뢰 fixture + 결정적 비교 | 주 제안의 탐지 기준선 |
| D | C + LLM 정책 초안·검토 지원 | 판정 성능과 별개로 정책 작성 시간 측정 |
| 외부 비교군 | 동일 범위의 ZAP Access Control 또는 Akto | 기존 도구와 중복·차이 확인 |

ZAP은 Allowed/Denied/Unknown 접근 규칙과 사용자 설정을 사용한다. 같은 정책 정보를 외부 비교군에도 제공하고 설치·튜닝 시간을 기록해야 공정하다. [ZAP 공식 절차](https://www.zaproxy.org/docs/desktop/addons/access-control-testing/)

Akto의 제품 전체 기능과 특정 OSS 버전에서 실행한 기능을 구분한다. 설치하지 않은 기능은 `NOT_RUN`으로 기록하고 기능 부재나 탐지 실패로 점수화하지 않는다.

### 정답셋

초기 제안은 시나리오 그룹 60개다: 정상 24개, 명확한 위반 24개, 정책 불명확/실험 불완전 12개. 취약/수정 버전 쌍에서 각 실행의 기대 결과를 미리 작성한다. 같은 시나리오를 10번 반복해도 독립 사례가 10배 늘었다고 주장하지 않는다.

문서·필드명·ID만 바꾼 변형이 학습/검증/시험에 섞이지 않도록 시나리오 가족 단위로 분리한다. BOLA·BFLA·BOPLA와 정상 공개/공유/타 조직/담당자/캐시 사례를 별도로 집계한다.

### 지표

- 위반 precision = 참 위반 확정 / 모든 위반 확정.
- 전체 위반 recall = 확정한 참 위반 / 실제 위반 전체. 실제 위반의 보류·미실행도 미탐 분모에 남긴다.
- 정상 오탐률 = 정상인데 위반 확정 / 정상 전체.
- 보류율 = NEEDS_REVIEW / 전체, 실험 불완전율과 미실행률은 별도.
- 자동 판정 coverage = 자동 확정/위반 미관측 결과 수 / 전체.
- 공개·공유 정상 사례의 오탐률, 타 조직 접근 탐지율을 분리한다.
- API별 테스트 설정 시간, 정책 작성·수정 시간, 증거 검토 시간을 측정한다.

권한이 없는 접근을 놓치는 오류와 정상 업무를 잘못 막는 오류를 함께 보고한다. 보류가 많은 시스템은 precision만 높아 보일 수 있으므로 coverage·recall을 항상 같이 제시한다.

## 8. 개인정보·LLM 평가

### 비교군

1. 기본 정형 탐지기.
2. 정형 탐지기 + 한국어 필드·맥락 규칙.
3. LLM 단독 후보 분류.
4. 규칙 + LLM + 검토 보류의 결합 방식.

두 질문을 분리한다: ‘문자열에서 개인정보 표현을 찾았는가’와 ‘개인과 연결된 의미를 정확한 법령 범주로 매핑했는가’.

### 데이터

500개 합성 한국어 샘플을 시작점으로 제안한다. 개발 300, 검증 100, 최종 시험 100으로 가족 단위 분리한다. 개인정보/비개인정보, 일반/민감/고유식별정보, 부정·일반론·인용문·가족 관련 문구, 불명확 사례를 포함한다. 최소 2명이 라벨을 검토하고 합의하지 못한 샘플은 별도 ambiguity 정답으로 남긴다.

기본 인식기를 재사용하므로 식별번호 탐지 개선과 LLM 문맥 개선을 한 수치로 섞지 않는다. 일반 문장을 건강정보라고 과잉 분류하는 오류도 측정한다. 고정 법령 팩을 프롬프트에 제공하고 테스트셋 결과를 보고 튜닝하지 않는다.

### 지표

| 평가 대상 | 지표 |
|---|---|
| 개인정보 표현 위치 | span precision/recall/F1 |
| 법령 분류 | 유형별 precision/recall, macro-F1, 혼동행렬 |
| 잘못된 법적 매핑 | 일반 UUID→고유식별정보, 일반 사진→생체 민감정보 등 오류율 |
| 근거 품질 | 존재하는 원문 span 비율, 사람이 근거를 수용한 비율 |
| 불확실성 처리 | 보류율과 보류에 포함된 실제 오류 비율 |
| 운영 비용 | 필드당 처리시간, 호출 비율, 입력/출력 토큰, 메모리 |
| 주입문 견고성 | 동일 의미 입력에 명령문 삽입 전후 분류 변경률·스키마 오류율 |

사람에게는 모델 결과를 가린 상태로 정답을 작성하게 한다. 모호한 법적 분류를 팀 합의만으로 확정 사실처럼 보고하지 않고 ‘프로젝트 정답 기준’과 전문가 검토 여부를 명시한다.

## 9. 우선순위와 집계 평가

- 전문가 또는 교수님이 정한 수정 순위와 시스템의 top-k 일치율·순위 상관을 비교한다.
- 법정 공식 점수가 있다고 전제하지 않는다. 비교 기준을 제시한 검토자와 사유를 기록한다.
- 1명이 여러 객체·여러 API에 반복 등장하는 fixture로 중복 집계를 확인한다.
- 한 응답에 여러 사람이 있는 경우와 주체 키 없는 경우를 포함한다.
- 정상 접근과 테스트 요청이 사고 노출 건수에 들어가지 않는지 확인한다.
- 샘플링·드롭·잘림을 의도적으로 넣고 실제 전체 수를 확정 표시하지 않는지 확인한다.
- 가중치 민감도 실험에서 순위가 불안정한 finding은 순위 범위를 표시한다.

## 10. 성능·장애 검증

비교 환경은 ① API 직접 호출 ② APISIX 기본 ③ APISIX + 수집 ④ 수집 + 비동기 분석으로 나눈다. LLM 처리 지연과 사용자 API 응답 지연을 별도 측정한다.

초기 실험 조건 제안: 10KB JSON, 100 RPS, 고정된 동시성, warm-up 후 5분 측정, 3회 반복. 큰 응답·압축·수집 제외 경로는 별도 실험으로 둔다. 같은 하드웨어·API·데이터로 비교한다.

초기 수용 목표 제안:

| 항목 | 목표와 해석 |
|---|---|
| gateway 수집 추가 p95 지연 | 기본 APISIX 대비 10ms 이내를 목표로 검증. 보장값 아님 |
| 정상 요청 결과 | 수집 유무에 따른 status·본문의 의도치 않은 변화 0건 |
| LLM·분석 장애 | API 전달은 유지, 분석 누락 상태 표시 |
| drop 관측 | 유실을 숨기지 않고 카운터·시간 구간 표시 |
| 검토 화면 | 비밀값 없이 정책·응답 필드·법령 근거 추적 가능 |
| 원문 비밀값 | 보고서·일반 로그·프런트엔드 응답에 토큰·Cookie 출력 0건 |

하드웨어·OS·컨테이너 메모리·모델 양자화·context length·실행 버전을 결과와 함께 남긴다. 일정과 장비 확인 후 기준을 조정하되 최종 평가 직전에 유리하게 바꾸지 않는다.

## 11. 장비와 비용 판단

우선 학교/팀의 기존 PC 또는 내부 Linux 서버에서 개발한다. Windows는 Linux 컨테이너 환경을 사용할 수 있지만 네트워크·GPU 설정은 장비별로 검증해야 한다.

실습 구성 제안은 RAM 32GB급 한 대, LLM은 선택적 GPU 사용이다. 이는 구매 권고나 최소 사양 보장이 아니다. API·DB·crAPI·모델을 모두 실행하면 요구량이 늘어난다. GPU가 없다면 작은 모델 또는 CPU 비동기 분석으로 정확도와 처리시간을 먼저 측정한다.

8B급 4bit 모델은 가중치만 단순 계산하면 약 4GB 규모지만, 실제 추론은 추가 메타데이터·KV cache·runtime·context 메모리가 필요하다. VRAM 8GB에서 반드시 충분하다고 가정하지 않는다. 모델 후보·컨텍스트를 정한 뒤 실측으로 결정한다.

기본 계획은 외부 유료 LLM API 호출 없이 수행한다. 비용은 장비·전력·운영 시간에 좌우된다. 외부 모델 비교가 필요해지면 합성 데이터로만 별도 실험하고 실제 과금 단가를 그 시점에 확인한다.

## 12. 일정이 부족할 때 줄일 것

| 조건 | 유지할 핵심 | 줄일 범위 |
|---|---|---|
| 2인 또는 4주 수준 | 합성 API, 정책 기반 BOLA/BOPLA, 정형 분류, Markdown 결과 | 대시보드 규모, LLM 정책 작성 보조, 다중 도메인 |
| 4인·8주 | 본 문서 MVP | 실시간 차단, 이미지, Kubernetes, 사고 자동 신고 |
| 12주 이상과 여유 장비 | 기본 MVP의 독립 검증 | 그 후 OCR·비전, 승인 정책 실시간 적용을 하나씩 추가 |

범용 API 보안 전체, 모든 개인정보 법령, 이미지 이해, 무설정 인가 학습을 동시에 완성 목표로 두면 일정상 위험하다. 지원하는 서비스·정책·프로토콜·데이터 범위를 명확하게 제한한다.

## 13. 졸업작품 완료 기준

1. 내부망에서 정해진 설치 절차로 시작하고 명시한 REST/JSON 범위에서 트래픽을 관측한다.
2. 공개·공유·조직 경계·역할 사례를 구분하고 BOLA/BFLA/BOPLA 근거를 보여준다.
3. 개인정보 분류에 법령 근거와 검토 상태를 연결한다.
4. 자체 점수식의 입력과 불확실성을 설명한다.
5. 관측 범위·누락·테스트 노출·사고 관측의 차이를 보고서에 남긴다.
6. LLM을 뺀 비교군과 평가해 추가 효과·오류·비용을 수치로 제시한다.
7. 취약/수정 버전에서 정상 업무 보존과 회귀 결과를 제시한다.
8. 모든 아키텍처·설정 계약·평가 절차·한계를 Markdown으로 제공한다.

## 14. 교수님께 보여줄 5분 데모

1. API 목록에서 공개 프로필·비공개 상담·관리자 기능을 보여준다.
2. 공개 프로필을 B로 조회해 정상 처리되는 것을 보여준다.
3. 공개 프로필에 이메일을 반환하는 버그를 켜고 BOPLA 근거를 보여준다.
4. 비공개 상담의 객체 인가 버그를 켜고 BOLA를 재현한다.
5. 한국어 건강 문구와 일반 상담 문구를 비교해 분류·보류를 보여준다.
6. 수정 버전으로 다시 테스트하고 정상 사용자·담당자 접근이 유지되는 것을 보여준다.
7. 마스킹된 근거·정책 버전·관측 규모가 담긴 Markdown 보고서를 내보낸다.

시연 성공과 독립 평가 성능은 구분해 발표한다. 소수 시연 사례만으로 실서비스 전체에 대한 정확도나 법적 판단 능력을 주장하지 않는다.
