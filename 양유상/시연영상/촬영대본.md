# 킥오프 데모 직접 촬영 대본

예상 길이는 설명 속도와 조작에 따라 약 4–6분입니다. 숫자는 촬영 편집을 위한 참고 시각이며, 화면 조작이 끝난 뒤 설명을 이어가면 됩니다. 화면에 실제 합성 결과가 다르게 나타나면 대본 숫자에 맞춰 바꾸지 말고 화면의 결과를 그대로 설명합니다.

## 촬영 전 준비

1. [`데모코드`](../데모코드/README.md)의 안내에 따라 데모 서버를 시작합니다. AI 실험실에서 직접 추론을 보여주려면 로컬 SemIf 작업자도 준비하고 화면의 연결 상태를 확인합니다.
2. 브라우저에서 `http://127.0.0.1:8810`을 열고 저장된 합성 실행이 보이는지 확인합니다.
3. 브라우저 전체 화면으로 녹화하고, 마이크 음량과 화면 글자 크기를 짧게 점검합니다. 주소창의 개인 계정 정보, 토큰, 실제 업무 화면은 녹화하지 않습니다.
4. 사후 조사에서는 저장 실행 `incident-4bf3904446c9`, 계정 `bob`을 선택합니다. 한국어 분류 예시는 `ko96-h01`과 `ko96-o01`을 사용합니다.

## 장면별 화면과 멘트

### 1. 도입 — 프로젝트와 범위 (약 15초)

**화면:** 제목 화면 또는 대시보드 첫 화면. 합성 데이터라는 안내를 함께 보여 줍니다.

**멘트:** “안녕하세요. 저희는 API 인가 취약점과 개인정보 노출 범위를 함께 살펴보는 내부망 보안 게이트웨이를 만들고 있습니다. 오늘은 인가 제어, 저장 로그 기반 사후 조사, 한국어 개인정보 분류 실험을 보여드리겠습니다. 모든 화면은 로컬 합성 데이터입니다.”

**자막:** `API 인가 제어 · 사후 로그 조사 · 한국어 개인정보 분류`

### 2. 인가 제어 — 취약·수정 정책 비교 (약 35초)

**화면:** 대시보드에서 취약 모드와 수정 모드를 차례로 실행하고 인가 판정 화면을 엽니다. 가능한 경우 공개 프로필·공유 문서처럼 정상적으로 허용된 예도 함께 보여 줍니다.

**멘트:** “같은 요청을 취약 정책과 수정 정책에서 비교합니다. 판정은 다른 사람의 데이터가 보였는지 또는 HTTP 200이었는지만으로 내리지 않습니다. 객체 범위, 역할, 테넌트, 허용 필드와 실제 응답을 함께 봅니다. 공개 프로필이나 공유 문서처럼 설계상 허용된 접근은 위반으로 단정하지 않습니다.”

**자막:** `요청 대상 · 실제 응답 필드 · 승인 정책을 함께 비교`

### 3. 요청·응답 로그와 필드 결합 (약 35초)

**화면:** 이벤트 화면에서 추적 ID·요청자·경로·상태를 보여준 뒤 필드 매핑 화면으로 이동합니다. 서로 다른 필드 이름의 alias 후보와 테넌트 구분을 보여 줍니다.

**멘트:** “요청과 응답 요약을 추적 ID, 계정, API 경로와 연결해 저장합니다. 필드 매핑에서는 `member_id`와 `customer_no`처럼 이름이 다른 필드를 같은 의미 후보로 정규화합니다. 정규화만으로 동일인을 확정하지 않고, 확인된 식별자와 테넌트·실행 범위가 맞을 때만 필드를 결합합니다. CIM의 공통 필드 개념을 참고한 실험이며 공식 호환 인증을 뜻하지 않습니다.”

**자막:** `원본 alias 보존 · 확인된 키와 테넌트 경계 안에서 결합`

### 4. 저장 로그 기반 사후 조사 — 응답 증거 포함 (약 30초)

**화면:** 사후 로그 분석으로 이동해 저장 실행 `incident-4bf3904446c9`, 계정 `bob`, 저장된 응답 증거 포함 모드를 선택하고 분석합니다. 요약과 API별 기록을 잠시 멈춰 보여 줍니다.

**멘트:** “이 화면은 API를 다시 호출하지 않고 이미 저장된 로그를 읽습니다. 이 합성 실행에서 계정 bob의 호출 13건, API 8종, HTTP 2xx 11건, 정책 위반 근거가 기록된 응답 7건, 응답에서 관측된 정보주체 3개를 확인할 수 있습니다. 이는 이 실행에서 확인한 관측 범위이지 실제 사고 전체 피해 규모가 아닙니다.”

**자막:** `저장된 합성 실행의 관측값 | 13회 호출 · 8개 API · 정보주체 3개`

### 5. 저장 로그 기반 사후 조사 — 메타데이터만 있는 경우 (약 20초)

**화면:** 증거 모드를 메타데이터 전용으로 바꾸어 다시 분석합니다. 조회 대상·응답 항목이 `알 수 없음`으로 바뀌는 부분을 보여 줍니다.

**멘트:** “응답 증거가 없으면 호출 경로와 횟수는 남더라도 실제 반환된 정보주체나 개인정보 항목은 확인할 수 없습니다. 그래서 이 구현은 확인되지 않은 수를 0으로 만들지 않고 `알 수 없음`으로 남깁니다. 로그 보존 범위가 사고 분석의 한계를 결정한다는 점도 함께 보여 줍니다.”

**자막:** `응답 증거가 없으면 0이 아니라 알 수 없음`

### 6. 한국어 개인정보 분류 — 문맥 예시 (약 35초)

**화면:** `/privacy-lab`을 열고 `ko96-h01` 본인 천식 진단 사례와 `ko96-o01` 일반 건강 안내 사례를 차례로 선택합니다. 로컬 추론을 시연한다면 결과를 그대로 보여 주고, 응답이 늦으면 저장된 비교 결과를 사용합니다.

**멘트:** “이 실험실은 여덟 가지 기술 라벨로 한국어 필드 설명과 문맥을 분류합니다. 두 예시에 모두 천식이라는 단어가 있지만 한쪽은 특정인의 진단이고 다른 쪽은 일반 안내입니다. 단어 일치만으로 분류하면 일반 안내를 건강정보로 오분류할 수 있습니다. 화면의 모델 결과는 실제로 나온 대로 보여주며, 기대 라벨에 맞추려고 입력을 바꾸지 않습니다.”

**자막:** `단어가 아니라 필드와 문맥을 검토`

### 7. 한국어 분류 — 평가 결과와 오분류 (약 35초)

**화면:** 평가 결과 탭의 96건 비교를 보여주고, 이어 실험 탭의 오분류 예시 필터를 열어 몇 사례를 확인합니다.

**멘트:** “직접 작성한 합성 개발 사례 96건에서 SemIf는 82건, 85.4퍼센트였고 같은 Qwen3 4B 계열 모델의 JSON 방식은 81건, 84.4퍼센트였습니다. 규칙 기준선은 73건, 76퍼센트였습니다. 두 모델 방식의 차이는 한 건뿐이라 우열을 주장할 수 없습니다. 오분류 14건 중 12건은 선택지 상대 점수가 90퍼센트 이상이었습니다. 이 점수는 정답 확률이 아니므로 결과는 사람 검토 후보로만 다룹니다.”

**자막:** `96건 합성 개발 셋 | SemIf 85.4% · JSON 84.4% · 규칙 76.0%`

### 8. 마무리 — 범위와 다음 단계 (약 15초)

**화면:** 평가 결과 또는 대시보드의 요약 화면. 영상 끝에는 개인정보 분류가 자동 법률 판단이 아니라는 문구를 남깁니다.

**멘트:** “이번 데모는 사전 인가 검증과 저장 증거 기반 사후 조사를 연결하고, 한국어 개인정보 후보를 검토하는 가능성을 확인했습니다. 합성 평가만으로 실제 서비스 성능이나 법률상 유출 범위를 확정할 수는 없습니다. 다음 단계에서는 독립 검증셋과 서비스별 접근 정책으로 오탐·누락을 평가하겠습니다.”

**자막:** `자동 법률 판단이 아닌, 근거가 있는 보안 검토 보조`

## 화면에 숫자를 보여줄 때

- 사후 조사 숫자는 선택 실행의 기록 범위라고 함께 말합니다. 저장되지 않은 요청, 게이트웨이를 우회한 접근, 잘린 응답은 이 분석에서 알 수 없습니다.
- 96건은 합성 개발용 평가셋입니다. 독립 블라인드 평가나 실제 서비스의 정확도로 표현하지 않습니다.
- SemIf는 공식 TypeSafe Jev 제품과 구분되는 오픈소스 구현입니다. 선택지 점수는 보정된 확률이 아닙니다.
- 결합 결과는 후보 범위입니다. 개인정보보호법상 특정 가능성이나 신고 의무를 이 데모가 자동 확정한다고 말하지 않습니다.
